# Orders

These are the bootstrap orders of KAAL, as given. They are the origin record.
Nothing in this repository should exist that cannot trace back to them.

They are not assumed complete. If a failure arrives that these orders cannot
adequately perceive or control, that failure is evidence for what the bootstrap
was missing, and it is recorded as such in `learning/`.

---

## MOVE — Main Offers Valuable Experience

`main` is the accepted experience from which KAAL operates and learns.

Candidate change happens away from `main` and crosses an observable integration
boundary before becoming accepted experience.

Two different kinds of evidence matter:

**Tested → Verified.** A Program executed an explicit test and established
exactly what that test computes.

**Judged → Validated.** A Human or Agent evaluated something that cannot
honestly be reduced to the test that ran.

Neither means universally true. Later experience may overturn either. `main`
remains valuable because it preserves what was accepted, under which controls,
as the next starting point.

## First Order — HAPTIC

*Human → Agent → Program To Improve Controls*

When experience teaches something, ask where that learning belongs.

Keep Human judgement where meaning is still required. Move repeated Human
correction into Agent capability when earned. Move sufficiently understood and
computable Agent behaviour into Program control.

The purpose is not automation for its own sake. The purpose is progressively
stronger, cheaper and more deterministic control without pretending that
judgement is computation.

## Second Order — EEE

*Engineer ↔ Embed → External → feedback → Engineer*

Engineer and Embed form the recursive development loop. Engineer develops KAAL;
Embed tests what actually survives separation from the engineering context.

External exposes KAAL to reality it did not construct, including other
repositories and independent contexts. External exists because an internally
coherent learning system can still become wrong about the world.

What Embed and External teach about KAAL must feed subsequent engineering.
External observation does not give KAAL ownership of the thing it observes.

Exercise Embed and External frequently. Do not wait for Engine to be "finished."

## Third Order — PDCA

*Plan → Do → Check → Act*

Plan makes the intended change and its refusal conditions clear before
implementation settles the answer.

Do performs the work without rewriting Plan to flatter the result.

Check establishes what the available evidence actually demonstrates. A green
test establishes only what that test computes.

Act preserves what was learned — including failed hypotheses, limitations,
corrections and changed interpretations — so the next cycle can learn from this
one.

## Fourth Order — BASS

*Bare → AGENTS.md → Skill → Script*

BASS describes increasing control over Agent behaviour.

**Bare:** rely on model capability.
**AGENTS.md:** persist guidance the Agent should apply.
**Skill:** package a bounded capability with procedure, evidence standard,
outputs, stopping conditions and limitations.
**Script:** execute the sufficiently computable part deterministically.

BASS is not a mandatory march to the right. After a success or failure, ask for
the least-rightward control strong enough for what has actually been learned.

## Bootstrap discipline

MOVE provides the substrate. HAPTIC determines where learning moves. EEE makes
it meet the world. PDCA structures each change. BASS determines how Agent
control matures.

Do not bootstrap findings schemas, bug ledgers, roadmap grammars, release
machinery, evidence formats, review ceremonies, mutation rules, or other
mechanisms simply because an earlier KAAL eventually acquired them.

Let failures earn them.

The objective is not to reconstruct the previous KAAL. The objective is to build
a system capable of learning what KAAL needs to become.
