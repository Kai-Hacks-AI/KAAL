# Standalone use of kaal-testing: Architecture

- **testing/A50** [testing/F146, testing/F147, testing/F148, testing/N32]: **Pack, install, observe from outside.** The Cases pack the package (`npm pack`, no scripts), install the tarball into a fresh empty directory under the system temp folder (Hosting and `c8` come from the registry), and observe only the installed copy: the command, the exports, the manifest, the tree and the files. The package under test is the repository package by default; `KAAL_TESTING_PACKAGE` points the Cases at a reference for validation only. Failures of the machine, the registry or npm are errors (UNKNOWN), never RED; only a failure npm attributes to the package is RED. The KAAL family that arrived is read from the lockfile (nested and transitive included) and checked against a fixed allowlist. The judged part keeps what a Case cannot decide, the reading of a transcript, in `trial/`: protocol, prompt, key and fixture are fixed by the PLAN, the runs are the DO's, and the Case checks that the record is complete, isolated, quotes the transcript and meets the declared acceptance. Test Cases are Testing's own, beside the package, and use nothing of KAAL.

**Pattern borrowed from controls (N8, T777):** scan the Skill text for names from outside, allow only declared dependencies, prove the package works away from the repository. **Where Testing differs:** it has runtime dependencies, so "away from the repository" is an install into an empty directory, not a folder copy, and the scan runs on the installed files.
