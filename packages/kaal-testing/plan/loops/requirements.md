# Loops as a Graph: Requirements

Each Requirement names, in brackets, the Intents it serves.

## Functional

- **testing/F105** [testing/I29]: **The consumer declares its loops.** A Loop Declaration is data owned by the consuming package: an ordered list of levels, outermost first. A level has a `name`, the Node `kinds` that belong to it and the context `folders` it covers (path prefixes). The folder is the loop: a Case file sits in the folder of the item it proves. A kind belongs to one level and a folder to one level. A missing, empty, duplicated or overlapping entry is a finding. One level may be marked as holding Defects beside another level (the Defect sits next to Requirements). Testing prescribes no names and no depth.
- **testing/F106** [testing/I30, testing/I33]: **A Case sits beside its item.** A Case file is named for its item and sits in that item's folder, such as `01-intent/I1.test.mjs`, `02-requirements/functional/F4.test.mjs`, `03-architecture/A7.test.mjs`, `05-src/<module>.test.mjs` and `06-defects/D20.test.mjs`. Its loop is the level whose folder contains it, and its target is the Node it is named for, which the Graph must resolve and whose kind must belong to that level. A title's brackets (testing/F84) may add further targets of the same level. A Case file in a folder no level covers, with no item of that name, or targeting another level, is a finding. A code Case's item is the module it sits beside and its outward Edge is to an Architecture element; a module's mapping to Architecture is the consumer's (testing/F105).
- **testing/F107** [testing/I30]: **Traces between items go outward.** Every Edge between two items runs from a level to a strictly outer level. The single exception is an Edge from a Defect to the Requirement it reveals: a Defect sits next to Requirements, so that Edge is the only one allowed between two items of the same level. Any other same-level Edge, an Edge to an inner level, and any cycle are findings naming the Edge. The Edge types are the ones the item owners define (for example Requirements' `Serves`); Testing reads the ones the declaration names and defines none of them.
- **testing/F108** [testing/I30]: **A trace that cannot be proven is `unknown`.** A target that is not yet a Node, a reference the Graph does not resolve, or an item whose kind the declaration does not place gives `unknown` for that Edge, never `outward`. Testing gives the result. Whether a check passes is the consumer's.
- **testing/F109** [testing/I31]: **A Defect is a Node revealing a Requirement.** A Defect Node carries the record members of testing/F98 and one `reveals →` Edge to the Requirement that is missing or wrong, added by the Change that fixes it. Before that Edge exists the Defect is confirmed by its RED Case alone (testing/F99). A Requirement never points at a Defect.
- **testing/F110** [testing/I31]: **Answered is computed down the chain.** `answered(graph, declaration, runs, defect)` is `established` only when the Defect's confirming Run (testing/F99) exists, the revealed Requirement exists, and every item reachable from it inward down to code has at least one Case whose latest observation is a pass at the confirming Case's version. Otherwise it is `unknown` or `open`, with the first missing item named. A status word in the record is a claim that this computation confirms (testing/F100).
- **testing/F111** [testing/I32]: **Plans by selector.** `plan(graph, declaration, selector)` gives the Case identities and files to run, for one of: a `loop` (the Cases whose folder is that level); a `change` (the affected items given by the caller, followed inward and back through `tests →` with `impact`, so that an `unknown` impact is reported and fails closed); `red` (the Cases whose target is an open Defect); `promotion` (every Case of every level). The caller supplies the Change's items; Change decides what they are.
- **testing/F116** [testing/I33]: **A move keeps the identity.** A Case's identity is its permanent `owner/T<n>` (testing/N2); its location gives its loop and its target, not its identity. Moving a Case beside its Node keeps its T-number, so every existing citation of it stays valid, and a Case declared in two places stays a finding (testing/F86). The migration records each move as `{ identity, from, to }`, and `tests →` is re-derived from the new place, so the trace is carried and never silently re-minted. A move changes the Case file's bytes and therefore its version (testing/F89): earlier Runs no longer stand for it (testing/F40), and a Defect confirmed before the move is confirmed again in one Run at the new version before it can be answered (testing/F99). A new Case takes the next T-number as today.
- **testing/F115** [testing/I33]: **Suites are collected from context Cases.** `04-test` holds no Cases. A suite (`package-check`, `boundary-check`, `engineering-check`) is a membership over the Cases the context folders define. Testing's Skill gives the capability of composing one in two parts. *Computed*: scripts in the Skill walk the Graph from Intent through Requirements to Architecture and select the Cases by trace (the Cases of an Architecture element and of everything it realizes, the Cases of a Requirement subtree, the boundary-relevant N and A), reporting `unknown` where the graph is incomplete. *Judged*: what the graph cannot decide, such as which Cases make a coherent boundary suite, is judged by the Skill, an Agent or a person, and the judgment is stated and kept apart from the computed part. A suite is never presented as complete beyond what the graph shows (testing/F88). How a collector tells a suite's membership, from Node frontmatter or from the Case, is open.
- **testing/F112** [testing/I32]: **RED is a role, inverted by the Plan.** In a `red` or `promotion` Plan, a Case targeting an open Defect is expected to fail. It is reported as `red as expected` while the Run's own result stays `failed` and listed (testing/F28). A pass is a finding (`unexpectedly green`) that asks for the Defect to be answered. A Case failing while its Defect is answered is a regression. The role is never produced by a `skip` or `todo` marker, which this PLAN does not use for RED. The existing rule stands unchanged: a skipped or `todo` Case is RED and is reported (testing/I1, testing/F2).
- **testing/F113** [testing/I32]: **Execution uses what exists.** A Plan runs by file with `node:test`, narrowed by name pattern to the Case identities (a title's leading identity is unique), through Testing's reporter, and maps each reported test back to its Case identity. A reported test that maps to no planned Case, or a planned Case never reported, is `unknown`.
- **testing/F114** [testing/I32]: **Open REDs are counted.** `promotion` gives the number of open Defects with their Cases, so a Change that adds Cases (raising it) or answers (lowering it) is visible. Whether growth is accepted is Change's judgment (FAR's sibling in testing/C54), and the ratchet itself stays open there.

## Nonfunctional

- **testing/N23** [testing/I30]: `loops` is pure and deterministic. It reads only what it is given: the declaration, a Graph and Case text. It reads no host and no clock, and the same input gives the same findings in the same order. It imports `kaal-testing/model` and `kaal-testing/traces`, and the Graph only through the data it is given.
- **testing/N24** [testing/I29]: A consumer with one loop, or with six, works with no change to Testing. Adopting the Graph is gradual: items that are not yet Nodes degrade to `unknown`, never to a pass.
