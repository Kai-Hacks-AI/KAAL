# Loops as a Graph: Requirements

Each Requirement names, in brackets, the Intents it serves.

## Functional

- **testing/F105** [testing/I29]: **The consumer declares its loops.** A Loop Declaration is data owned by the consuming package: an ordered list of levels, outermost first. A level has a `name`, the Node `kinds` that belong to it and the case `locations` (path prefixes) whose files are its Cases. A kind belongs to one level and a location to one level. A missing, empty, duplicated or overlapping entry is a finding. One level may be marked as holding Defects beside another level (the Defect sits next to Requirements). Testing prescribes no names and no depth.
- **testing/F106** [testing/I30]: **A Case's loop is its location.** A Case's loop is the level whose location contains its file. The Case's target is read as testing/F84 reads it. The target must be a Node the Graph resolves, and its kind must belong to the Case's own level. A Case whose file is in no declared location, or whose target is of another level, is a finding.
- **testing/F107** [testing/I30]: **Traces between items go outward.** Every Edge between two items runs from a level to the same or an outer level. The one same-level Edge is from a Defect to the Requirement it reveals. An Edge to an inner level, or any cycle, is a finding naming the Edge. The Edge types are the ones the item owners define (for example Requirements' `Serves`); Testing reads the ones the declaration names and defines none of them.
- **testing/F108** [testing/I30]: **A trace that cannot be proven is `unknown`.** A target that is not yet a Node, a reference the Graph does not resolve, or an item whose kind the declaration does not place gives `unknown` for that Edge, never `outward`. Testing gives the result. Whether a check passes is the consumer's.
- **testing/F109** [testing/I31]: **A Defect is a Node revealing a Requirement.** A Defect Node carries the record members of testing/F98 and one `reveals →` Edge to the Requirement that is missing or wrong, added by the Change that fixes it. Before that Edge exists the Defect is confirmed by its RED Case alone (testing/F99). A Requirement never points at a Defect.
- **testing/F110** [testing/I31]: **Answered is computed down the chain.** `answered(graph, declaration, runs, defect)` is `established` only when the Defect's confirming Run (testing/F99) exists, the revealed Requirement exists, and every item reachable from it inward down to code has at least one Case whose latest observation is a pass at the confirming Case's version. Otherwise it is `unknown` or `open`, with the first missing item named. A status word in the record is a claim that this computation confirms (testing/F100).
- **testing/F111** [testing/I32]: **Plans by selector.** `plan(graph, declaration, selector)` gives the Case identities and files to run, for one of: a `loop` (the Cases whose location is that level); a `change` (the affected items given by the caller, followed inward and back through `tests →` with `impact`, so that an `unknown` impact is reported and fails closed); `red` (the Cases whose target is an open Defect); `promotion` (every Case of every level). The caller supplies the Change's items; Change decides what they are.
- **testing/F112** [testing/I32]: **RED is a role, inverted by the Plan.** In a `red` or `promotion` Plan, a Case targeting an open Defect is expected to fail. It is reported as `red as expected` while the Run's own result stays `failed` and listed (testing/F28). A pass is a finding (`unexpectedly green`) that asks for the Defect to be answered. A Case failing while its Defect is answered is a regression. No `skip` or `todo` marker is used (testing/I1, testing/F2).
- **testing/F113** [testing/I32]: **Execution uses what exists.** A Plan runs by file with `node:test`, narrowed by name pattern to the Case identities (a title's leading identity is unique), through Testing's reporter, and maps each reported test back to its Case identity. A reported test that maps to no planned Case, or a planned Case never reported, is `unknown`.
- **testing/F114** [testing/I32]: **Open REDs are counted.** `promotion` gives the number of open Defects with their Cases, so a Change that adds Cases (raising it) or answers (lowering it) is visible. Whether growth is accepted is Change's judgment (FAR's sibling in testing/C54), and the ratchet itself stays open there.

## Nonfunctional

- **testing/N23** [testing/I30]: `loops` is pure and deterministic. It reads only what it is given: the declaration, a Graph and Case text. It reads no host and no clock, and the same input gives the same findings in the same order. It imports `kaal-testing/model` and `kaal-testing/traces`, and the Graph only through the data it is given.
- **testing/N24** [testing/I29]: A consumer with one loop, or with six, works with no change to Testing. Adopting the Graph is gradual: items that are not yet Nodes degrade to `unknown`, never to a pass.
