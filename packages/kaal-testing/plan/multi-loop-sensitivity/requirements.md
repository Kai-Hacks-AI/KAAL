# Multi-Loop Testing and Sensitivity: Requirements

Each Requirement names, in brackets, the Intent it serves. All answer `testing/I44`.

## Functional

- **testing/F156** [testing/I44]: **Composable testing dimensions (`Concern/Claim` × `Evidence method/boundary`).** `skills/kaal-testing/SKILL.md` updates its frontmatter `description` for discovery alignment (judged by review and trial) and replaces `## The three loops` with `## Testing loops`. The section teaches two composable dimensions rather than a fixed triad or a monolithic chain:
  - **Concern / Claim:** what expectation is evaluated and who owns it (`src -> architecture -> requirements -> intent`, extensible with additional concerns on top).
  - **Evidence method / boundary:** what observation or judgment supports a claim, explicitly preserving **Architecture conformance** (`permitted` / `prohibited` / `undecidable` + validation judgment), **Capability acceptance** (delivered package installed fresh, public interface only, supported hosts, promised failures), **Implementation** (test-first internal behaviour: do not introduce functionality without a justified obligation), and **Judgment** (when an outcome cannot be settled by a deterministic oracle).
  - **Qualified reuse:** Reuse an observation where its execution conditions and provenance satisfy each supported claim. Keep each inference explicit; do not duplicate runs solely to duplicate labels, and do not reuse evidence where a claim requires an independent execution (for example, a fresh consumer installation versus a workspace run).
  Whether the Skill effectively teaches this is judged by the Skill trial (`testing/C72`), never by text-matching regexes.
- **testing/F157** [testing/I44]: **Behavioural RED, Targeted Mutation Verification, and unrequested-behaviour handling.** `## Testing loops` teaches two sensitivity checkpoints at loop boundaries:
  - **Behavioural RED:** before implementing, run the loop's tests against an inert stub (or unfixed target) with valid shape returning neutral values while preserving unrelated valid exports/behaviours when testing a focused claim; the run must fail on a behavioural assertion, whereas a missing module, syntax error, or setup failure is *blocked* (UNKNOWN), never RED evidence.
  - **Targeted Mutation Verification:** after turning GREEN, challenge the tests with targeted mutations tied to authoritative claims and concrete witness inputs; a kill requires that the intended behavioural assertion detects the introduced violation (never just an unrelated error or a broad stub masked by an unrelated check), outcomes are classified as `killed`, `survived`, `invalid`, or `unresolved`, and a surviving mutant is bounded evidence that the suite did not reject that change.
  - **Narrowed rule for uncovered behaviour & 4-kind taxonomy:** Do not introduce functionality without a justified obligation. When a mutation exposes behaviour not covered by existing Cases, establish its contractual basis, necessity, and consumer dependencies (checking repo consumers and noting that zero repo consumers does not prove zero external consumers for a public export) before proposing tests, a contract clarification, or removal. Do not remove behaviour solely because no existing Case requires it. Classify uncovered behaviour using Testing's existing four finding kinds in [references/findings.md](../../skills/kaal-testing/references/findings.md) without adding a fifth kind: `unknown` when authority or necessity is unresolved, `architectural concern` when responsibility placement or duplication is suspected, and `potential defect` only for a plausible expectation violation (never merely untested behaviour) — leaving Defect creation, placement, correction, and closure to Review, Defect, and Architecture.
  Whether the Skill effectively teaches this is judged by the Skill trial (`testing/C72`).

## Judged Skill Trial Protocol (`testing/C72`)

Whether `## Testing loops` achieves `testing/I44` is established by a **judged Skill trial** in `testing/C72`, never by deterministic wording checks or vocabulary recall:

1. **Independent subject:** Run the trial on a bounded subject independent of the `testing/C73` `lib/contracts.mjs` pilot so pilot context cannot leak into the trial.
2. **Non-disclosing bounded task:** Give agents a bounded task that embeds five deliberately distinct evidence needs — (a) one behaviour with an unambiguous expected result, (b) one architectural boundary, (c) one setup failure that must not be called behavioural RED, (d) one plausible test gap exposed by mutation, and (e) one underspecified or judgment-only claim — **without naming or disclosing those five needs in the prompt**.
3. **Frozen assessment key:** Write and freeze the assessment key **before** authoring the new `SKILL.md` wording in `testing/C72`.
4. **Comparable arms & run count:** Run `n = 2` fresh agent runs per arm — control arm using the existing `SKILL.md` on `main` vs. updated arm using the new `SKILL.md` from `testing/C72` — keeping task, environment, permissions, and starting artifacts identical between arms.
5. **Verified Skill loading:** Explicitly place/deliver the arm's `SKILL.md` in the agent's skill location (or verbatim prompt context with recorded SHA-256 prompt hash) and verify from the transcript that the agent loaded and read it.
6. **Separate judging session:** Run judgment in a separate session from execution, retaining raw transcripts, prompt hashes, and an assessment citing verbatim excerpts found in the transcripts.
7. **Reasoned judgment:** Assess whether the agent identifies authoritative claims and traces them to owners, chooses and composes concerns and evidence methods (reusing observations only where conditions/provenance hold), separates behavioural RED from blocked execution, challenges inadequate claims, and exposes unpinned contracts via witness-backed mutations — as a reasoned judgment, never a mechanical 5-of-5 score.
