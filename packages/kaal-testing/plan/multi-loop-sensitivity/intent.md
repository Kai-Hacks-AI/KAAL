**What is missing.** Two gaps sit side by side in how `kaal-testing` guides outer-to-inner TDD:

1. **Conflating a fixed three-item list with composable dimensions.** `skills/kaal-testing/SKILL.md` currently groups testing under `## The three loops` (`Architecture conformance`, `Capability acceptance`, `Implementation`), which mixes *execution perspectives/boundaries* with *concern/claim layers*. Teaching a concern chain (`src -> architecture -> requirements -> intent`, extensible upward) *without* preserving those assurance perspectives would risk implying that "requirements testing" replaces delivered-package acceptance or that every concern needs a separate physical test run. Instead, Testing must teach **two composable dimensions**:
   - **Concern / Claim:** what expectation is evaluated and who owns it (intent, requirements, architecture, defect, or higher concerns).
   - **Evidence method / boundary:** what observation or judgment supports that claim (architecture conformance with `permitted`/`prohibited`/`undecidable`, delivered-package acceptance with fresh installation/public interface/promised failures, implementation tests, or judgment).
   One observation can support multiple concerns through separate, explicitly qualified inferences when its execution conditions and provenance satisfy each claim—without forcing redundant runs solely to duplicate labels, and without reusing evidence where a claim requires an independent execution (such as a fresh consumer install vs. a workspace run).
2. **No explicit sensitivity checkpoints at loop boundaries.** KAAL already uses inert-stub RED and targeted mutation checks in isolated places (`kaal-core/src/conformance.ts`, `test/engineer/duplicates-mutations.mjs`), yet the Skill does not teach the general, consumer-agnostic discipline: proving a loop's tests fail on a behavioural assertion against an inert stub before implementation (distinct from a blocked setup/syntax failure), and challenging GREEN code with targeted mutations tied to authoritative claims and witness inputs to surface unpinned invariants as calibrated findings using Testing's existing four finding kinds.

- **testing/I44**: Testing teaches two composable dimensions — **Concern/Claim** (`src -> architecture -> requirements -> intent`, extensible upward, allowing evidence reuse only where execution conditions and provenance satisfy each supported claim) and **Evidence method/boundary** (preserving architecture conformance, delivered capability acceptance, implementation TDD, and judgment) — paired with Behavioural RED and Targeted Mutation Verification, keeping the Skill consumer-agnostic, minimal (`SKILL.md` + existing `references/findings.md` only), strictly BASS-ordered (Skill first; any reusable Script deferred to a later Change only if earned), and respectful of Defect, Review, and Architecture ownership boundaries.

Principle: follow BASS (`Bare < Agent < Skill < Script`). Teach the method cleanly in the Skill first, establish teaching effectiveness through a judged Skill trial on an unbiased 5-item bounded task (`testing/C72`), apply the sensitivity protocol as a one-off trial on `lib/contracts.mjs` whose durable output is justified regression Cases integrated into `npm test` (`testing/C73`, no standing mutation harness), close the collector with one structured ACT retro over `[testing/C71, testing/C72, testing/C73]` before automatic promotion, and track triad wording alignment in `payload/Testing.md` / `README.md` plus `engineering/` or `.kaal/` wiring as explicit follow-ups.

**Out of scope.** No new exports, no `skills/kaal-testing/scripts/`, no extra `references/` files, no fifth finding kind, no edits to `capability/Testing.md` or `payload/Testing.md`, no standing mutation harness in `npm test`, no ownership of Defect creation/lifecycle/closure, and no changes to `engineering/`, `.kaal/`, or `.github/`.
