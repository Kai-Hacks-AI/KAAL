# Multi-Loop Testing and Sensitivity: Intent

This is `testing/C71`, a PLAN Change. It ships no package code and changes no Skill. `testing/C72` (DO, not yet authorized) updates the `kaal-testing` Skill and executes the judged Skill trial. `testing/C73` (DO, not yet authorized) runs a one-off sensitivity trial on `packages/kaal-testing/lib/contracts.mjs` and turns its surviving-mutant findings into ordinary durable Cases beside `test/contracts.test.mjs`. Provisional ids (taking the next free block after PR #2120's `testing/C69`–`C70`, `I43`, `F152`–`F155`, `N34`, `A52`, `T378`–`T380`): recheck across all `kaal/testing/*` collectors just before DO.

**What is missing.** Two gaps sit side by side in how `kaal-testing` guides outer-to-inner TDD:

1. **A fixed list of three loops instead of composable loops.** `skills/kaal-testing/SKILL.md` treats testing as a fixed triad (`Architecture conformance`, `Capability acceptance`, `Implementation`). In practice, testing composes upward across clear loop boundaries (`src -> architecture -> requirements -> intent`, extensible with further loops on top), and evidence from one layer can serve multiple concerns without merging them, while keeping each loop's runnable evidence strictly separate.
2. **No explicit sensitivity checkpoints at loop boundaries.** KAAL already uses inert-stub RED and targeted mutation checks in isolated places (`kaal-core/src/conformance.ts`, `test/engineer/duplicates-mutations.mjs`), yet the Skill does not teach the general, consumer-agnostic discipline for outer-to-inner TDD: proving a loop's tests fail on a behavioural assertion against an inert stub before implementation (rather than failing blocked on a missing module or environment error), and challenging GREEN code with targeted contract-breaking mutations to report unpinned invariants as `potential defect` findings with their owning claim.

- **testing/I44**: Testing teaches a composable multi-loop model (`src -> architecture -> requirements -> intent`, extensible upward, with evidence able to serve multiple concerns without merging them) paired with Behavioural RED and Targeted Mutation Verification at loop boundaries, keeping the Skill consumer-agnostic, minimal (`SKILL.md` + existing `references/findings.md` only), strictly BASS-ordered (Skill first; any reusable Script deferred to a later Change only if earned), and respectful of Defect, Review, and Architecture ownership boundaries.

Principle: follow BASS (`Bare < Agent < Skill < Script`). Teach the method cleanly in the Skill first, validate teaching quality through a judged Skill trial (`testing/C72`), apply the method as a one-off trial on `lib/contracts.mjs` whose lasting output is durable contract Cases beside `test/contracts.test.mjs` (`testing/C73`, no standing mutation harness inside `npm test`), and defer any `engineering/` or `.kaal/` wiring to a separate follow-up Change.

**Out of scope.** No new exports, no `skills/kaal-testing/scripts/`, no extra `references/` files, no edits to `capability/Testing.md` or `payload/Testing.md`, no standing mutation harness in `npm test`, no ownership of Defect lifecycle or routing, and no changes to `engineering/`, `.kaal/`, or `.github/`.
