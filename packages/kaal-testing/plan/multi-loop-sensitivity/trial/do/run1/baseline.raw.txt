### 1. Assessment of Each Claim in `budget-gate/spec.md`

- **BG-I1** *(Owner/Concern: Intent)* — *"Prevent accidental overspend by checking itemized integer costs against a numeric budget limit before an action proceeds."*
  - **Assessment**: **Point at judgement.** Whether this approach actually prevents accidental overspend in real use—and specifically *"before an action proceeds"*, given that `budget.mjs` only exports a passive calculation function `evaluateBudget(items, limit)` rather than gating execution itself—is a fitness-for-purpose/outcome claim that no unit test on `budget.mjs` can settle.
  - **Evidence needed / missing**: Evidence of the verified requirement behavior (`BG-R1`, `BG-R2`) together with integration/usage evidence showing how callers enforce the returned `{ over }` before proceeding with actions, judged by an independent reviewer (e.g., product/system owner from a seat other than the claim's author) and recorded as a judgement. Currently missing.

- **BG-R1 [BG-I1]** *(Owner/Concern: Requirements)* — *"`evaluateBudget(items, limit)` sums each item's `cost` (non-negative integer) and returns `{ over: boolean, remaining: number }`, where `over` is `total > limit` (exact equality `total === limit` is within budget: `over: false, remaining: 0`) and `remaining` is `limit - total`."*
  - **Assessment**: **Verify** (with minor edge questions to clarify).
    - **Observable**: return value `{ over, remaining }` from `evaluateBudget(items, limit)`.
    - **Oracle**: `total = sum(item.cost)`, `over === (total > limit)`, `remaining === limit - total` (including `total === limit` yielding `{ over: false, remaining: 0 }`).
  - **Unresolved questions / edge cases**: Does `spec.md` permit non-integer finite `limit` (e.g., `10.5`, which `budget.mjs` allows)? What should happen for sums exceeding `Number.MAX_SAFE_INTEGER` (where JS loses integer precision) or `limit === -0` with `items = []` (where `limit - total` yields `-0`)?
  - **Evidence needed / missing**: Only two happy-path cases (`total < limit`, `total > limit`) exist in `budget.checks.mjs`. Missing: boundary equality (`total === limit`), empty `items` (`[]`), `limit === 0`, `cost === 0`, single/multi-item sums, fractional finite `limit` (if permitted), acceptance-loop verification across supported hosts via fresh install, and coverage data (`cover`).

- **BG-R2 [BG-I1]** *(Owner/Concern: Requirements)* — *"Any item with negative, non-integer, or non-finite `cost`, or a negative or non-finite `limit`, throws a `RangeError`."*
  - **Assessment**: **Verify** for the named invalid values, plus **Challenge** on unspecified malformed inputs.
    - **Observable**: synchronous exception thrown by `evaluateBudget(items, limit)`.
    - **Oracle**: `err instanceof RangeError` for `cost < 0`, non-integer `cost`, non-finite `cost` (`NaN`, `Infinity`, `-Infinity`), `limit < 0`, and non-finite `limit`.
  - **Unresolved questions**: `spec.md` does not specify what should happen for non-array `items` (`budget.mjs` throws `TypeError`), `null`/non-object elements or missing `cost` (`item?.cost` gives `undefined`, throwing `RangeError` rather than `TypeError`), or non-number `limit`/`cost` (currently `RangeError`). Put these contract boundaries to the Requirements owner without inventing expectations.
  - **Evidence needed / missing**: Currently **zero** working checks verify `BG-R2` (`broken.checks.mjs` fails at import time and does not even call `evaluateBudget`). Tests are needed in both the implementation loop and capability acceptance loop for every specified `RangeError` condition.

- **BG-R3 [BG-I1]** *(Owner/Concern: Requirements)* — *"Large batches should complete promptly."*
  - **Assessment**: **Challenge.** Both *"large batches"* (item count/shape) and *"promptly"* (latency/complexity bound and target host) are too underspecified to yield an unambiguous oracle. Under `kaal-testing`, Testing must not invent a threshold or batch size to obtain GREEN; put the question to the Requirements owner to define measurable bounds (or designate who will judge if left qualitative), and report `BG-R3` as **unknown**.
  - **Evidence needed / missing**: Owner-supplied batch-size, host, and timing/scaling criteria first; then repeatable timing/benchmark evidence against those criteria on supported hosts. Currently missing.

- **BG-R4 [BG-I1]** *(Owner/Concern: Requirements)* — *"Error messages should be clear and helpful to operators."*
  - **Assessment**: **Point at judgement.** Clarity and helpfulness to operators are fitness-for-purpose qualities that cannot be verified by an automated test; asserting exact wording (e.g., `"each item cost must be a non-negative integer"`) would be a brittle Case checking incidental wording / author's preferred phrasing rather than operator helpfulness.
  - **Evidence needed / missing**: Actual error messages emitted across `budget.mjs` error paths (`limit`, `items`, `item.cost`) alongside realistic operator failure contexts (note that `budget.mjs` currently omits which item index or invalid value failed), reviewed and judged by an operator or independent reviewer from a seat other than the claim's/code's author, and recorded as a judgement. Currently missing.

- **BG-A1 [BG-I1]** *(Owner/Concern: Architecture)* — *"`budget.mjs` is pure domain logic with no host filesystem or subprocess access (it must not import `node:fs` or `node:child_process`)."*
  - **Assessment**: **Verify** (for declared host-module boundaries via an Architecture conformance check) + **Validation/Judgement** (for *"pure domain logic"* beyond static imports, e.g., host globals/environment access and indirect host calls).
  - **Unresolved questions**: Does *"pure domain logic"* also prohibit `process.env` access (`budget.mjs` line 18), or only `node:fs` and `node:child_process`? Put to the Architecture owner/validator.
  - **Evidence needed / missing**: A capability boundary declaration as data plus an automated Architecture conformance check demonstrating all three required cases (**permitted**, **prohibited** failing with location, and **undecidable** constructs surfaced for recorded validation), alongside recorded architectural validation of `process.env` and any uninspectable/indirect host access. Currently completely absent—and by inspection, `budget.mjs` directly imports `node:fs` and reads `process.env`.
