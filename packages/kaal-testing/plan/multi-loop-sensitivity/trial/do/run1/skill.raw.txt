## 1. Assessment of Each Claim in `budget-gate/spec.md`

### `BG-I1` (Concern: Intent)
> "Prevent accidental overspend by checking itemized integer costs against a numeric budget limit before an action proceeds."
- **Decision:** **Verify** (via its decomposed functional/architectural criteria `BG-R1`, `BG-R2`, `BG-A1`, and capability acceptance) + **Point at judgement** (for overall Intent soundness and fitness for purpose).
- **Why & unresolved questions:**
  - Whether checking `evaluateBudget(items, limit)` actually prevents accidental overspend *before an action proceeds* cannot be settled by a unit check alone: `budget.mjs` only exports a passive evaluation function returning `{ over, remaining }` and does not itself gate any action. An independent reviewer (not the claim's author) must judge whether this interface boundary and its intended caller wiring soundly satisfy the Intent, and whether permitting non-integer `limit` values (while restricting `cost` to integers) is fit for purpose against floating-point rounding or overspend risk.
  - Because `BG-R1` is only partially checked and `BG-R2`/`BG-A1`/acceptance are unverified or contradicted, `BG-I1` currently lacks sufficient evidence.
- **Evidence needed / missing:** Complete verification of `BG-R1`, `BG-R2`, `BG-A1`, capability acceptance against a fresh install, and a recorded independent **judgement** on Intent soundness.

### `BG-R1` (Concern: Requirements, owns via `BG-I1`)
> "`evaluateBudget(items, limit)` sums each item's `cost` (non-negative integer) and returns `{ over: boolean, remaining: number }`, where `over` is `total > limit` (exact equality `total === limit` is within budget: `over: false, remaining: 0`) and `remaining` is `limit - total`."
- **Decision:** **Verify** (with **Challenge** on unspecified boundary/input cases).
- **Why & unresolved questions:**
  - **Observable & oracle:** Return value `{ over, remaining }` of `evaluateBudget(items, limit)`, where `over === (total > limit)` and `remaining === (limit - total)` (with `total === limit` yielding `{ over: false, remaining: 0 }`).
  - **Unresolved questions to put to the Requirements owner:**
    1. `budget.mjs` (lines 7–9) throws `TypeError` when `!Array.isArray(items)`—is that required/contractual (`spec.md` does not mention `items` type validation)?
    2. What is the intended handling for `limit = -0` (`-0 < 0` is `false`, so `evaluateBudget([], -0)` yields `remaining: -0`) and for sums exceeding `Number.MAX_SAFE_INTEGER` (where JS integer addition loses exactness)?
    3. Are fractional finite `limit` values (e.g. `10.5`) explicitly intended to remain valid?
- **Evidence needed / missing:**
  - Implementation-loop tests and capability acceptance tests covering: exact equality `total === limit` (`{ over: false, remaining: 0 }`), empty `items = []`, `cost = 0`, `limit = 0`, single/many items, and fractional finite `limit` (if confirmed valid).
  - **Behavioural RED** evidence against an inert stub and **Targeted Mutation Verification** (currently, mutating `total > limit` to `total >= limit` at `budget.mjs:18` would **survive** `budget.checks.mjs`).

### `BG-R2` (Concern: Requirements, owns via `BG-I1`)
> "Any item with negative, non-integer, or non-finite `cost`, or a negative or non-finite `limit`, throws a `RangeError`."
- **Decision:** **Verify** (for the stated conditions) + **Challenge** (on unspecified invalid-type cases).
- **Why & unresolved questions:**
  - **Observable & oracle:** Calling `evaluateBudget(items, limit)` with any stated invalid `cost` or `limit` throws an instance of `RangeError` (and, at capability acceptance, promises failure cleanly without side effects).
  - **Unresolved questions to put to the Requirements owner:**
    1. When an element in `items` is `null`, `undefined`, a primitive, or an object missing `.cost`, `budget.mjs` (`budget.mjs:12-15`) reads `item?.cost` (`undefined`) and throws `RangeError`. Is `RangeError` intended for malformed/non-object items, or should that be `TypeError`?
    2. When `limit` is a non-number (e.g., `"10"`, `null`), `budget.mjs` (`budget.mjs:4-6`) throws `RangeError`. Is `RangeError` intended rather than `TypeError`?
- **Evidence needed / missing:**
  - **Zero** passing checks currently verify `BG-R2`. Both implementation and capability acceptance tests are needed for: negative `cost` (both first and subsequent items), non-integer `cost` (`1.5`), non-finite `cost` (`NaN`, `Infinity`, `-Infinity`), negative `limit`, non-finite `limit` (`NaN`, `Infinity`, `-Infinity`), plus owner-clarified malformed `items`/non-number inputs, with Behavioural RED and mutation verification.

### `BG-R3` (Concern: Requirements, owns via `BG-I1`)
> "Large batches should complete promptly."
- **Decision:** **Challenge** (report as **unknown**).
- **Why & unresolved questions:**
  - Too underspecified to decide objectively: neither "large batches" (item count $N$) nor "promptly" (maximum latency, host/runtime conditions, complexity bound) has a defensible oracle. Per `kaal-testing`, we must not invent a threshold to obtain GREEN.
  - **Questions for the Requirements owner:** What batch size(s) represent a "large batch", what elapsed time limit (and host/execution environment) defines "promptly", and is a linear time/bounded memory requirement intended?
- **Evidence needed / missing:** Owner-defined quantitative acceptance criteria, followed by a reproducible performance check stating exact execution conditions and provenance.

### `BG-R4` (Concern: Requirements, owns via `BG-I1`)
> "Error messages should be clear and helpful to operators."
- **Decision:** **Point at judgement** (report as **unknown** until judged).
- **Why & unresolved questions:**
  - Whether error wording is "clear and helpful to operators" is a question of soundness and fitness for purpose that no test oracle can settle; exact-string assertions would be brittle checks on incidental wording and must be rejected.
  - **Who should judge & on what evidence:** An independent reviewer (from a seat that is not the claim's author, e.g. an operator representative) inspecting the error messages produced on every error path (`budget.mjs:5` `"limit must be a non-negative finite number"`, `budget.mjs:8` `"items must be an array"`, `budget.mjs:14` `"each item cost must be a non-negative integer"`), including noting for judgment that messages omit the offending value and failing item index.
- **Evidence needed / missing:** A recorded **judgement** from an independent seat reviewing the emitted error messages across all failure paths.

### `BG-A1` (Concern: Architecture, owns via `BG-I1`)
> "`budget.mjs` is pure domain logic with no host filesystem or subprocess access (it must not import `node:fs` or `node:child_process`)."
- **Decision:** **Verify** (via the **Architecture conformance** loop for explicit module-import boundaries) + **Point at judgement** (for undecidable / broader "pure domain logic" boundaries such as `process.env`).
- **Why & unresolved questions:**
  - The module-import restriction ("must not import `node:fs` or `node:child_process`") has an unambiguous mechanical check and oracle when declared as boundary data.
  - However, "pure domain logic" raises an architectural validation question beyond static `node:fs` / `node:child_process` imports: `budget.mjs:19` reads `process.env.BUDGET_AUDIT_FILE` (host process environment coupling) alongside `existsSync` (`budget.mjs:1,19`), and other indirect/dynamic host-access mechanisms could exist in general.
- **Evidence needed / missing:**
  - A runnable **Architecture conformance** check declaring allowed/prohibited host boundaries as data, demonstrating all three cases: **permitted** (clean module passes), **prohibited** (breach fails with exact file/line location), and **undecidable** (constructs the static check cannot decide—such as `process.env` reads or dynamic imports—surfaced explicitly for recorded validation, failing if unjudged).
  - Currently, no architecture conformance check has been run, while inspection of `budget.mjs` already reveals an apparent `node:fs` violation and `process.env` coupling.

   - Ask the Requirements owner to clarify **BG-R1 / BG-R2** contract gaps: non-array `items`, malformed/null/missing-`cost` items, non-number `limit`, fractional `limit` acceptance, `-0` handling, and `Number.MAX_SAFE_INTEGER` overflow expectations.
   - Check contractual necessity and known consumer dependencies for `BUDGET_AUDIT_FILE` / `existsSync` (`budget.mjs:1,19-21`) with Architecture/Intent owners before removing or keeping it.

2. **Record independent Judgements (Validation):**
   - **BG-R4:** Obtain a recorded judgment from an independent seat (not the spec/module author, e.g. an operator reviewer) inspecting `budget.mjs` error messages at lines 5, 8, and 14 (including noting omitted context such as failing item index and offending value).

   - **AC-1:** Validate or dismiss the suspected `node:fs` and `process.env` architectural concerns with a recorded judgment (naming reviewer and reasoning), and remediate `budget.mjs` if confirmed as a boundary breach.

3. **Separate and build the three verification loops:**
   - **Architecture conformance (`BG-A1`):** Declare allowed/prohibited host boundaries as data (`node:fs`, `node:fs/promises`, `node:child_process`, etc., plus policy on `process.env`). Run a mechanical check demonstrating **permitted**, **prohibited** (reporting file/line location—which should detect `budget.mjs:1` until fixed), and **undecidable** (surfacing constructs like `process.env` or dynamic imports for validation, failing if unjudged).
   - **Implementation loop (`BG-R1`, `BG-R2`):** Repair/replace `broken.checks.mjs` so it imports `evaluateBudget`, uses self-contained inputs (no missing fixture), and invokes `evaluateBudget(...)` inside `assert.throws(..., RangeError)`. Verify **Behavioural RED** against an inert stub, add all missing `BG-R1` (`total === limit`, `[]`, `0` costs/limits, owner-confirmed edges) and `BG-R2` (negative, non-integer, non-finite `cost` and negative, non-finite `limit`) cases, then run **Targeted Mutation Verification** (e.g. `total > limit` $\to$ `total >= limit`, `limit < 0` $\to$ `limit <= 0`, integer/finite guards removed) and classify every mutant (`killed`, `survived`, `invalid`, `unresolved`).
   - **Capability acceptance:** Add `test/acceptance/` scenarios exercising `evaluateBudget` solely through the public interface (covering promised successes and promised failures), and run `accept` (`kaal-testing/acceptance`) against packed tarballs installed fresh via `install` on each supported host.

4. **Measure Coverage and Ownership:**
   - Run `cover` (`kaal-testing/coverage`) and `report` (`kaal-testing/report`) against delivered files; report non-blank text lines and executed lines side by side (never as a single ratio), and explicitly name any unexecuted delivered file.
