# change/F56 ratchet

The Cases of a Change are hot only during the Change, and the count of RED Cases moves one way per kind of transport. The scope is every Test Case the Change adds or touches, inside its folder and beside the elements, **derived** from the ids the Change names in its own records (no hand-kept list). RED target tests are the Gaps: analyzing the Change means finding them.

1. **PLAN.** The RED count at head stays the same or rises against base. A PLAN that adds a Case testing an id the Change does not name is a finding (`case-not-named`): the Change is adjusted to name the new Gap.
2. **DO.** The RED count stays the same or falls. UNKNOWN may not rise (proposed, for the Owner): lowering RED by breaking a Case is no progress.
3. **ACT.** Allowed only at RED 0 and UNKNOWN 0. `act.md` then closes the Change, the folder is cold (the check says "closed, nothing to run") and ACT unwires nothing. Many PLANs and many DOs may come before one ACT.
4. **UNKNOWN** is a separate count and never a pass.

Testing's runner supplies the counts `{ red, green, unknown }` at base and at head, through a command given to the check as an argument: kaal-change takes no package dependency on it. The PR type (PLAN, DO, ACT) is known to release's envelope, which passes it as `phase`; Guard never reads it and stays Change-agnostic.
