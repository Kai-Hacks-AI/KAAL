# change/C200 ids from a declared block

On 28 November 2026 the coordinator reported that Change, Case and Defect ids keep colliding across capabilities: C166, C167, C175, C176 and T1740 were each picked twice in one morning. Earlier the same happened with T1571, T1581 and T1597, and on 27 November T1580 to T1582 were moved after the clash. The cause is the same each time: a thread picks the next number after the highest one it can see, and what it can see is main and the open pull requests, not the collector branches of the other capabilities. Two threads then see the same highest number and take the same next one. This PLAN removes the cause, not the symptom. It starts no implementation, adds no workflow and no ruleset, and installs nothing.

## Baseline

A Change identity is `<namespace>/C<n>`, so `release/C175` and `controls/C175` are different identities. In practice the numbers are one running sequence across the repository: the folder names `C175-entry-names-its-stations` and `C175-gh-error-loud` exist side by side, and Case ids are repo-wide by agreement. Nothing says who may take which number, so uniqueness depends on every thread seeing every branch. On 28 November the open branches already hold two Changes each for C160 to C165, C175 and C176.

## PLAN

Adds I35, F71, F72, N21 and the Cases T2000 to T2003, parked RED (`.red.mjs`). The draft register `blocks.draft.json` in this folder is the target; the DO delivers it unchanged.

- **F71. A block per capability, declared in a file.** One file on main, `packages/kaal-change/13-source/ids/blocks.json`, holds `blocks`: entries `{ capability, kind, from, to }`, with `kind` as `change` (the `n` of `C<n>`) or `case` (the `n` of `T<n>`). Blocks of a kind never overlap, which is checkable from the file alone. A capability takes new ids only from its own blocks, upward, and never reuses one. Two capabilities can therefore never pick the same number, however many branches exist and whichever of them a thread can see, so no thread scans anything. A capability whose block runs out adds one line to the file, a block above every existing one; that is a small Change of its own and the only write to the file. The ids below the first block (Changes up to C199, Cases up to T1999) are legacy: they stay as they are, are never judged against a block, and the next free number in a block never sits below them.
- **F72. check Id Block, a detective control.** `change/check Id Block` judges, over data it is given and with no file, process, network or Git access: the register, and the ids the Change adds with the capability that owns each (the owner of the path, from `ownership.kaal.json`). `checkIdBlock({ register, owned })` returns PASS, FAIL or UNKNOWN. FAIL findings: `overlap` (two blocks of a kind share a number), `outside` (an id above the legacy ceiling that is not in a block of its owner) and `duplicate` (one number taken twice in the data it is given). A register or an owner it cannot read is UNKNOWN with the fact named, never a pass. Which data it is given, and where it runs, is the consumer's: this PLAN adds no workflow, flag or WIRE, and the control stays detective until the Owner decides otherwise.
- **N21. Files and numbers only.** The register and the control name no branch, pull request, host or date, and nothing scans refs: that is the point of a block. Defect ids are not in the register, because they are already `<capability>/D<n>` and cannot collide across capabilities.

Defaults to leave open: block sizes and the order of the first blocks are the draft's and the CPO's to change before the DO; the exact finding names are the Cases'.

## Why not the other two

- **One register that every PLAN appends to.** Every PLAN writes the same file, so each collector holds its own copy of the next number until a SYNC, and two PLANs append the same line and also conflict in that file. It moves the race to a file and adds a conflict.
- **A check that fails an id that exists on any branch.** It needs the list of all branches, which is Git and Hosting mechanics and not KAAL semantics, and it finds the clash only after both branches exist. It can still be added later as a safety net by Hosting; this PLAN does not need it.
