# change/C15 succession

Kai asked on 26 November 2026 for an edge between Change records: the successor knows its predecessors, and only for hard dependencies. Change already defines the relationship (`capability/Succeeds.md`, change/I2, change/F4, change/F12) and reads it from Nodes (`lib/delivery.mjs`). It does not define how a Change Record states it, which dependencies are worth declaring, or what a reader of records must report. This PLAN does that. Change owns the format; Release uses it, and raises its own PLAN for the detective controls `verify Succession` and `verify Overlap`. It starts no implementation, adds no control and installs nothing.

## Baseline

`Succeeds` is an Edge from a Change Node to the Nodes it succeeds, pinned to their exact bytes, with a finding for an unresolved or stale target and for a cycle. A repository's Change Record (`C<n>.md` in a Change folder) has no field that states those Edges, so no record says what it depends on and no consumer can read it. Nothing says that only a hard dependency is declared, and nothing keeps file overlap out of the statement: Release's own set of paths a collector owns (release CTL33) is where overlap is known, and it must stay there.

## PLAN

Adds I32, F61 to F64, N18 and the Cases T1557 to T1562, parked RED (`.red.mjs`). `fixtures.mjs` is shared by the Cases and is not one. The format, the rules and the interface below are the target; the DO delivers them unchanged.

- **F61. Statement.** A Change Record may hold `succeeds`, a list of entries `{ change, pin, because }`, in its frontmatter. `change` is the predecessor's identity (`<namespace>/C<n>`, change/F2). `pin` is the identity of the predecessor's record bytes as the consumer's own derivation gives it (Core's content address); the reader takes that derivation as an argument and never invents one. `because` is one line saying what fails without the predecessor on main. A Change that succeeds nothing states nothing.
- **F62. Hard dependencies only.** An entry with no `because`, or an empty one, is a finding `not-hard` naming the Change and the predecessor. Whether the reason is true is a reviewer's to judge; the format only requires that someone gave one. A malformed entry (an identity that is not `<namespace>/C<n>`, a pin that is not 64 lowercase hexadecimal characters, a missing field) is `malformed`, and a repeated predecessor is `duplicate`.
- **F63. Validity.** Against the records given: a predecessor that is not present is `unresolved`; one present whose bytes no longer give the pin is `stale`, naming the pinned and the present identity, reported and never repaired, and it is not an Edge; a cycle, and a Change that succeeds itself, are `cycle` naming each Change, sorted (change/F12). The valid Edges are returned with their `because`. These are the same findings as change/F4 and change/F12, read from records instead of Nodes.
- **F64. Only the successor states it; nothing derived is written.** What succeeds a Change is derived from the other records' entries (`successors(identity)`), never stated. A record that holds `successors`, `succeededBy` or `precedes` is `derived-stated`. File overlap is never declared: a record that holds `overlaps`, `conflicts` or `files` is `overlap-stated`; overlap is derived from the paths each collector owns, which is Release's.
- **N18. Pure and host-free.** The reader is `readSuccession(records, { pinOf })` in `lib/succession.mjs`, over `[{ identity, text }]` and the derivation it is handed. It reads no file, no process and no network and names no host. Which records to read, and from where, is the caller's: Release reads files on a branch, another consumer reads another source.

Defaults to leave open: the exact finding names are the Cases', and a consumer may add its own.

## What Release uses

Release's detective controls read the records, call `readSuccession`, and report `verify Succession` (the findings of F62 to F64, plus whether each predecessor is on main) and `verify Overlap` (overlap derived from the collector's own paths, compared with `successors`). They are Release's PLAN. This Change defines no control, check, flag or ruleset.

## Questions

1. **Pin on records or on Nodes.** The pin is the identity Core derives from the record's bytes. Release's controls and a record in a repository must derive it the same way; the CPO or Core confirms which derivation, and the Cases inject it so they do not decide it.
2. **Stale after an amendment.** An amended predecessor leaves every successor stale until it is pinned again. That is the Definition (`Succeeds.md`), accepted for hard dependencies only; a PLAN amendment of a Change that has successors must say so.
3. **Case ids.** T1557 to T1562 and I32, F61 to F64, N18, G18, C15 were checked against `main` and every remote branch on 26 November 2026. Release confirms hand-picked ids.
