# change/C250 one identity claim, claimed before the content

On 28 November 2026 the coordinator reported that Change, Case and Defect ids keep colliding across capabilities: C166, C167, C175, C176 and T1740 were each picked twice in one morning, and C200 was taken by two threads while this PLAN was open. Earlier T1571, T1581 and T1597, and T1580 to T1582, clashed the same way. The cause is always the same: a thread takes the next number after the highest one it can see, it sees main and the open pull requests but not the other capabilities' collector branches, and it finds the clash only when real content already carries the number. Kai observed the same day that if identities are spliced away from the content and travel faster to main, every capability can share one identity concept. This PLAN is that concept. It starts no implementation, adds no workflow, flag, ruleset or WIRE, and installs nothing.

## Baseline

A Change identity is `<namespace>/C<n>`, so `release/C175` and `controls/C175` are different identities. In practice the numbers are one running sequence across the repository, and Case ids are repo-wide by agreement. Nothing says who may take a number, and a number is claimed only by using it in content, so a clash costs a renumbering of finished work. Backlog's fast lane (backlog/C2) is the existing design for a small, whitelisted change that reaches main directly. Its judge exists and is merged on the backlog collector; no branch kind, ruleset or workflow is built, and the Owner has not given a go for any of them (backlog thread, 28 November).

## PLAN

Adds I35, F71, F72, F73, N21 and the Cases T2000 to T2003, parked RED (`.red.mjs`). The draft `claims.draft.json` in this folder lists the first claims; the DO delivers each as its own file, unchanged.

- **F71. An identity claim is a fact of its own.** One file per claim, `13-source/ids/claims/<kind>-<from>-<capability>.json`, holds `{ capability, kind, from, to }`. `kind` is `change` (the `n` of `C<n>`) or `case` (the `n` of `T<n>`). A claim is a range; a single number is a range of one. A capability takes new ids only inside its own claims, upward, never twice, and a claim of a kind never overlaps another claim of that kind. A file per claim means two claims never edit the same file. An id below the lowest claim of its kind is legacy: it stays, is not judged, and the next free number never sits below it. Defect ids are not claimed: they are `<capability>/D<n>` already and cannot collide.
- **F72. check Id Claim, a detective control.** `change/check Id Claim` judges, over data it is given and with no file, process, network or Git access: the claims, and the ids a Change adds with the capability that owns each (the owner of the path, from `ownership.kaal.json`). `checkIdClaim({ claims, owned })` returns PASS, FAIL or UNKNOWN. FAIL findings: `overlap` (two claims of a kind share a number), `outside` (an id at or above the lowest claim of its kind that is not in a claim of its owner) and `duplicate` (one number taken twice in the data). Claims or an owner it cannot read are UNKNOWN with the fact named, never a pass. It names no branch, pull request or host, and nothing scans refs.
- **F73. How it fits with a fast lane, and with blocks.** The claim route has two stages and one shape. Today, with no fast lane: a capability claims a large range, a block of 100 Change numbers and 200 Case numbers, as an ordinary small Change, once and rarely; inside its block it takes numbers freely, so no thread scans anything and nothing can clash. When Backlog's fast lane is activated: a capability may claim a small range, even one number, as a claim-only change that lands on main directly, so a claim is on main in minutes, before any content exists. The lane judges the claim files as a second table entry (root, name pattern, add and modify only, uniqueness key): the key is the file name, and the overlap rule of F72 is judged on the full resulting tree, so a second claim of the same number fails in the merge queue and its author takes the next number before any content depends on it. A block is a claim of a range; the two are the same concept and the same files. This PLAN decides the claim and its judge; the lane's table, branch kind and activation are Backlog's and Release's own Changes and need the Owner's go, and are not started here.

Defaults to leave open: block sizes and the order of the first claims are the draft's and the CPO's to change before the DO; the exact finding names are the Cases'.

## What was weighed

- **One register file every PLAN appends to.** Every PLAN writes the same file, each collector holds its own copy of the next number until a SYNC, and two appends of the same line conflict. A file per claim removes the conflict; blocks remove the race.
- **A check over all branches.** It needs the list of branches, which is Git and Hosting mechanics, and it finds the clash only after two branches carry the number.
- **A fast lane alone.** It narrows the race to the merge queue but does not exist yet; blocks work today and make the lane an addition, not a prerequisite.
