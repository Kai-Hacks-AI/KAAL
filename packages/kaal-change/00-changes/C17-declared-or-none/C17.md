# change/C17 declared or none

Kai asked on 27 November 2026 that a PLAN be able to declare the Changes it depends on, in a form the queue can read when it orders promotions. The form exists since change/C15 and change/C16: a record states `succeeds` as entries `{ change, pin, because }` with `change` as `<namespace>/C<n>`, so by capability and id, and `change/check Predecessor` judges them. What the queue still cannot tell is a Change that has no hard predecessor from a Change whose author never said: an absent `succeeds` reads as "nothing stated". That was the gap found while ordering the 2 DEC chain, where whether release C158 and C159 needed controls C158 and C159 had to be answered from memory. This PLAN closes that gap and nothing else. It starts no implementation, adds no control and no workflow, and installs nothing.

## Baseline

`readSuccession` treats a record without `succeeds` and a record with `succeeds: []` alike: no finding. `checkPredecessor` passes a carried Change that states nothing and says only that this is no declared prerequisite, not a claim that none exists. So a promotion cannot require that a Change has answered the question.

## PLAN

Adds I34, F69, F70, N20 and the Cases T1700 to T1702, parked RED (`.red.mjs`). The form of a statement is change/C15's and is not changed. The rules and the interface below are the target; the DO delivers them unchanged.

- **F69. Declared or none.** A Change that has answered the question has the key `succeeds`: entries when it has hard predecessors, `succeeds: []` when it has none. `readSuccession(records, { pinOf, require })` takes `require`, a list of identities that must have answered. A required record without the key is the finding `{ kind: 'undeclared', change }`; with entries or an explicit empty list it is none. A record not in `require` is read as before, so a repository that never passes `require` sees no change. Which Changes are required is the caller's: the reader names no date, host or rule.
- **F70. check Predecessor can require it.** `checkPredecessor({ ..., require })` passes `require` on to the reader for the identities it is given and reports `undeclared` as a FAIL finding for a carried Change, one per Change. Without `require` it behaves exactly as before. With it, a carried Change that states `succeeds: []` passes and its note says that it declared none, which is a statement and not the absence of one. `require` that is not a list of identity strings is UNKNOWN, never a pass.
- **N20. The question is Change's and the answer is in the record.** The statement lives in the Change Record file, not in a pull request body, a title or a template chapter: PLAN bodies keep their four chapters, and no host word enters the reader. Whether a promotion requires the answer, for which Changes, and from when, is Release's to decide when it runs the control; this PLAN defines only that the answer can be required and what it looks like.

Defaults to leave open: the exact finding name is the Case's, and a consumer may add its own.

## What uses it

Release's small PLAN that runs the two controls at PROMOTION and in the Dispatcher passes the carried Changes as `require` once it chooses to, and reads `successors` and the edges from the records of the open collectors to order promotions. That PLAN is Release's and waits for change/C15 and change/C16 on main. This Change declares its own dependencies in its record above, as the form asks: it succeeds change/C15 and change/C16.
