# hosting/C114 change

## From

Each KAAL App is a hand-made GitHub object. Its manifest is a JSON file written in GitHub's words inside the capability that uses it, its token is minted by a third-party action in a workflow, its API calls are plain `fetch` in the capability's own scripts, and nothing says what its logo must be. The Inspector and the Approver have none of this yet, so Review would write each in GitHub's words too.

## To

1. **A declaration, written by the capability that owns the App, with no GitHub word.** One file per App at `packages/<capability>/13-source/github-apps/<app>.json`: `{ app, name, owner, purpose, appId, abilities: [...], logo? }`. `abilities` is a closed vocabulary Hosting defines: `read-contents`, `read-pull-requests`, `raise-pull-requests`, `approve-pull-requests`, `read-checks`, `post-checks`. Hosting maps each to the GitHub permission and level (for example `raise-pull-requests` and `approve-pull-requests` are both `pull_requests: write`, which GitHub does not tell apart and Hosting does). No App may hold both `raise-pull-requests` and `approve-pull-requests`: an App never decides on what it raised. Which App may hold `approve-pull-requests` at all is Review's rule, checked by Review. `appId` is the App's numeric GitHub id, recorded by the Owner once the App exists, in a reviewed change on the default branch: it is the Owner-established binding of this logical App to one GitHub identity, so two Apps with identical abilities (the Dispatcher and the Approver can have) are still told apart, and no two declarations may share an `appId`. Every App lists `read-contents`, since its declaration is read through it (item 3). An ability outside the list is refused, and no ability can write contents, workflows, administration or secrets: the three Apps never push. The capability states what its App needs, never how GitHub says it. Engineering confirms the folder in C37.
2. **Manifest.** `renderAppManifest(declaration)` returns the manifest GitHub's App-from-manifest flow reads, as stable JSON: `name`, the fixed `url`, `public: false`, an inactive hook with the inert address the existing manifest already uses, no events, and `default_permissions` mapped from the abilities (and always `metadata: read`). Deterministic, LF, a field outside the declaration format refused.
3. **Token and grant, established from trusted authority.** The caller names only the App, the App id, the key, the repository and the abilities it wants. It never supplies the declaration, the permissions, a token or an ability list that is believed. `mintToken({ app, appId, privateKey, repo, abilities }, { fetch?, api?, now? })` returns a **grant**:
   1. It signs an RS256 App JWT with `node:crypto` (`iss` the App id, `iat` a minute back, `exp` at most ten minutes ahead) and finds the installation (`GET /repos/{repo}/installation`).
   2. The installation's granted permissions must equal the permissions of the declaration, no more and no less (`APP_INSTALLATION_MISMATCH`). This is the adoption check: an App installed wider than it declares, or narrower, is refused, so a wide installation cannot slip in.
   3. It creates a bootstrap token narrowed to `contents: read` on that repository, and with it reads the declaration **itself**: the repository's default branch (asked of GitHub, not the caller), its commit, its tree, and the one file `packages/*/13-source/github-apps/<app>.json`. None or two such files, a truncated tree, a file that is not a valid declaration or whose `app` differs from its file name, is refused (`APP_DECLARATION_MISSING`, `APP_DECLARATION_AMBIGUOUS`, `INVALID_APP_DECLARATION`). A change to a declaration takes effect only once it is on the default branch.
   4. **Identity.** What GitHub says the key belongs to (`GET /app` with the JWT) must have an `id` equal to the declaration's `appId` and to the `appId` the caller passed, and the installation's `app_id` must equal it (`APP_IDENTITY_MISMATCH`). The caller's `app` name only selects which declaration to read; it is never the identity. Swapping credentials (another App's id and key with this App's name), or this App's id and key with another's name, refuses before the narrowed token is requested.
   5. The requested abilities must be within that declaration (`APP_TOKEN_REFUSED`), then it creates the installation token narrowed to exactly them and to that repository.
   6. It **verifies what GitHub returned**: `permissions` must equal the requested abilities' permissions exactly (an empty, extra, higher or unknown permission is `APP_GRANT_MISMATCH`), `expires_at` must be a time after `now` and within one hour of it, and the repository selection must be the one repository.
   7. The grant is a frozen value Hosting created, `{ app, repo, expiresAt }`, whose token, abilities, `appId`, installed repository and the **origin it was minted against** Hosting holds privately (`grantAbilities(grant)` and `grantIdentity(grant)` (`{ appId, login }`, the App's bot login from `GET /app`) read them; a copy, a clone, a plain object or a bare token carries none and is refused with `GRANT_UNTRUSTED`). The abilities of a grant are what GitHub really granted, which Hosting derived from the declaration, never what a caller says.
   Every Hosting call that uses a token (the reads below, C113's raise, and the approve and post operations of Review when they are built) takes the grant as its only authority, and refuses before any call: a non-grant (`GRANT_UNTRUSTED`), an expired one (`GRANT_EXPIRED`), one used for another repository than it was minted for (`GRANT_REPO_MISMATCH`), one used with another origin or transport than it was minted against (`GRANT_TRANSPORT_MISMATCH`: a token is sent only where it was minted, and production's origin is GitHub's own, so a substituted `api` or `fetch` receives nothing), one without the ability the call needs (`ABILITY_REFUSED`). A `token`, `abilities` or `declaration` option is not an option and is refused. A 404 for the installation is `APP_NOT_INSTALLED` and a 401 is `APP_KEY_REJECTED`, so the two failures of the first Dispatcher raise are told apart. The private key, the JWT and the token never appear in an error, a log line or a path.
   **Approval identity, shown before adoption.** Hosting reads reviews as facts (`listReviews(repo, number, { grant })`: `{ state, commit, by: { login, type } }`) and gives the identity of a verified grant (`grantIdentity(grant)`: the App's id and bot login, from GitHub, bound to the Owner's declaration). **Hosting judges nothing about approval**: which review counts, on which revision, by whom, is Review's judgement, made on these facts, and Review gives the operational proof of its gate and of trusted execution before the Approver is adopted (its WIRE is not asked for before then). Hosting does not write the ruleset or the gate.
   **Adapter policy and GitHub's permission.** GitHub has one `pull_requests: write` for raising and approving, so GitHub cannot keep the Dispatcher from approving; a token used outside Hosting could. Hosting keeps the two apart by (a) separate Apps (never both abilities), (b) the installation check above, (c) every Hosting operation gating on the grant. What remains outside Hosting is a workflow that mints or uses a token without Hosting. That is closed where the approval is counted, not here: only the Approver's identity counts as an approval (Review's rule, in its ruleset), so a Dispatcher token that approved would not count. Release moves token minting into Hosting in its own Change.
4. **Reads for the Dispatcher.** The reads the Dispatcher makes move behind Hosting and close the read half of hosting/D11: `listBranches(repo, prefix, { grant })`, `compareRevisions(repo, base, head)`, `listPullRequests(repo, { state, base?, head? })` and `readRef(repo, ref)`. Each is GET only, pages until a short page, returns Hosting's own fact shape (never GitHub's JSON), and a failure is a named error. Raising stays hosting/C113's `raisePullRequest`: the Dispatcher raises through it, and the policy of the type, read at the base revision, decides what it may raise.
5. **Logo slot.** A declaration may name `logo`, a file path under the capability's package. `checkLogo(bytes)` accepts a PNG that is square and at least 200 by 200 pixels (GitHub's own recommendation; the DO restates the limit from GitHub's documentation at that day) and names what is wrong otherwise. Hosting holds no logo and uploads none: an App's logo is set by the owner in GitHub's settings, so the slot only makes the asset checkable.
6. **No App, no secret, no install here.** Hosting never creates or installs an App, reads a key from disk, or stores a token. Creating each App and keeping its key stay Kai's.

## Because

One adapter for everything GitHub in the Apps' life, so Release and Review write the judgement and not a line of GitHub, a second host would add its own adapter without touching a declaration, and the first Dispatcher failure (a 404 nobody could read) cannot recur silently.

## Which part comes from which owner

| Part | Owner | Source | Hosting's part |
| --- | --- | --- | --- |
| What the Dispatcher needs and why | Release | `packages/kaal-release/13-source/github-apps/dispatcher.json` (to be written by Release) | maps abilities to permissions, renders the manifest |
| What the Inspector and the Approver need and why | Review | `packages/kaal-review/13-source/github-apps/{inspector,approver}.json` (to be written by Review) | the same |

| Which abilities exist | Hosting | the closed vocabulary here | defines, refuses the rest |
| Pull request types and their rules | Engineering, Change, Release | hosting/C113's policy files | read at the base revision |

Release's existing `app-manifest.json` is `{ metadata: read, pull_requests: write }`. The Dispatcher also reads `compare`, `git/ref` and `git/matching-refs`, and C113's raise reads policy files at the base revision, which GitHub serves only with `contents: read`. Release's declaration therefore lists `read-contents` beside `raise-pull-requests`; that is a Release decision in its own Change, and Hosting refuses a token request beyond the declaration read from the default branch.

## Amendment (four defects in the drafts and one in the fixtures, found at the DO)

The drafts were run, for the first time as Cases, against the adapter, and four of them cannot pass as written, none because of what they claim: T318's example Apps held neither `read-contents` (which item 1 requires of every App) nor a way to be read, so they now hold it, with its permission in the expected output; T320 decoded the JWT from a header that still began `Bearer `; T321's two declarations of one App had no `appId`, so they were invalid before they were ambiguous; T330's first assertion minted on a world with no route for the ref, so the read it expected to succeed returned nothing. The fixtures' authentication gate did not accept the grant's own token, so every read through a grant was refused before it began. No claim of any Case changes. The DO delivers the Cases as amended here.

## Amendment (the Approver's facts, asked by Review in PLAN #2702 and agreed with it)

The Approver judges a pull request only on facts that Hosting made, and only on a read it made with its own grant. Three additions, with three executable drafts, `T336` to `T338`, in `facts.red.mjs` (ids provisional: F106 and F107, A47, T336 to T338, checked against `main` and every remote branch; C115 holds I23, F104, F105, A46 and T332 to T335). Nothing else in this PLAN changes, and T318 to T326 and T329 to T331 are as delivered or drafted.

1. **Attribution is never a field.** Every fact that a Hosting read returns (the five reads and the new one) is a frozen value that Hosting registers in a table of its own, held privately like a grant's token, with the App whose grant read it and the repository. `factOrigin(fact)` returns `{ app, repo }` for a fact Hosting made and `null` for anything else: a copy, a clone, a JSON round trip, an object with the same shape, a value that names an origin of its own. A consumer treats `null` as UNKNOWN, never as a result. The table lives in one process. A fact that crosses a process boundary carries no attribution, whatever form it takes, so a judge in another process re-reads the facts through Hosting with its own grant instead of receiving them (T336).
2. **`readPullRequestFacts({ repo, number, check }, { grant, fetch?, api?, now? })`** needs `read-contents`, `read-pull-requests` and `read-checks`, sends GET requests only and returns one fact: `{ number, head: { ref, sha, parents }, base: { ref, sha }, main, author: { login, type }, checks: [{ name, revision, status, conclusion, signer }] }`. `main` is the default branch's revision, asked of GitHub. `parents` are the head commit's parents, and a pure merge is Review's judgement from them, not Hosting's. `checks` holds **every** check run called `check` at the head revision, with `filter=all` so reruns are not dropped, paged to a short page, newest first (by GitHub's `started_at`, then `id`), each with GitHub's own `status` and `conclusion` (`null` while it is not complete) and `signer`, the App that created it. A run of another revision is never listed. Hosting selects nothing and collapses nothing: an older success cannot hide a newer failure or a pending run, because all of them are there and Review judges them. An empty list means there is no such run. No body, message or verdict is returned (T337).
3. **Refusals before any call.** A missing ability (each of the three, T338), no grant or a forged one, a `token`, `facts` or `origin` handed in, a missing check name, a number that is not a pull request number, another repository than the grant's. The caller supplies no fact, no origin and no authority.

Errors and options are those of the other reads. The requirements F106 (facts carry Hosting's attribution, held privately, `factOrigin`) and F107 (`readPullRequestFacts`) and the architecture element A47 (`facts.ts` holds the table and `app-reads.ts` registers each fact it returns) state the three. The second DO also delivers T326 and amends T310 to T317 and T335 only in how they obtain authority (the grant), with no change to what they expect.

## The interface the Cases fix

All from `@kaihacksai/kaal-hosting`; the modules are `scripts/github/app-manifest`, `app-token`, `app-reads` and `app-logo`.

- `renderAppManifest(declaration): string`; `mintToken({ app, appId, privateKey, repo, abilities }, { fetch?, api?, now? }): Promise<Grant>` with `Grant = Readonly<{ app, repo, expiresAt }>` and `grantAbilities(grant): string[]`; `checkLogo(bytes): { ok: true, width, height } | { ok: false, problem: "empty" | "not-png" | "not-square" | "too-small", width?, height? }`.
- `listReviews(repo, number, { grant, fetch?, api?, now? }): Promise<{ state, commit, by: { login, type } }[]>` (needs `read-pull-requests`); `grantIdentity(grant): { appId, login }`.
- `listBranches(repo, prefix, opts): Promise<string[]>`; `compareRevisions(repo, base, head, opts): Promise<{ status, aheadBy, behindBy, files, truncated }>`; `listPullRequests(repo, { state, base?, head? }, opts): Promise<{ number, title, state, merged, head: { ref, sha }, base: { ref }, body }[]>`; `readRef(repo, ref, opts): Promise<string | null>`; `opts` is `{ grant, fetch?, api?, now? }`; `read-contents` is needed by `listBranches`, `compareRevisions` and `readRef`, `read-pull-requests` by `listPullRequests` and `listReviews`. `listReviews(repo, number, opts): Promise<{ state, commit, by: { login, type } }[]>` and `grantIdentity(grant): { appId, login }`.
- Errors carry a `code`: `INVALID_APP_DECLARATION`, `APP_IDENTITY_MISMATCH`, `GRANT_REPO_MISMATCH`, `GRANT_TRANSPORT_MISMATCH`, `APP_DECLARATION_MISSING`, `APP_DECLARATION_AMBIGUOUS`, `APP_TOKEN_REFUSED`, `APP_INSTALLATION_MISMATCH`, `APP_GRANT_MISMATCH`, `APP_NOT_INSTALLED`, `APP_KEY_REJECTED`, `APP_TOKEN_FAILED`, `GRANT_UNTRUSTED`, `GRANT_EXPIRED`, `ABILITY_REFUSED`, `INVALID_READ`, `READ_FAILED`.
- A Case injects the transport (`fetch`, `api`, `now`), never data. The key a Case uses is generated inside the Case.

## Questions, settled by the reading below unless said otherwise

- **Owners write the declarations, in their own Changes.** Release writes the Dispatcher's, Review writes the Inspector's and the Approver's. This Change plans the format and the adapter and writes none of them.
- **`read-contents` for the Dispatcher.** Settled above: the Dispatcher needs it for the reads and for C113's raise; Release lists it.
- **The Approver.** Settled with Review (26 November): approving is its own ability, `approve-pull-requests`; no App holding `raise-pull-requests` may also hold it; Review writes the Inspector's declaration (`post-checks`, `read-contents`, `read-pull-requests`, provisionally) and the Approver's in its own Changes, and checks that only the Approver holds approving. Hosting mints a token only for what the declaration lists and gates each call by ability.
- **Gating C113's raise.** Settled by the CPO's review: the same rule everywhere. C114's DO changes `raisePullRequest` (C113) to take `grant` in place of `token`, requiring `raise-pull-requests` and `read-contents`; the CLI mints its grant from `KAAL_APP_ID` and `KAAL_APP_KEY` (read in the CLI, never in the adapter) instead of `GITHUB_TOKEN`. C113's Cases T310 to T317 change their transport set-up to this (accept list below) and T326 adds the refusals. C113's DO (open) is not touched by this PLAN.
- **Token minting in workflows.** `actions/create-github-app-token` stays in `.github/workflows` until Release moves it in its own Change; Hosting only offers the call.
