# Portability Across Capabilities: Requirements

Each Requirement names, in brackets, the Intents it serves. They extend hosting/F27–hosting/F34 (`hosting/C13`) and change none of them.

## Functional

- **hosting/F36** [hosting/I10]: **The operating-system boundary is declared by Hosting.** `kaal-hosting/conformance` exports `OS_BOUNDARY`, a frozen list of the package names that are the operating-system boundary, exactly `["@kaihacksai/kaal-hosting"]`. `osBoundary(name)` is `true` for a listed name and `false` for every other string, and throws a `TypeError` for anything that is not a string. A package's own field, such as `osBoundary: true` in its manifest, never makes it the boundary. Engineering establishes Testing's `osBoundary` (testing/F67) from this declaration.
- **hosting/F37** [hosting/I10]: **Host facts.** A host fact is a named capability of a host that a case may need, named without any platform: `kaal-hosting/special-entries`, a FIFO and a Unix-domain socket can be placed in a directory tree. `facts()`, from `kaal-hosting/fixtures`, establishes each fact on the running host by trying it in a fresh temporary directory, never by reading the platform's name, and returns `{ [fact]: { holds, reason, evidence } }`: `holds` a boolean, a nonempty `reason`, and an `https` link to the evidence. Hosting adds a fact only through a PLAN Change.
- **hosting/F38** [hosting/I10]: **The special-entry fixture.** `specialEntries(dir)`, from `kaal-hosting/fixtures`, where `kaal-hosting/special-entries` holds, makes a FIFO at `dir/fifo` and a listening Unix-domain socket at `dir/socket`, and returns `{ holds: true, fifo, socket, close }`. `close()` stops the listener and leaves the entries for the case to inspect. Where the fact does not hold, it makes nothing and returns `{ holds: false, fact, reason, evidence }`, the same reason and evidence as `facts()`. It never throws because a host lacks the fact. Where the fact holds but the fixture cannot be made in `dir` (for example, `dir` is missing or is a file), that is a setup failure: it throws a `SetupFailure` with `outcome: "unknown"`, the fact, the directory and the reason, and makes nothing. It never returns `holds: false` for it, so a setup failure can never stand for a host that lacks the fact or justify a case being not applicable; a case using it fails, never skips or passes (the Owner's review on #679, comment 6541495990). It is the only place a KAAL test makes a FIFO or a socket.
- **hosting/F39** [hosting/I10]: **Applicability rules.** For every package but the boundary:
  - A case may be not applicable by host fact: `{ host: [fact…], reason, evidence }`, where each fact is one of hosting/F37's, the reason is nonempty and the evidence is an `https` link. It is not applicable on a run only where `facts()` established one of its facts not holding there. The case stays registered on every host, with the same title and body, and is never reported as passed.
  - A case is never scoped by `platforms`, and a manifest never limits the package by `os` or `cpu`. Either is an architectural violation (testing/F67), never an exemption.
  - Applicability by optional complement (`requires`, `absent`) is Testing's and the composition rule's, not Hosting's. The audit leaves it alone.
- **hosting/F40** [hosting/I10]: **The portability audit.** `portability({ name, root, builtins, test, applicability })`, from `kaal-hosting/boundary`, runs `boundary` (hosting/F33) on the same options and extends its result. `applicability` is the capability's declarations, keyed by case name, as the runner read them from the capability's manifest or Test Plan.
  - `osBoundary` is `osBoundary(name)` of the `name` in `root`'s `package.json`, `false` where there is none.
  - `applicability` lists one finding per problem, each with the `case` (or `package.json`), its `rule` and the problem stated: `platform-applicability`, a declaration with nonempty `platforms`, or a manifest `os` or `cpu`, outside the boundary; and, for a declaration with `host`, `unknown-host-fact` (a fact that is not hosting/F37's), `unreasoned` (no reason), `unevidenced` (no `https` evidence), and `stale` (no test source registers a case of that title, or every fact it names holds on every host in hosting/F41's guide).
  - Two deterministic cases follow hosting/F33's three: `applicability is not scoped by platform`, which fails on any `platform-applicability` and is `not applicable` where `osBoundary` is true; and `host exceptions are well-formed`, which fails on any other applicability finding. Both are `not run` when the inspection could not complete. `result` follows hosting/F33 over all five cases.
  - `reviews` adds one request per host declaration, well-formed or not: `id` `kaal-hosting/host-applicability@<case>`, `rule` `kaal-hosting/host-applicability`, `owner` `Hosting`, the `case`, the `declaration`, and the question whether the case is genuinely inapplicable where the fact does not hold, with its assertions intact where it does. A `review` link inside the declaration is evidence only, and the request stays open in the result: the judgment and its record are Review's (hosting/A14).
  - `challenged` lists, sorted and once each, the case names Testing must not count as evidence (testing/F58, `challenged`, on #668): each declared case with an applicability finding, and the title of each test that a `registration` or `dilution` finding decides or sits in, where that title is a string literal. A `setup` finding challenges nothing.
  - hosting/F33's other members, `summary` included, are unchanged.
  - A conditional expression that picks between a test registration function and anything else, such as `(WINDOWS ? () => {} : it)(…)`, is "a test registered inside a branch" of hosting/F29, so `registration`.

  `portabilitySuite(options)` registers the five cases and `judgment requested` as `boundarySuite` does (hosting/F31). The command takes `--applicability <file>`, a JSON file of the declarations; with it, it runs `portability` and prints the result on the same `kaal-hosting-boundary` line with the same exit codes, and without it, it is hosting/F31's command unchanged.
- **hosting/F41** [hosting/I10]: **The per-host review guide.** Hosting ships `skills/kaal-hosting-boundary/HOSTS.md`, pointed to from the Skill. A table between `<!-- kaal-hosting:hosts -->` markers gives, for each fact and each of `linux`, `darwin` and `win32`, whether it holds (`yes` or `no`) and an `https` link to the evidence. On each host, `facts()` agrees with that host's row, so every Hosting lane checks the guide. The guide then states the rules of hosting/F39, explains each applicability finding and the host-applicability request, says what a reviewer checks for each fact on each host, and escalates through PREACH when an agent's authority is not enough.

## Nonfunctional

- **hosting/N6** [hosting/I10]: The audit is tested with positive and negative fixtures. Guard's negative sources from `engineering/guard/acceptance/fixtures/platforms.json` (#577) are among them: a registration off one platform, a skip and a todo inside a case, an undeclared skip option and an unlisted platform reference. Each is found, and each case it decides is challenged by name. A portable guard/T114 is not. Each applicability rule has a declaration that must be found and a similar one that must not.

## Limits

- The audit reads the declarations the runner gives it and the sources under `root`. A declaration kept elsewhere is not audited; Engineering's runner is responsible for passing the capability's declarations.
- Whether a host fact holds is established on the hosts KAAL runs (Linux, macOS, Windows). Another host gets its own row through a PLAN Change.
- Hosting defines the facts, the rules and the questions. Review decides each judgment, Testing decides how a not applicable case is counted, and each capability corrects its own cases.
