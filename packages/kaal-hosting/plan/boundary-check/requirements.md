# Boundary Check Per Package: Requirements

Each Requirement names, in brackets, the Intents it serves. They extend hosting/F27 to hosting/F34 (`plan/boundary`); where they differ, these win from `hosting/C102`.

## Functional

- **hosting/F64** [hosting/I15]: **Any target.** `kaal-hosting-boundary --target <path>` takes a file or a folder. A folder is read recursively through Hosting's `read`, as today. A file is read alone and is judged in the scope its path implies (hosting/F27). `--target` may be repeated. `--name` is optional and defaults to the base name of the first target. `--root <dir>` stays as a synonym for a folder `--target` in 0.0.x. The result carries `target`, the list of targets as given. A target that cannot be read makes the result `unknown`, never `verified`.
- **hosting/F65** [hosting/I15]: **Findings only.** With `--target`, the command is a scan. It prints one result line, `kaal-hosting-boundary {…}`, with `findings` and no `failures` and no `result: failed`. It exits 0 when the scan completed, including when the list is empty or not, and 2 when nothing could be read. It never exits 1 for a finding. A report with no finding means none was found within the stated coverage, never that the target complies (hosting/F32). The deterministic Test Cases and exit 1 and 3 of hosting/F31 and F33 remain for `boundary()` and `boundarySuite()`.
- **hosting/F66** [hosting/I15]: **One finding per line.** There is one finding for each source line that holds platform logic. When a line hits several rules or kinds, the finding lists all of them in `rules` and `kinds`. A later line that only uses an identifier bound to a platform query or literal is not a new finding. It is a reference: it is listed under the finding that binds the identifier, in `references`, with its own place, and is counted apart as `references`. The binding is found from the declaration, not from a repeated text match. The order is by file, then line, and the same input gives the same result.
- **hosting/F67** [hosting/I15]: **What counts.** Any platform logic outside Hosting is a finding, in production code and in test code alike, whatever `kind`. `kind` classifies and never excuses. An acknowledgement (hosting/F30) stays evidence and never removes a finding. Hosting's own sources and tests are not a target of the check: they are where platform logic belongs, and are declared not applicable (hosting/F71). Over-reporting is accepted; hiding a finding is not.
- **hosting/F68** [hosting/I15]: **A finding is a question.** Each finding has a stable `id`, `<file>:<line>` relative to the target root and prefixed `kaal-hosting/`, so one id names one line. It carries `file`, `line`, `column` of the first hit, `scope`, `rules`, `kinds`, the constructs as written, and a `question`: whether this logic can move to Hosting or be removed, or is legitimate, and what evidence says so. The finding has no decision field. The result carries per-package counts of findings and references by rule and kind, so a decider can group similar findings.
- **hosting/F69** [hosting/I15]: **Decisions stay outside.** Hosting emits the finding list and does not store, read or judge decisions. A package records its decisions in its own Boundary Check Test Plan (hosting/F71), keyed by the finding `id`, or by a named pattern that lists every id it covers. Whether a decision is right stays with the CTO and CPO.
- **hosting/F70** [hosting/I15]: **One skill.** `skills/kaal-hosting-boundary/` is removed, with `SKILL.md`, `HOSTS.md` and every mention of it (the `kaal-hosting` skill, `references/operations.md`, the README, `files`, tests, plans). Hosting ships one skill, `kaal-hosting`. Its Boundary Check section says how to run the command, how to read the list (rules, kinds, references, the question), that the list is evidence and not a verdict, and that deciding is the owner's. The host facts that `HOSTS.md` held move into the `kaal-hosting` skill's references, scoped to `@kaihacksai/kaal-hosting/…` specifiers (hosting/F15).
- **hosting/F71** [hosting/I15]: **Two Test Plans.** Hosting declares two Test Plans in the shape agreed with Packaging and Testing. The Package Check is Hosting's own `verify` Cases. The Boundary Check is declared **not applicable** for Hosting, with the reason that Hosting is the operating-system boundary (hosting/C13, hosting/I10), and with no silent omission. The shape for every other package (a Boundary Check that names its targets, its finding list and its recorded decisions) is Packaging's and Testing's to state; Hosting supplies the scan and the id format.

## Non-functional

- **hosting/N9** [hosting/I15]: The scan takes no new runtime dependency and reads no TypeScript parser. It is deterministic, never executes the target, and never loads `node:test` from the command.
