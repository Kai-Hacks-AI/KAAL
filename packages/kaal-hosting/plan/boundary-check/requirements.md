# Boundary Check Per Package: Requirements

Each Requirement names, in brackets, the Intents it serves. They extend hosting/F27 to hosting/F34 (`plan/boundary`); where they differ, these win from `hosting/C102`.

## Functional

- **hosting/F64** [hosting/I15]: **Any target.** `kaal-hosting-boundary --target <path>` takes a file or a folder. A folder is read recursively through Hosting's `read`, as today. A file is read alone and is judged in the scope its path implies (hosting/F27). `--target` may be repeated. `--name` is optional and defaults to the base name of the first target. `--root <dir>` keeps its gating meaning (hosting/F31, `mode: "gate"`) and is not a synonym; `--target` is the scan. The result carries `target`, the list of targets as given. A target that cannot be read makes the result `unknown`, never `verified`.
- **hosting/F65** [hosting/I15]: **Findings only.** With `--target`, the command is a scan. It prints one result line, `kaal-hosting-boundary {…}`, with `mode: "scan"` (the gating run of hosting/F31 prints `mode: "gate"`, so a reader knows which exit semantics apply), `findings` and no `failures` and no `result: failed`. It exits 0 when the scan completed, including when the list is empty or not, and 2 when nothing could be read. It never exits 1 for a finding. A report with no finding means none was found within the stated coverage, never that the target complies (hosting/F32), and exit 0 with an empty list is not a pass: the result carries its coverage (hosting/F68) so a reader can tell complete from partial. The deterministic Test Cases and exit 1 and 3 of hosting/F31 and F33 remain for `boundary()` and `boundarySuite()`.
- **hosting/F66** [hosting/I15]: **One finding per line.** There is one finding for each source line that holds platform logic. When a line hits several rules or classes, the finding lists all of them in `rules` and `classes`. A later line that only uses an identifier bound to a platform query or literal is not a new finding. It is a reference, never carries a decision of its own, and follows the decision of its binding's finding. It is listed under the finding that binds the identifier, in `references`, with its own place, and is counted apart as `references`. The binding is found from the declaration, not from a repeated text match. The order is by file, then line, and the same input gives the same result.
- **hosting/F67** [hosting/I15]: **What counts.** Any platform logic outside Hosting is a finding, in production code and in test code alike, whatever `kind`. `kind` classifies and never excuses. An acknowledgement (hosting/F30) stays evidence and never removes a finding. Hosting's own sources and tests are not a target of the check: they are where platform logic belongs, and are declared not applicable (hosting/F71). Over-reporting is accepted; hiding a finding is not. In particular a quoted reference counts: a string literal that reads `"process.platform"`, in production code or in test code, is a finding, though it is not executable. This is deliberate broad detection (the CPO/Owner decision on finding 3b, 4 Nov, #1030), not a scanner bug and not an automatic Defect; the CTO and the CPO judge it under Gate B like any finding. A finding is never suppressed because it is non-executable.
- **hosting/F68** [hosting/I15]: **A finding is a question.** A scan finding has no Testing outcome. Its `classes` are Hosting's own classification of hosting/F29 (coupling, registration, dilution, setup), so they are not Testing's finding kinds; which Testing kind a scan finding is, is Testing's to say. Each finding has a stable `id`, `kaal-hosting/<file>:<line>`, where `<file>` is relative to one base for the whole scan: the current directory of the run, or `--base <dir>` when given, written with `/`. Every target must lie under the base, and a target outside it is refused. So two targets with files of the same name (`src/index.ts` and `test/index.ts`) give distinct ids, and a file reached by two overlapping targets is read once. One id names one line. It carries `file`, `line`, `column` of the first hit, `scope`, `rules`, `classes`, the constructs as written, a `digest`, and a `question`: whether this logic can move to Hosting or be removed, or is legitimate, and what evidence says so. The finding has no decision field. `digest` is Hosting's own `digest` (SHA-256, lowercase hex, hosting/F63) of the line's text as UTF-8, so an edit above the line moves its `id` but never its `digest`, and an edit to the line changes the `digest`. The result carries `coverage`: the files read, the files not readable with the reason, and the rules applied, so a reader can tell a complete scan from a partial one. It also carries counts of findings and references by rule and class, so a decider can group similar findings.
- **hosting/F69** [hosting/I15]: **Decisions stay outside.** Hosting emits the finding list and does not store, read or judge decisions. A package records its decisions in its own Boundary Check Test Plan (hosting/F71), keyed by the finding `id`, or by a named pattern that lists every id it covers. A decision is a Review judgment, owned and recorded in the package's own context; the Test Plan only references it. It carries the finding's `id`, `digest` and construct text as written. It matches a finding only when `id` and `digest` both match. A decision that matches no finding is stale and a finding with no matching decision is undecided; both stay visible to the owner, and neither is silently dropped. Whether a decision is right stays with the CTO and CPO.
- **hosting/F70** [hosting/I15]: **One skill.** `skills/kaal-hosting-boundary/` is removed, with `SKILL.md`, `HOSTS.md` and every operational mention of it: the `kaal-hosting` skill, `references/operations.md`, the README, `files`, `bin`, and tests other than the removal test. A plan or a record of history may name the retired path as history; the removal test names it only to assert its absence. Hosting ships one skill, `kaal-hosting`. Its Boundary Check section says how to run the command, how to read the list (rules, classes, references, the question), that the list is evidence and not a verdict, and that deciding is the owner's. The host facts that `HOSTS.md` held move to `skills/kaal-hosting/references/hosts.md`, keeping the `kaal-hosting:hosts` table and its scoped `@kaihacksai/kaal-hosting/…` specifiers (hosting/F15). This **supersedes hosting/F34** (the boundary Skill's review instructions, which the `kaal-hosting` skill's Boundary Check section now carries) **and the file location of hosting/F41** (the per-host guide, whose content is unchanged). The planned Cases that name the old paths (hosting/T40's skill clauses, the portability guide Case of `test/plan/portability.test.mjs`, and hosting/T66) are superseded in the same Change by hosting/T121 and hosting/T123, with the reason recorded in each file.
- **hosting/F71** [hosting/I15]: **Two Test Plans.** Hosting declares two Test Plans in the shape agreed with Packaging and Testing. The Package Check is Hosting's own `verify` Cases. The Boundary Check is declared **not applicable** for Hosting: a declared status with a reason, in the shape Packaging gives not applicable (C33, #667), and not a skipped Case or an outcome. The reason is that Hosting is the operating-system boundary (hosting/C13, hosting/I10), and nothing is omitted silently. The shape for every other package (a Boundary Check that names its targets, its finding list and its recorded decisions) is Packaging's and Testing's to state; Hosting supplies the scan and the id format.

## Non-functional

- **hosting/N9** [hosting/I15]: The scan takes no new runtime dependency and reads no TypeScript parser. It is deterministic, never executes the target, and never loads `node:test` from the command.
