# review/A2 review-items

Three kinds of file, one reader and one command; nothing else.

- **Review item**, `V<n>.md`: the definition (F27). **Review result**, `RV<n>.md`: the execution and result (F29). Both are Markdown with simple front matter: `key: value`, `key: [a, b]`, or a key followed by indented `- item` lines (for `parts`, each item ending in `: <conclusion>`). They are read as text and never run. The ids are `<namespace>/V<n>` and `<namespace>/RV<n>`; `RV<n>` is the object the package layout already reserves under `02-learnings/reviews` for reviews worth keeping, and every result of a defined item is worth keeping.
- **The reader**, `skills/kaal-review/scripts/navigate.mjs`, exports `navigate(root, { revision })` and is also the command `navigate [--root dir] [--revision r] [--subject id]`. It lists the tree through Hosting (`list` with skip and links, then `readFile`) and Review owns what the files mean. It returns `{ items, results, validatedBy, current, stale, findings }`: the items, the results (an execution that could not be performed is a result entry with `conclusion: null`), the reverse pointer `validatedBy[subject] = [item ids]`, `current[item] = [{ result, applicability }]` with `applicability` `applies` or `carried` to the stated revision (an empty list when none), `stale[item]` the results of other revisions that no carry reaches, and the findings. A malformed file is a finding with its path and is never dropped silently, as in Testing's catalog: `no-id`, `duplicate-id`, `item-incomplete`, `dangling-appraises`, `bad-conclusion`, `performed-without-conclusion`, `conclusion-without-performance`, `part-contradicts-conclusion`, `no-relation`, `carry-without-reason`, `carry-dangling`, `carry-other-item`, `carry-conclusion-differs`, `malformed-front-matter`, `bad-execution`, `result-incomplete`, `authority-claim`. The command prints the answer as JSON, exits 0 whenever an answer was produced, and gives no verdict.
- **Placement.** An item sits beside the subject it points at, in a folder named `review-items`, the way a Case sits in `test-cases`; results sit in `02-learnings/reviews`. Neither placement is assumed by the reader: it takes a root and reads what is under it. Adding `review-items` to the layout of a package is Engineering's change to the layout, and is asked for, not made here.
- **Dependencies.** Hosting, for the walk and the reads, and Node. Foundation if a digest is ever needed; none is. It imports no other KAAL package, and in particular not Testing's catalog: it mirrors its contract (read as text, never dropped silently, no verdict) without sharing its code.

## What corresponds to what in Testing, and where it differs

| Testing | Review | Difference |
| --- | --- | --- |
| Case `T<n>`, `id`, `tests`, `title`, `run()` | Review item `V<n>`, `id`, `validates`, Question, Criteria, Expected evidence | a Case is executable and carries its oracle; an item carries the criteria a reader applies |
| `tests`: Intent, Requirement, Architecture, Defect, code | `validates`: anything with an id, or a path | everything can be validated and not everything can be verified, so the targets are wider; the symmetry is in structure, not in scope |
| `collectCases(root)` and its findings | `navigate(root)` and its findings | same contract: read as text, a malformed file is a finding |
| run report, one per run, regenerated | execution, one per appraisal, kept | an appraisal cannot be re-run on demand, so its record is the only evidence of it |
| observation GREEN, RED, UNKNOWN | conclusion `satisfied`, `not-satisfied`, `unresolved` | UNKNOWN there also covers a run that could not finish; here that is `could-not-perform`, apart |
| expected revision mismatch makes everything UNKNOWN | a result for another revision is `stale`, or `carried` by an explicit record | a judgement may still hold at the next revision, and the carry says why |
| a Case is RED, parked or GREEN | an item with no result, a result, or a stale one | there is no parked state; absence is itself the answer |
| a GREEN Case is evidence for a verifier to read | a `satisfied` result is evidence for an owner to read | neither decides acceptance |

## Boundary

Testing owns Cases, the catalog and the run report, and the Judgement loop of its Skill already says a claim that only judgement can settle is recorded as a judgement, never as a passing test, from a seat that is not the author's: that is where Review's results begin. Subjects and their acceptance stay with their owners. Controls owns what a control requires and where it is required; a record has no field for a station, and an adapter that wants the field `required-at` keeps it beside the item, outside this contract. Research owns the method of a trial; an item may name a trial as expected evidence and nothing more.
