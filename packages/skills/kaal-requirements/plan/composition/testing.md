# Optional Composition with Architecture: Testing

The planned outer tests will live in `packages/skills/kaal-requirements/test/plan/composition.test.mjs`, written in `requirements/C3` and turned GREEN by `requirements/C4`. Each title names the contracts it checks. They are immutable to DO and CHECK. The four states are Acceptance scenarios on the packed packages, with T7 following T3, named as `architecture/C8` names its own: alone, both present, Architecture removed (Architecture says "Requirements removed"), independent upgrade. What RED and GREEN mean, and what counts as evidence, is Testing's.

| Test | Checks | Loop |
| --- | --- | --- |
| requirements/T1: **alone.** A consumer installs and registers only `kaal-requirements`. The Engine verifies, no `Placement` is present, and every Requirement's placement reads as not assessed | requirements/I1, requirements/N2, requirements/F1 | Acceptance |
| requirements/T2: **both present.** A consumer registers both packages. A Requirement reached by a decision's `Placement` Edge reads as placed, citing that decision by name and id. A Requirement no Edge reaches reads as without architectural response. The Engine verifies | requirements/F1, requirements/F2 | Acceptance |
| requirements/T3: **Architecture removed.** In the consumer from T2, a first process observes the placed Requirement and writes a `Placement Observation` to a directory the consumer owns, outside the Engine. The consumer then uninstalls Architecture. A fresh process, with only `kaal-requirements` installed and nothing carried over from the first, reads that directory. The observation's bytes still match its id. It names the Requirement, the decision, `Placement` and when it was observed, and it reads as retained: not current and not false. Requirements' Nodes are unchanged and still admitted, the Engine verifies, and placement now reads as not assessed | requirements/F3, requirements/F6, requirements/N2 | Acceptance |
| requirements/T7: **re-check restored.** The consumer from T3 reinstalls the same Architecture, with the same decision. A fresh process reads the same observation as current again, without rewriting it | requirements/F6, requirements/I3 | Acceptance |
| requirements/T4: **independent upgrade.** In the consumer from T2, the Requirement is replaced by a version with another id. The decision's Edge is unchanged, `check()` reports it as naming another id, and the Requirement reads as placed against an earlier version. Upgrading Requirements alone leaves its Nodes admitted | requirements/F4, requirements/N2 | Acceptance |
| requirements/T5: `package.json` has no `dependencies`, `peerDependencies` or `optionalDependencies` naming `kaal-architecture`, and nothing it ships imports it | requirements/N1 | Requirements |
| requirements/T6: The Node `Requirements` and the README state the three placement values, that Requirements reads `Placement` and owns none, an observation's three currencies, and that reading a placement transfers no ownership | requirements/F1–F6 | Requirements |
| requirements/T8: `Placement Observation` is a `KAAL Definition` admitted with the Capability. It states the fields of F3, that an observation is the consumer's, that it adds no Edge, and its three currencies | requirements/F3, requirements/F6 | Requirements |

The Test Cases do not judge whether a Requirement is well stated or a placement is good, and they do not test Architecture's own behaviour. Those are the agents' and Architecture's own tests.
