# architecture/C17 defect-placement

Lets Architecture do for an accepted Defect what it already does for a Requirement: address it, so that the record is the functional placement of the correction.

## Baseline

`kaal/architecture/classify` holds the record mechanics (F14 to F16, `lib/records.mjs`): an A-record's `addresses` may name only a Requirement, an F or an N. A Defect today is a record of the capability that found it, for example `hosting/D14`, with its Test Cases.

## Authorities and the order of a Defect

| Step | Owner |
| --- | --- |
| a finding, from a human, an agent or a control | external input: not an instruction, not a KAAL artifact |
| proof | Testing |
| **Found**: where it showed up | the Defect record, owned by Defect and Testing |
| **Born**: the level where it originated (intent, requirements, architecture, code, test, operations) | Review judges it, consulting the owners; an accepted Defect then becomes a subject of KAAL |
| **Placed**: the architecture component, KAAL or external, where the correction happens | Architecture: `addresses` the Defect |
| **Fixed**: where the correction happens | the same place as Placed; it follows from Placed |

Born comes before Placed. Born in code: the architecture stands and the code is corrected to it. Born in architecture: the placing record is re-judged and changed, then the code is judged against it again. Born in requirements or intent: the correction starts there and the placement follows. The lifecycle and the authority boundaries are the same in a hotfix, which can carry PLAN and DO in one pull request, and in a collector, which can split them across pull requests.

## PLAN

Adds I3, F17, F18 and N3, and the Cases T27 to T29. F17 widens what `addresses` may name to an accepted Defect. F18 states the order Found, Born, Placed, Fixed, that Review judges Born, that the addressing record is the placement and Fixed follows it, and that a Defect addressed by none is unplaced. The special `places`, `origin` and `fixOwner` fields and `placement.mjs` of the earlier head are dropped. The Cases are red: T27 fails because `checkAddresses` rejects a Defect id, T28 and T29 because `addressing` is not yet exported. The DO changes `lib/records.mjs` only: accept a Defect id in `addresses`, and add `addressing(id, records)`, the derived reverse lookup.

## Open questions for the CPO

1. Where Review's judgement of Born is recorded, and so how a placement is informed by it, is for Defect and Review to say; this Change reads no Born and checks no consistency between Born, Placed and the Change that fixes it.
2. Whether an accepted Defect is recognised by being a Defect record in an observed namespace, as here, or by a status the Defect capability defines, is left to Defect.

## What this Change does not do

It changes no Defect record in any package, accepts, proves or judges no finding, does no fixing, execution, CI or workflow orchestration, adds no Control and no gate, and resolves nothing across packages.
