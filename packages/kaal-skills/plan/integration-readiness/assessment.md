# kaal-skills: gap assessment of the six other capabilities

Method and limits. I read each capability's package or collector, its Skill and its tests. **I ran none of them** (this environment has Node 22, the repository needs 24 and a built Hosting). Compliance below is "as far as reading shows". Where I name a Change, it is the *smallest* that would make the capability conform, proposed for the CPO; I registered no Gap or Change id for any of them. Testing is the reference (`evidence.md`). Two state facts matter to every row: **Intent** and **Requirements** are not on `main` in the current layout, and **Architecture** and **Release** are on collectors that are not promoted yet.

Reading: F1 Declare, F2 Call without an agent, F3 Say honestly, F4 The rule stays home, F5 Judgment stays judgment, F6 Name no host. "n/a" means the capability has no mechanism of that level, which the contract does not demand.

## Per capability: what is missing and the smallest Change

**Intent.** *Missing:* it is not on `main` in the current layout, and it has no declaration. *Smallest Change:* none until Intent lands (its own Change, already planned in C5/C9). Then one declaration with one `skill` mechanism `capture-intent`: Skill file, the "Steps" section, shape = the fields of the Intent form. No script: whether an Intent says "what" without "how" is judgment.

**Requirements.** *Missing:* the Skill itself. There is nothing yet to integrate, and the contract does not ask for it to exist. *Smallest Change:* the Skill belongs to Requirements' own Changes (C15/C16 are about it standing alone); once there is one, a declaration with one `skill` mechanism. A `script` candidate is the trace "a Requirement serves an Intent" (the `Serves` Edge); Change's isolation already traces Intent to Requirements, so a second checker would duplicate it. Do not add one.

**Architecture.** *Missing:* a declaration; promotion. *Smallest Change:* after promotion, one declaration, one `skill` mechanism `classify`, shape = the report it already specifies. Note the open Owner call on S4 `ambiguous` (T3): it is exactly the kind of question the contract does not answer. A `skill` mechanism's quality is judged, never tested by a common Case.

**Change.** *Missing:* a declaration and a fixtures module that names the three inputs for each check. *Smallest Change:* a declaration with three `script` mechanisms (`isolation` and `delivery` as `check`, `lifecycle` as `measure` or `check`) and one `skill` mechanism for the transition, plus fixtures (the existing `test/fixtures/model.mjs` is the base). Nothing else changes. `test/verify.mjs` (exit 0/1/2: `verified`/`failed`/`cannot verify`) is the package's own consumer verification, not a mechanism for a target; it should stay out of the declaration. Open point for Change's thread: an `unknown` fixture for `isolation`.

**Review.** *Missing:* a declaration. *Smallest Change:* a declaration with one `skill` mechanism `review-work`: shape = a finding (what was checked, the evidence, or "inferred") and the list for the human observer. No script and none wanted: a review is validation, a judgment, and VIVA AQUA keeps it apart from verification. Review can ride its next Change (applications #1601) rather than open its own.

**Release.** *Missing:* a declaration; the Skill is not on `main`. *Smallest Change:* after #1577 lands, a declaration with two `script` mechanisms in the command form (`pull-promotion` as `check`, `show-wip` as `measure`) and one `skill` mechanism for the release steps. This is the only existing command-shaped mechanism, so it should also be the first non-Testing declaration to pass the Cases (it tests the part the Testing evidence could not). **Boundary to keep:** the release *engine* (`engineering/release`: pack, publish, registry acceptance) acts, and Owner approval gates publication. It is Engineering's, outside this contract: F2 and F3 describe mechanisms that read and report, not ones that publish.

## Reading across the seven

- Four of the seven (Intent, Requirements, Architecture, Review) are judgment capabilities. Their integration is an agent given a Skill and a result shape, not a script. The contract encodes that (F5) and does not push them toward a script they should not have.
- Three have mechanical parts (Testing, Change, Release). Testing and Change are module APIs; Release is a command. The contract allows both forms.
- No capability needs a refactor to conform. Every smallest Change is one declaration (data) and, for the mechanical ones, a fixtures module. Order, by readiness: Testing (reference), Change, Review, Release (after #1577), Architecture (after promotion), Intent, Requirements (after they land).
