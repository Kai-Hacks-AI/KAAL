# Skill Standard: Requirements

Each Requirement names, in brackets, the Intents it serves, and says what verifies it.

## Nonfunctional

- **core/N25** [core/I27]: The standard is capability-agnostic. Core's check takes only the files it is given, names no capability, reads no registry, and gives the same result for the same input, whichever path the Skill takes. Verified by core/T106.
- **core/N26** [core/I28, core/I29, core/I30]: Core judges and reports. It does not decide what a verdict allows. A gate, WIRE or a control owns the policy and the baseline file, and Controls only runs the check. Verified by core/T106 (exit status and data) and core/T108.
- **core/N27** [core/I27]: No Core rule contradicts the Agent Skills standard. Core's rules are stricter, never different. Verified by core/T105 (a Skill of `SKILL.md` alone, the Agent Skills minimum, passes clean) and by the Owner's review of the DO against agentskills.io, a judgement.

## Functional

- **core/F92** [core/I27]: Core's payload carries a `Skill Standard` Definition, typed by `KAAL Definition`, beside `CASE` and `LOVE`. It states the vocabulary and conventions, that agentskills.io is the floor, the router and `lane` rules, that the frontmatter is reviewed separately, and that capabilities own their content. It changes neither the Kernel nor the id of any existing Node. Verified by core/T107.
- **core/F93** [core/I29]: `judgeSize` counts the words of a `SKILL.md` body: the whitespace-separated tokens after the frontmatter. The frontmatter is the block from a first line `---` to the next line `---`, found without reading its fields; a leading byte order mark is ignored, and a file with no such block, or an unterminated one, counts whole. Line endings do not change the count. It returns one level: `ok` up to 200 words, `soft` above 200, `medium` above 400, `hard` above 600. Exactly 600 is `medium`, and passes. Verified by core/T103.
- **core/F94** [core/I29]: Every `soft`, `medium` and `hard` result carries a warning as data: the Core rules that apply (`size`, `router`, `detail` and `lane` at every stage), the three remedies (review the whole router, consolidate, move detail to references), a `response` stage, and the actions the stage requires. The required actions of a higher stage include all of those of the lower one and more: `review-router` at `soft`, plus `restructure` at `medium`, plus `correct-before-delivery` at `hard`. Trimming words is never a remedy. Only `hard` blocks. Verified by core/T104.
- **core/F95** [core/I27]: `judgeLayout` takes the paths of a Skill directory and finds: no top-level `SKILL.md`, and any top-level entry that is not `SKILL.md`, `references/`, `scripts/` or `assets/`. `SKILL.md` alone is a complete Skill. Anything below the permitted folders is free. Verified by core/T105.
- **core/F96** [core/I27, core/I28]: `kaal skill check <dir> [--json] [--baseline <file>] [--of <reference dir> [--as installed|development|variant] [--version <v>] [--source <label>] [--owner <capability>] [--declared <file> --id <variant id>]]` judges a Skill directory by `judgeLayout` and `judgeSize`, and reads only `<dir>`, the baseline and the files `--of` and `--declared` name. Its exit status is what a gate relies on: 0 when nothing blocks (`ok`, `soft`, `medium` and a known baseline entry included), 1 when something does, 2 when it cannot judge (no such directory, unreadable file or baseline, a missing or contradictory option), which a gate treats as unknown and never as clean. With `--json` it prints the verdict as data. The directory is the candidate as data, so a gate may run Core from its base or default branch. Verified by core/T106.
- **core/F97** [core/I30, core/I31]: The `skill-size` ratchet. A baseline is a JSON object from a canonical Skill's name to `{ "owner": <capability>, "words": <recorded body words> }`; an entry without both is an unreadable baseline. Against it, a `hard` canonical Skill is `known` when its words equal the entry and passes; `grew` when above it and blocks; `new` when it has no entry and blocks. An entry whose Skill is now below its recorded words is `stale` and blocks until the entry is lowered or removed, so the allowance only shrinks and a resolved finding leaves it. With no baseline, `hard` blocks. An unreadable baseline is exit 2. The key is the Skill's name, never a path, so the Skill has one entry wherever it is deployed. Verified by core/T108.
- **core/F99** [core/I31, core/I34]: Comparison. With `--of <reference dir>` and no `--as`, `<dir>` is a deployed copy, and its tree digest (SHA-256 over the sorted relative paths and the exact bytes of every file) must equal the reference's: `identical` passes, `differs` blocks and lists the differing paths as data. An instance is judged under its canonical's name and so its entry, as a ceiling: `known` at or below its words, `grew` above them, `new` when it is `hard` and has no entry, and never `stale`, because only the canonical, which has no `--of`, retires an entry. An instance is never given an entry of its own. The result names the reference and, where given, its version. Verified by core/T109.
- **core/F100** [core/I32]: Variants. `--as variant --of <canonical dir> --owner <capability> --declared <file> --id <id>` judges an instance that differs by design. `<file>` is the owning capability's declaration, a JSON object from the Skill's name to `{ "owner": <capability>, "variants": { <id>: { "transformation": <text> } } }`. The variant is `declared` when the declaration's owner equals `--owner` (and the baseline entry's, when there is one) and it lists `--id`. It is `unauthorized` when the declaration's owner differs, and `undeclared` when the id is not listed. Both block, and the instance's own files are never read as a declaration. Without `--owner`, `--declared` or `--id` the check cannot judge (exit 2). A declared variant is otherwise judged by `core/F99`, so it may differ from the canonical and never has more than the canonical's allowance. Verified by core/T109.
- **core/F101** [core/I33]: Installed content. A directory under a `.kaal/` path is always judged `--as installed`, and any other role for it cannot be judged (exit 2). `--as installed` requires `--of <the published artifact's Skill directory>` and `--version <the published version>`; without either it cannot be judged (exit 2), never clean. The tree must equal the published artifact's exactly, a declared variant as published included: `identical` passes and `altered` blocks with the differing paths. The result names the version the reference is. Core does not fetch a published artifact: the gate supplies the one the registry serves for the version the installation record names, and cannot judge when it has none. Verified by core/T110.
- **core/F102** [core/I34]: Development versions. `--as development --of <published artifact> --version <v> --source <label>` judges a Skill under development as its canonical: the whole of `core/F93` to `core/F97`, `stale` included. It adds a comparison report, `compared: { development: <label>, published: <v> }` and the differing paths as data, that never blocks by itself. Without `--version` or `--source` it cannot judge (exit 2). Verified by core/T111.
- **core/F98** [core/I27]: The frontmatter is not counted, and Core reads none of its fields. Its upstream conformance is Engineer Skill's `checkSkill` (a result), and its clarity and concision are a review's judgement. No Test Case judges them. Verified by core/T103 (not counted), and by judgement for clarity and concision.

## Amended

- **core/I14** and **core/N13** (see Intent): Core defines no Skill file format and never rewrites a `SKILL.md`. It states the KAAL standard, finds where the frontmatter ends and counts words.
- **core/F7** stands: a `SKILL.md` follows the Agent Skills standard and is deployed unchanged.
