# Core 0.0.1 initialization and consumer completion: Requirements

Each new statement traces to this PLAN's Intent. This is a proposal, not a claim about today's installed package.

## BASS

- **core/F89** [core/I26]: Core delivers one Agent Skill at `skills/kaal-core/SKILL.md`, with its Skill Node `skills/kaal-core/Core-Skill.md`, named `Core Skill` and typed by the existing `KAAL Skill`. The Skill covers discovery, inspection, explicit initialization, registration, verification and escalation. It uses the existing public API and the installed scoped package's own CLI. It implements no other capability's product behavior and defines no new Skill format.
- **core/F90** [core/I26]: Core's delivered `AGENTS.md` points an agent to that Skill in the installed `@kaihacksai/kaal-core` package and to applicable repository authority. It remains navigation, not a second procedural manual. Reading guidance or discovering a Skill never authorizes a write or means the Skill was used. Installation/import/inspection performs no initialization.

## Explicit initialization

- **core/F91** [core/I27]: For a new missing or empty Engine, an explicitly requested `kaal init` admits and registers Core's own Capability, its Core Skill, Foundation's owner-declared contribution and Hosting's owner-declared contribution, preserving each contribution's CASE kind. `kaal list`/`catalog` report the admitted contributions and `kaal verify` succeeds. Installing their packages alone registers none of them. Core's existing `Core` Capability Node is reused byte for byte; its ownership claim stays repository data.
- **core/F92** [core/I27]: A missing, malformed, wrongly typed, conflicting or rejected mandatory contribution refuses initialization with the owning package/contribution and reason, before any target write. It never reports that contribution as admitted, infers a substitute from package metadata, chooses another installed package, or partially initializes the Engine. An already complete identical initialization is a no-op. An existing valid bare Engine missing the mandatory registrations is left unchanged and reported as incomplete by `init`, with an explicit recovery direction; it is not silently adopted or migrated. Existing inspection and generic bootstrap semantics are unchanged.
- **core/F93** [core/I27]: Presence, registration, admission and use remain distinct. An unregistered Skill outside the Engine does not appear in its admitted catalogue. A refused contribution does not change the Engine or appear as admitted. Core does not prevent an agent from reading an unregistered Skill and does not report that reading as KAAL-verified. There is no new persistent index or registration recorder.
- **core/N24** [core/I27]: Core validates the complete prospective initialization, including ownership-preserving installation records, before Hosting publishes it as one operation. Existing no-write-on-refusal, preservation of author files and lifecycle ownership guarantees apply. Core writes no Foundation/Hosting-owned installation record on their behalf. The declaration transport and lifecycle responsibility must be agreed with those owners before DO; Core may not invent their declarations to remove the dependency.

## Package and assurance completion

- **core/F94** [core/I28]: Core reuses Testing's approved result and model contracts and Packaging's generic conformance. One final `kaal-core-verification {json}` report holds `result`, `exit`, `candidate`, per-case `cases` and `causes`; a healthy run reports `verified`, exit 0, with every required case observed `pass`. The candidate names package, version and manifest digest. The same execution supplies both human and machine evidence; no second recorder or independent coverage registry is introduced. Missing/inconsistent evidence remains `cannot verify`, never `verified`. The existing failure and tamper semantics are preserved.
- **core/F95** [core/I28]: Core declares a separate source suite `test:release` as `node --test test/plan/release.test.mjs`. Comprehensive source `npm test` runs it using the existing runner. The suite runs the complete existing release acceptance boundary, not a name-filtered subset. Planned future tests are not silently enrolled until their DO. The installed runner still runs only consumer verification.
- **core/F96** [core/I28]: The existing three-host Acceptance scenario also executes installed Core's `npm test`, with its candidate-specific per-case report retained by the existing evidence mechanism. Package identity/integrity, installed behavior and platform assurance remain separate findings. No new workflow, database, service, authentication mechanism or required check is needed by this PLAN.
- **core/N25** [core/I26, core/I27]: Embed and External share Core semantics. Pure APIs and explicit Engine paths permit inspection from a separate controller. Read-only commands against an explicitly named external Engine write neither that Engine nor the controller's `.kaal`. Initialization remains an explicit write to the named Engine. Recorded upgrade/remove still act only on the supported repository-root `.kaal`; this release introduces no external activation or arbitrary-target lifecycle.
- **core/N26** [core/I28]: Existing contracts core/F68–F88, core/N19–N23 and the Installation Contract remain the release boundary except for the explicit amendments below. A source build uses the locked Engineering checkout and Graph's pinned build inputs. An installed consumer needs neither workspace layout, Graph, TypeScript, publisher tests nor network to verify. A manifest match proves consistency, not provenance. Registry dependency resolution and publication acceptance cannot be claimed from a tarball-only trial.

## Explicit amendments for the subsequent DO

| Existing contract | Proposed amendment; preserved obligation |
| --- | --- |
| core/F40, core/A18 | Core's Capability Node may ship as an initialization contribution. The ownership claim remains repository-only. Its bytes/identity and product meaning do not change. It is not another foundational Definition. |
| core/F43, core/A20–A22 | New `init` includes the owner-declared mandatory contributions and Core Skill. Existing record/version, preservation and atomic-refusal guarantees stay. No general migration is added. |
| core/F70, core/F85, core/F87, core/A43 | Normalize the existing report/inventory to Testing's authoritative model and Packaging's public reader, preserving exact case identity, missing/skip/todo/undeclared/failure distinctions and candidate identity. Do not copy Testing's algorithms into Core. |
| core/F69, core/F71, core/A33 | Delivered documents describe the implemented initialization, Skill, model/report and true test allocation; historical publisher evidence is not consumer evidence. |
| core/F74 | Complete Core's already approved scoped identity and public metadata. Hosting and other importers change under their own ownership. |

Existing immutable planned tests that assert the old payload count, `init` result, manifest shape or result-line spelling require a reviewed PLAN amendment before DO. That amendment must retain their behavioral discriminators and identify every changed assertion; a new expected count or parser must not erase the underlying assertion. C40's new executable cases are immutable to its DO as well.
