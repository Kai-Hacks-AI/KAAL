# Core 0.0.1 initialization and consumer completion: Architecture

## Elements

- **core/A45** [core/F89, core/F90]: The shipped Core Skill guides the existing CLI/API, with a concise Skill Node. Core's existing `AGENTS.md` supplies navigation. Engineer Skill checks Skill format; Core decides Node admission. Instructions use the installed scoped package's own CLI path, never a potentially unrelated `npx kaal` or `npm exec` bin. Any reference material is inside the Skill folder.
- **core/A46** [core/F91–F93, core/N24]: Initialization plans one prospective Engine using existing admission, contribution-registration and Installation Contract rules, validates it, then asks Hosting to publish once. It does not serially publish four contributions and leave a half-initialized Engine on failure. Core's own Node/Skill are Core data. Dependency declarations are owner-authored bytes acquired through an owner-approved public delivery contract. An installed dependency's public contribution is the simplest source when available; a repository-only ownership claim is not a consumer delivery contract. An explicit Core-owned binding names the package, contribution and CASE kind; dependencies do not implicitly register themselves. The transport is an owner-interface decision, not a new Core-defined cross-product registration standard. Existing generic bootstrap and inspection remain usable without these contributions.
- **core/A47** [core/F94, core/N26]: The existing runner/verifier and manifest generator adopt Testing's model/report through their approved public contracts. Packaging runs from outside against the same installed candidate, with Testing's real `check`/`tested` supplied by the verifier's caller. Neither becomes a Core runtime dependency merely because it judges Core. The final normalized report replaces divergent reporting; it does not create parallel evidence storage.
- **core/A48** [core/F95, core/F96]: One `test:release` entry invokes the existing release file. Engineering's existing Core Acceptance scenario, `engineering/acceptance/embed.test.mjs`, runs installed verification on Linux/macOS/Windows and records the exact candidate report through the existing lane. The workflow and mandatory checks do not change.
- **core/A49** [core/N25]: An external controller supplies a directory to the existing Engine APIs or `--engine`. Read-only commands are tested for unchanged controller/target state. Explicit writes use existing Hosting boundaries; no target-side installation or activation is inferred from inspection.

## Small delivery sequence

1. **C40 PLAN**, this Change: review boundary and executable/scenario acceptance. Ordinary Change into `kaal/core`, squash after independent review and required CI. It enables no runtime or new required check.
2. **TDD/PLAN completion**: settle the owner declaration transport and record/lifecycle responsibility with Foundation/Hosting; settle Testing/Packaging interface versions. Amend affected existing planned tests explicitly, preserving assertions. Finish the dependency-dependent negative cases before their DO. These are genuine prerequisites, not permission for Core to implement those capabilities.
3. **Bounded DO slices**: (a) own Skill/navigation; (b) explicit initialization using available owner declarations; (c) Core scoped identity, normalized verification and full release suite. Consuming capability owners first prepare any name-dependent imports/tests where needed; Core does not bundle those trees merely to rename itself. Each receives independent tests and review; no unrelated collector content travels.
4. **Engineering-owned adoption**: add the installed-verifier invocation to the existing three-host Core acceptance scenario through its permitted Core support path. A workflow/ruleset change, if later found necessary, is separately owned and isolated.
5. **Dependency delivery/SYNC**: Hosting completes its own governed preparation and focused promotion. Core receives promoted dependencies only by a merge-commit SYNC from main. No Graph runtime promotion is required. New main states are synchronized again when needed; never mix a SYNC with an ordinary Change.
6. **Package acceptance**: locked clean build, committed-manifest check, exact pack inventory/exports, fresh copied installation without Graph/build tools, API/CLI/configuration behavior, negative cases and independent Packaging/Hosting findings. Repeat from a clean checkout to challenge reproducibility; preserve tarball digest and tool versions outside the self-manifest. Run installed verification on all three hosts through existing assurance.
7. **Focused Core promotion**: only after that evidence and independent Owner review, synchronize current main and promote by squash under Branching's queue/order rules. No promotion is opened merely to reserve a queue position.
8. **Publication separately**: a tarball candidate can be tested before npm publication. Public release additionally needs real registry resolution of every runtime dependency, then separately authorized publication and registry acceptance of the exact tested bytes through the existing release engine. Never claim Packaging's registry criterion from local tarballs.
