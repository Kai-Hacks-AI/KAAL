# Installation Integrity: Requirements

Each Requirement names, in brackets, the Intents it serves, and says what verifies it. Contract decisions that are still open are marked `open` and listed in `architecture.md`.

## Nonfunctional

- **core/N28** [core/I33]: Independent. The integrity module names no entity, holds no inventory or asset path, imports no capability, and uses only what Core already depends on. Verified by core/T113.
- **core/N29** [core/I34]: Pure. The verdict is a function of the data it is given and gives the same result for the same input. Reading an installed location is the caller's, through Hosting, as Core's realization already does. Verified by core/T110.

## Functional

- **core/F100** [core/I32]: The verdict. For an expected set and an observed set, each a map from a repository-relative path to the SHA-256 of its exact bytes, the result lists the `missing` assets (expected, not observed), the `unexpected` ones (observed, not expected) and the `modified` ones (at the same path, other bytes), in path order. The status is `aligned` when the three lists are empty and `differs` otherwise. The same bytes at another path are one missing and one unexpected. A filename never decides on its own. Verified by core/T110.
- **core/F101** [core/I34, core/I37]: Evidence, not a label. The verdict takes the expected assets as evidence: the establisher's role and identity, and one or more sources, each with its kind, origin, manifest (the entity's kind, name, version and the assets it must have), the SHA-256 of each asset and a tree digest over them. Evidence that is absent, that names no establisher, or whose source is the installation or its own record, is `unknown` with the reason `unavailable`, `no-establisher` or `self-authority`. Verified by core/T111.
- **core/F102** [core/I32, core/I34]: A named comparison. The result names the entity, the selected version, the comparison, the establisher and each source's kind and origin. A source whose manifest names another entity or version is `unknown` with the reason `identity`. Compared with another version's evidence, the same installation gives that version's differences and nothing from the first. Verified by core/T112.
- **core/F103** [core/I32, core/I33]: Kind-agnostic. The same call judges the assets of a Capability, an Agent, a Skill, an Extension and an entity Core has never heard of, with no rule of its own for any of them. Verified by core/T113.
- **core/F104** [core/I35]: Detective first. The exit status of a result is 0 for `aligned` and for `differs`, 1 for `differs` only when enforcement is requested, and 2 for `unknown`, which is never clean. Verified by core/T114.
- **core/F105** [core/I36]: Variants are authenticated. A variant's expected set is accepted only when it carries the owner and path it was supplied from, and the ownership declaration, given as evidence by the establisher from the base branch, names that owner for the entity and that path among the owner's. Otherwise the verdict is `unknown` with the reason `not-owner`, or `no-ownership` when there is no declaration. A location is verified against the one set selected for it. When it matches another set instead, the verdict is `differs` and says which set it matches. Verified by core/T117.
- **core/F106** [core/I34, core/I35]: The three comparisons require their sources. `installed` (`.kaal/`) requires both the published artifact and its Git tag, `engineering` requires the current owning package, and `deployed` requires the selected source. A comparison missing a required source is `unknown` with the reason `unavailable`. Verified by core/T116. How each source is supplied and read is the establisher's, and the technical choice is the CTO's (D1, D5).
- **core/F107** [core/I33]: Reuse and discovery. An entity's identity, version and expected assets are taken from the existing Installation Contract, record, ownership declaration and registration, and a registered entity's installation location can be found and verified. Core derives an entity's expected set from its contract's file and directory assets (the source files under each target), and the scope an observer must enumerate from the same contract: a file asset is its own path, a directory asset is everything under its target, and a surface-gated asset is neither, because Core does not register it. Verified by core/T118. `open`: which published package supplies those source files (D1), and which entities have a contract (D4).
- **core/F108** [core/I34, core/I37]: Completeness. A source is complete when every asset its manifest lists has a SHA-256 in it, and its tree digest, which Core recomputes, equals the one stated. An incomplete source is `unknown` with the reason `incomplete`, and a source whose tree digest does not match is `unknown` with the reason `digest`. Verified by core/T115.
- **core/F109** [core/I34]: Disagreement. When two sources of one comparison, the artifact and its tag, differ in any asset or in their manifests, the verdict is `unknown` with the reason `disagree` and the differing paths, whatever the installation holds. It is never `aligned` with either, and never a difference against either. Verified by core/T116.
- **core/F110** [core/I37]: Unknown has reasons. Every `unknown` carries one machine-readable reason: `unavailable`, `no-establisher`, `self-authority`, `identity`, `digest`, `incomplete`, `disagree`, `inventory`, `not-owner` or `no-ownership`. A control reads the reason, never the wording. Verified by core/T111, core/T115, core/T116, core/T117 and core/T119.
- **core/F111** [core/I34]: Observed completeness. The observed inventory is evidence like the expected one. It states the `scope` its observer enumerated (repository-relative paths, a directory with a trailing `/`, or `.` for the whole location), the SHA-256 of every file found in it, and a tree digest, and may state `complete: false`. It is judged only when it states a non-empty scope, does not say it is incomplete, holds no file outside its scope, matches its tree digest as Core recomputes it, and its scope covers every expected asset. Otherwise the verdict is `unknown` with the reason `inventory`, never `aligned`, never `differs`. An `unexpected` asset is claimed only inside the scope, and a complete inventory of a scope that holds nothing is a finding: everything expected is missing. Verified by core/T119.

## Amended

None. The Installation Contract's and record's rules stand. If a decision adds a member to either, that is its own amendment, planned before it is made.
