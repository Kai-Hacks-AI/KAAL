# Release Readiness: Requirements

Each Requirement names, in brackets, the Intents it serves.

## Functional

- **hosting/F15** [hosting/I5]: The package is named `@kaihacksai/kaal-hosting`, at version `0.0.1`, unchanged. Its `exports` (`.`, `./conformance`, `./package.json`), `engines`, license and runtime dependencies are unchanged, and `files` changes only to add what hosting/F18 and hosting/F19 ship. It declares `publishConfig.access` `public`, which a scoped package needs to be published openly, and its `repository` names `packages/extensions/kaal-hosting` in this repository, as Guard's does. Its README is titled with the new name and states how to install it.
- **hosting/F16** [hosting/I5]: No reference to Hosting by its old name remains in the repository. A reference is a module specifier (`kaal-hosting` or `kaal-hosting/<subpath>`, quoted, in JavaScript, TypeScript or JSON), a dependency entry, a workspace selector (`-w kaal-hosting`, `--workspace kaal-hosting`), or an entry of `package-lock.json`. Each becomes `@kaihacksai/kaal-hosting`, in the same Change, and nothing else in the importing files changes, except where a test depends on how the name sorts, hashes or nests, or names it outside quotes (hosting/A7). Prose that mentions Hosting stays its owner's to revise. The directory `packages/extensions/kaal-hosting` keeps its path. There is no alias and no compatibility package under the old name.
- **hosting/F17** [hosting/I5]: Hosting's packed consumer experience is verified. The tarball `npm pack` makes holds exactly `package.json`, `README.md`, `LICENSE`, `dist/` without `.tsbuildinfo`, and `payload/`, and, once hosting/C12 lands, `docs/`, `test/acceptance/`, `test/unit/`, `test/verify.mjs` and `test/verify.json`. Nothing else ships: no source, no TypeScript test, no `dist-test/` and no `test/plan/`. Installed alone into a fresh, empty consumer outside this repository, with its runtime dependencies from the registry, it lands at `node_modules/@kaihacksai/kaal-hosting`, and a consumer script that imports `@kaihacksai/kaal-hosting` and `@kaihacksai/kaal-hosting/conformance` runs `within`, `reconcile` and `execute` there.

### The complete product and its consumer verification

Today the package ships its code, payload, README and license only. Its Intent, Requirements, Architecture and Testing live in `plan/`, which does not ship, and its tests are compiled into `dist-test` and never packed. So an installed Hosting carries no specification and no test a consumer can run.

- **hosting/F18** [hosting/I7]: **The product contract ships.** The package carries `docs/` with `intent.md`, `requirements.md`, `architecture.md`, `testing.md` and `limitations.md`. They define every Hosting identifier that a shipped case cites, each once, and they are authoritative: the README's guarantees and the PLANs in `plan/` are consolidated into them, and no document in `docs/` cites an Engineering path, a `plan/` path or a Change as its authority. The README keeps the overview, installation, removal and how to verify, and points to `docs/`. A promise the publisher verifies stays a product Requirement in `docs/`, with its allocation stated.
- **hosting/F19** [hosting/I6, hosting/I7]: **Delivered cases.** The package ships its Test Cases as plain `node:test` JavaScript that needs only Node 24: the outer acceptance loops in `test/acceptance/` (Intent, Requirements, Architecture) and the inner Code loop in `test/unit/`. They include the cases of today's `hosting.test.ts` and `conformance.test.ts` and the planned reconciliation tests hosting/T1–T20, which run on the consumer's host. The cases reach the package under test only by its name, so they exercise the installed copy, and they write only to the operating system's temporary directory.
- **hosting/F20** [hosting/I6]: **Invocation.** `npm explore @kaihacksai/kaal-hosting -- npm test` runs the verification entry `test/verify.mjs`, and the package's `test` script runs that entry and nothing else. It needs Node 24 or later and npm on PATH, and it can be repeated. The publisher's own suite moves to a `test:publisher` script.
- **hosting/F21** [hosting/I6]: **One result.** A run ends in exactly one of three results, named in a final summary line and carried as JSON on a line starting `kaal-hosting-verification `:
  - `failed`, exit 1: a delivered case failed, or the consumer changed during the run.
  - `cannot verify`, exit 2: nothing failed, but the run cannot claim verification, because a prerequisite is missing, no case ran, a loop ran no case, a case was skipped or marked todo outside its declared applicability, a declared case did not run, the installed files do not match the shipped manifest, or the verification itself could not complete.
  - `verified`, exit 0: every declared case ran and passed, apart from those declared not applicable on this platform, which are named.

  Every `failed` and `cannot verify` names its cause and a next step. The JSON carries `result`, `cause` (absent when verified), `package` (`name`, `version`, `location`), `platform`, `node`, `digest`, `cases` (each with `name`, `loop` and `outcome`: `pass`, `fail`, `skipped`, `todo`, `not applicable` or `not run`) and `coverage` (each identifier defined in `docs/`, mapped to `covered`, `allocated` or `unverified`).
- **hosting/F22** [hosting/I6]: **Evidence.** The output names the package, its version and install location (its real path), the platform and Node version it ran on, the digest of the installed files, and every case with its outcome. The digest is the SHA-256 of one line `<path>\0<sha256>\n` per installed file other than the manifest and the copy's own `node_modules`, in path order, so anyone can recompute it from the installed copy. The shipped manifest, `test/verify.json`, gives the SHA-256 of every other shipped file (`hashes`) and the inventory of delivered cases by name (`cases`). A mismatch, or a file the manifest does not ship, is `cannot verify`, naming the files. The manifest is consistency evidence, not provenance.
- **hosting/F23** [hosting/I6, hosting/I7]: **Declared coverage.** The manifest's `coverage` declares every identifier defined in `docs/`, each either covered by delivered cases in a named loop, allocated to the publisher's Engineering Test Plan with what the publisher runs, or named as verified by no Test Case with the reason. A run prints the allocated and unverified ones as not verified by it. An identifier that is none of these is `cannot verify`.
- **hosting/F24** [hosting/I6]: **Intact consumer.** The run compares the consumer's content, the installed copy included and other `node_modules` excluded, before and after. A difference is `failed`, naming the paths.
- **hosting/F25** [hosting/I6]: **Declared applicability.** A case may declare the platforms where it does not apply, such as an executable-mark case on Windows, with the reason in `docs/testing.md`. The manifest's `applicability` maps each such case to those platforms. There it is not run, its outcome is `not applicable`, and it does not keep the run from `verified`. A skip or todo that is not declared this way is `cannot verify`.

- **hosting/F26** [hosting/I6]: **One observable contract for every verifier.** Hosting's verifier is an independent implementation of the consumer-verification semantics KAAL Testing owns (testing/F11–testing/F17), as Guard's and Graph's are. Matching result labels prove nothing about equivalent semantics, so each verifier is checked against one shared observable result contract, with the same scenarios and the same expected observations. Each scenario sets up a packed candidate in a fresh consumer and changes one thing. The contract then compares the exit status, the result, the cause, each case's outcome, and the exact installed-package evidence (name, version, real location, platform, Node version and the recomputed digest), never the label alone. The scenarios cover at least:
  - no case, and a manifest declaring no case;
  - an absent manifest, a malformed manifest, and a declared case that does not exist;
  - an installed file changed, removed or added;
  - a case skipped, a case marked todo, and a case declared not applicable here;
  - a failing case, and the consumer changed during the run;
  - a clean run.

  Testing owns the contract's semantics and cases. Engineering runs them against each installed package's verifier in its own Change (#625). Testing plans them in #639 (testing/C29). The contract is the publisher's: it never ships and is never a runtime dependency. Hosting's own cases (hosting/T26–hosting/T31) check Hosting's verifier from the inside. They do not stand in for the contract.

## Nonfunctional

- **hosting/N4** [hosting/I6]: The verification entry uses only Node's built-ins and imports nothing from `dist/`, so a broken runtime cannot mask itself. It realizes the same three-result consumer-verification semantics as Guard in Hosting's own code. Hosting depends on no Testing or Guard package, and the verification adds no runtime dependency.

## Limits

- The rename is planned here and not applied. `hosting/C11` applies it only after this PLAN merges.
- The version stays `0.0.1`. Publication, and any sync or promotion of `kaal/hosting`, need the Owner's own go and are not part of this PLAN or its DO.
- `verified` establishes only that every declared case ran and passed against the installed copy on this host, that the installed files match the shipped manifest, and that the consumer did not change. It is not provenance, which only the registry's integrity and npm's provenance attestation give. It does not cover a behaviour no delivered case checks, nor how a consumer uses Hosting.
- The Test Cases of the verification itself do not ship, so a delivered run never verifies its own verifier. They are allocated to the publisher's Engineering Test Plan, run against a packed candidate in a fresh consumer on Linux, Windows and macOS.
- What Hosting cannot provoke in a consumer's run, such as a host refusing a rollback (hosting/F11) or a removal (hosting/F12), stays covered by the publisher's fault-injecting tests and is allocated to the publisher in `docs/testing.md`.
- hosting/F16 covers references on `kaal/hosting`'s base when `hosting/C11` is raised. A reference added elsewhere afterwards is updated when that branch next takes `main`.
