# Hosting: Requirements (what)

Each Requirement names, in brackets, the [Intents](intent.md) it serves. Functional Requirements (F) say what Hosting does; Nonfunctional ones (N) say how well. Where each lives is in [Architecture](architecture.md), and how each is checked is in [Testing](testing.md).

## Operations

- **hosting/F45** [hosting/I12]: **`read(dir)`** resolves with every file of a tree, keyed by its `/`-separated path relative to `dir`, whatever its name, with its exact bytes. A missing directory reads as empty. It takes no lock.
- **hosting/F46** [hosting/I12]: **`readFile(path)`** resolves with one file's exact bytes. A link to a file reads as that file, as in `read`. A directory, a link to one, a cycle of links, or anything else that is not a file is refused with `NOT_FILE`; a missing path, a dangling link included, with `MISSING`: unlike a tree, a single file has no empty reading. It takes no lock.
- **hosting/F47** [hosting/I12]: **`kind(path)`** says what is at a path: `directory`, `file`, `missing` or `other`. Links are followed as `read` and `readFile` follow them: a link or junction to a directory is `directory`, a link to a file is `file`. Nothing, a path below a file, and a dangling link are `missing`. Something that exists but is neither, such as a cycle of links or a socket, pipe or device, is `other`. A failure to look, such as a denied permission, is thrown as the host reports it, never taken for an answer. It takes no lock.
- **hosting/F48** [hosting/I12]: **`within(root, candidate)`** says whether `candidate` lies within `root`, by canonical path: the host's native `realpath` of both, with links, junctions, `..` and the host's own spelling resolved, then an exact comparison of path segments. The candidate is within when `root`'s segments are all of its own or an exact prefix of them, so `root` itself is within, and `/repo2` is not within `/repo`. There is no case folding and no string-prefix test. Both paths must exist: a missing path, a dangling link or a cycle of links is refused with `MISSING`, never answered `false`. A failure to resolve, such as a denied permission, is thrown as the host reports it.
- **hosting/F49** [hosting/I12]: **`update(dir, plan)`** is one writer at a time, across processes. `plan` receives the directory as it is and returns the change to make, `{ prefix, files }`, or nothing. The change is published all or nothing as a new directory: staged beside the directory, read back to confirm the host holds it exactly (`UNFAITHFUL` otherwise), and renamed into place, together with any parent directories it needs. Any failure leaves the directory exactly as it was. The lock is taken on the directory's canonical path, so every path that names one directory shares one lock.
- **hosting/F50** [hosting/I12]: **`initialize(dir, files)`** populates a missing or empty directory as its only writer. A missing directory appears complete or not at all; an existing empty one, such as the current directory, is filled in place, never removed or replaced. Anything else is refused.
- **hosting/F51** [hosting/I12]: **`execute(command, args, { cwd, env })`** runs an installed command, named on the PATH or by path, however the host realizes it: an executable, or on Windows a `.cmd` shim such as npm installs. Arguments reach the command exactly as given; no shell interprets them. It resolves with the exit status and everything written to stdout and stderr, and rejects when the command cannot be started.
- **hosting/F52** [hosting/I12]: **`contribution()`** resolves with Hosting's own Extension Node, `Hosting.md`, typed by KAAL Extension, for admission by KAAL Core.
- **hosting/F53** [hosting/I12, hosting/I3]: **Portable names.** A path is refused before anything is written when it would not be held faithfully on every supported host: names Windows cannot hold (reserved characters, a trailing dot or space, device names such as `con`) and a path that is not relative or has an empty, `.` or `..` segment (`INVALID_PATH`); and distinct paths that collapse into one where names are compared without case or Unicode normalization, such as `A.md` and `a.md`, or `café.md` in NFC and NFD (`COLLISION`). The rule is the same on every host, so what is written on one stays portable to the others.
- **hosting/F54** [hosting/I12]: **Links.** A link to a file reads as that file. A link to a directory is refused, by `read`, `readFile` and `update` alike: Hosting neither reads nor publishes through one, so nothing it reads or writes lies outside the directory.
- **hosting/F55** [hosting/I8]: **`inspect(files, { builtins })`**, from `@kaihacksai/kaal-hosting/conformance`, reads the JavaScript modules among `files`, as `read` returns them, and checks them against the Node builtins the consumer declares its code may import directly. Its report keeps three kinds of finding apart. `violations` are mechanically verified: a static import, an export-from, or an `import()` with a literal specifier names a builtin that was not declared, each with its file, line, column, specifier and the builtin's `node:` name. `validation` asks for judgment where a machine cannot decide: `import()` with a computed specifier, `process.getBuiltinModule`, `process.binding`, `process._linkedBinding`, `process.dlopen`, `eval`, `new Function`, and any file that cannot be read as a module. `outside` lists packages imported from outside the inspected files. Every report carries `coverage` and `exclusions`, a fixed statement of what was and was not examined. A report without violations means that none was found within that coverage, never that the code complies. The same input always gives the same report, and importing the main entry does not load the inspection.

## Guarded file reconciliation

### Nonfunctional

- **hosting/N1** [hosting/I3]: Every guarantee of Hosting holds on Linux, Windows and macOS. The publisher runs every case on all three, and a consumer's run checks the host it runs on.
- **hosting/N2** [hosting/I1, hosting/I2]: A reconciliation is one writer of its directory, serialized by the cross-process lock that `update` and `initialize` already take. One directory has one lock, whatever path names it.
- **hosting/N3** [hosting/I2]: The same directory and the same reconciliation give the same report on every host.

### Functional

- **hosting/F1** [hosting/I1]: `reconcile(root, { write, remove })` takes a directory and two lists. Each entry of `write` is `{ path, expect, bytes }`, with an optional `executable`. Each entry of `remove` is `{ path, expect }`. `path` is relative to `root` and `/`-separated. `expect` guards the entry: either the lowercase hexadecimal SHA-256 of the bytes the caller expects at `path` now, or `"absent"`.
- **hosting/F2** [hosting/I1]: An entry's precondition holds when `expect` is `"absent"` and nothing is at `path`, or when `expect` is a digest and a regular file is at `path` whose bytes have that SHA-256. Anything else fails it, such as other bytes, nothing where a digest is expected, a file where `"absent"` is expected, or a directory.
- **hosting/F3** [hosting/I1, hosting/I2]: Every precondition is checked before anything is touched. If any fails, nothing in `root` changes, and the refusal (`HostingError`, code `STALE`) lists every failing path in path order, with what was expected and what was found: the SHA-256 of the file there, `"absent"`, or `"not a file"`.
- **hosting/F4** [hosting/I1, hosting/I3]: Paths get the same refusals as `update`, before anything is touched. A path that is not relative or has an empty, `.` or `..` segment is refused (`INVALID_PATH`), and so is a name that is not portable to Windows, macOS and Linux. Two paths that collapse into one where names are compared without case or Unicode normalization are refused (`COLLISION`), whether both are in the reconciliation or one is already in `root`. A path that appears more than once in a reconciliation is refused (`INVALID_PATH`).
- **hosting/F5** [hosting/I1]: A reconciliation never reads, writes or removes through a link. A link at a path, or at any directory segment above it, is refused (`INVALID_PATH`). Something that is not a directory where a segment needs one is refused (`EXISTS`). Nothing is ever written or removed outside `root`.
- **hosting/F6** [hosting/I2]: Applying is all or nothing with respect to the failures Hosting observes: it rolls back on an observed failure, and promises nothing more (see [Limitations](limitations.md)). The new bytes are staged beside `root` and read back to confirm the host holds them exactly (`UNFAITHFUL` otherwise). Every file replaced or removed is kept aside until every change is in place. If any step fails and every step of the rollback succeeds, `root` is restored and the original failure is thrown unchanged. Either way, Hosting then removes what it staged and kept aside, as hosting/F12 states. Restored means restored in its observable state, which is all that Hosting promises: at every path the reconciliation wrote, removed, created or pruned, the same kind of entry as before (a file, a directory, or nothing), every file with the same bytes and, where the host has an executable mode, the same executable mark. Nothing else is promised. Timestamps, ownership, permissions other than the executable mark, access control lists, extended attributes, link counts and file identity may differ, and a directory that was pruned and then restored is a new directory. If the rollback itself fails, F11 applies instead, and `root` is not promised to be restored.
- **hosting/F7** [hosting/I3]: A write marked `executable` leaves an executable file wherever the host has an executable mode, and a write without it leaves a file that is not executable, even when it replaces an executable one. On a host without an executable mode, the mark is accepted and changes nothing. The mode is never part of a precondition.
- **hosting/F8** [hosting/I2]: A directory that a removal leaves empty is removed too, and so is each directory above it that becomes empty in turn, up to but never including `root`. A directory that was empty before, or still holds anything, stays.
- **hosting/F9** [hosting/I2]: A reconciliation that applies resolves with a report `{ outcomes, pruned }`: `outcomes` holds each entry's `path` and its `outcome`, and `pruned` the directories it removed under F8, each list in path order. The outcome is `written` when a write created or replaced a file, `removed` when a removal removed one, and `unchanged` when a write found exactly its bytes and its executable mark already there, or a removal guarded by `"absent"` found nothing. When the host refuses to remove what was staged or kept aside, the report also carries `leftovers` (hosting/F12).
- **hosting/F10** [hosting/I1]: `root` must exist and be a directory. Otherwise the reconciliation is refused (`MISSING`) before anything is touched.
- **hosting/F11** [hosting/I2]: When a step fails and a step of the rollback fails too, the reconciliation rejects with `HostingError` code `UNRESTORED`, never with the original failure and never with a code a successful rollback uses. The error carries the original failure as its `cause` and the recovery location as `kept`: the absolute path of the `<root>.aside-*` directory beside `root`. Hosting keeps that directory and everything in it. It holds every file the reconciliation displaced and could not put back, each at its own `/`-separated path relative to `root`, with the bytes it had. `root` may be partly applied. Everything staged is removed. What to do with the kept files is for the caller, and Hosting does nothing more with them.
- **hosting/F12** [hosting/I2]: Removing what was staged or kept aside comes after the outcome is settled and never changes it. The outcome is the report of a reconciliation that applied (hosting/F9), the original failure after a rollback that held (hosting/F6), or `UNRESTORED` (hosting/F11). Hosting retries each removal as far as the host allows. A directory it still cannot remove stays beside `root`, never inside it, and is reported, never lost and never shown as removed. Each one is a `Leftover` `{ path, error }`: `path` is the absolute path of the directory left beside `root`, and `error` is the host's error from the last attempt, as the host reported it. The leftovers, in path order, go into `leftovers`, which is present only when there is at least one:
  - **Applied.** The reconciliation resolves with its report, `{ outcomes, pruned, leftovers }`. A report without leftovers is exactly as hosting/F9 states, with no `leftovers` property.
  - **Rollback held.** The reconciliation rejects with the original failure, the same error object, with its message and code unchanged, and with `leftovers` added to it.
  - **Rollback failed.** The reconciliation rejects with `UNRESTORED`, its `cause` and `kept` unchanged, and with `leftovers` added to it. The `kept` directory is the recovery location and never a leftover.
- **hosting/F13** [hosting/I1, hosting/I2]: One reconciliation can change what kind of entry is at a path, a file into a directory of the same name or a directory into a file, under one lock and one rollback. Paths nest in exactly two shapes. Any other nesting, such as a write under another write or a removal under another removal, is refused before anything is touched (`INVALID_PATH`).
  - **File to directory.** A removal of `P` with writes under `P/`. The writes are checked as if `P` were already gone: the file at `P`, guarded by its removal, is not refused as a non-directory segment (hosting/F5), and each write under `P/` must expect `"absent"`.
  - **Directory to file.** A write of `P` expecting `"absent"`, with removals under `P/`. The write's precondition holds when `P` is a directory whose every file is removed by this reconciliation and which holds nothing else that would stay, files and directories alike. Otherwise it fails like any other precondition, found `"not a file"` (hosting/F3).
  - **Applying.** Every removal, and the pruning of the directories it empties (hosting/F8), happens before any write. A directory turned into a file is reported in `pruned`, and its write as `written`. A failure while applying restores every path to its kind, bytes and executable mark (hosting/F6), or is `UNRESTORED` (hosting/F11).
- **hosting/F14** [hosting/I1, hosting/I4]: A reconciliation can rely on files it leaves alone. `reconcile(root, { write, remove, expect })` takes an optional third list, `expect`. Each of its entries is `{ path, expect }`, with `path` and `expect` as in hosting/F1, and states what the caller relied on at a path it does not change.
  - **Checked with the rest.** Each expectation is a precondition like any other (hosting/F2). It is checked under the same lock as the writes and removals, before anything is touched. If it fails, nothing in `root` changes, and the `STALE` refusal lists it with every other failing path, in path order (hosting/F3).
  - **Only read.** An expected path is never written, removed, renamed, staged or kept aside, so its bytes, its executable mark and the file itself stay as they are. It has no outcome in the report. A reconciliation whose only entries are expectations applies nothing, and when they hold it resolves with empty `outcomes` and `pruned`.
  - **Paths.** An expected path gets the refusals of hosting/F4 and hosting/F5. A path that appears more than once in `expect`, or in `expect` and in `write` or `remove`, is refused (`INVALID_PATH`), and so is an expected path that has another path of the reconciliation under it or above it. All of these refusals come before anything is touched.

## The package and its consumer verification

- **hosting/F15** [hosting/I5]: The package is named `@kaihacksai/kaal-hosting`. Its interface is exactly what hosting/A15 declares. It needs Node 24 or later (`engines`), is licensed MIT, and declares `publishConfig.access` `public`, which a scoped package needs to be published openly. Its `repository` names `packages/extensions/kaal-hosting` in KAAL's repository. Its README is titled with the name and states how to install it.
- **hosting/F17** [hosting/I5]: Hosting's packed consumer experience is verified. The tarball `npm pack` makes holds exactly `package.json`, `README.md`, `LICENSE`, `dist/` without `.tsbuildinfo`, and `payload/`, `bin/`, `skills/`, `docs/`, `test/embed/`, `test/verify.mjs` and `test/verify.json`. Nothing else ships: no source, no TypeScript test, no build output for tests and none of the publisher's own tests. Installed alone into a fresh, empty consumer outside this repository, with its runtime dependencies from the registry, it lands at `node_modules/@kaihacksai/kaal-hosting`, and a consumer script that imports `@kaihacksai/kaal-hosting` and `@kaihacksai/kaal-hosting/conformance` runs `within`, `reconcile` and `execute` there.
- **hosting/F18** [hosting/I7]: **The product contract ships.** The package carries `docs/` with `intent.md`, `requirements.md`, `architecture.md`, `testing.md` and `limitations.md`. They define every Hosting identifier that a shipped case cites, each once, and they are authoritative: the README's guarantees are stated in them, and no document in `docs/` cites a path of the publisher's repository or a change record as its authority. The README keeps the overview, installation, removal and how to verify, and points to `docs/`. A promise the publisher verifies stays a product Requirement in `docs/`, with its allocation stated.
- **hosting/F19** [hosting/I6, hosting/I7]: **Delivered cases.** The package ships its Test Cases as plain `node:test` JavaScript that needs only Node 24: all in `test/embed/`: the outer loops, one file each (`intent.test.mjs`, `requirements.test.mjs`, `architecture.test.mjs`), and the inner Code loop in every other case file there. They include the Code loop's cases of every operation and of the boundary inspection, and the reconciliation cases hosting/T1–T20, which run on the consumer's host. The cases reach the package under test only by its name, so they exercise the installed copy, and they write only to the operating system's temporary directory.
- **hosting/F20** [hosting/I6]: **Invocation: one test entry, two places**. The package's `test` script is `node test/verify.mjs` and nothing else. npm ships the same script that it reads in source.
  - **In an installation,** `npm explore @kaihacksai/kaal-hosting -- npm test` runs the consumer verification only (hosting/F21–hosting/F25). It needs Node 24 or later and npm on PATH, and it can be repeated. It needs neither the publisher's tests nor KAAL's repository.
  - **In the source workspace,** `npm test` is comprehensive. It runs, once each and in name order, every suite the package declares as a `test:<name>` script, with `npm run`, in the package's directory. The publisher's suite, `test:publisher`, which builds and runs everything Hosting's lanes ran before, is among them. It never runs `test` itself. Its summary line is `kaal-hosting-verification ` followed by JSON with `result`, `cause` (absent when verified), `place: "source"` and `suites`, each with `name` and `outcome` (`pass` or `fail`). The result is `verified`, exit 0, only when every suite passed, and `failed`, exit 1, naming each suite that failed. With no `test:<name>` suite declared, it is `cannot verify`, exit 2.
  - **The place is detected explicitly, never inferred from a missing file.** An installation is a copy whose real directory sits directly in a `node_modules` directory, or in an `@scope` directory there. The source workspace is a directory that the nearest enclosing `package.json` declaring `workspaces` lists among them. A directory that is neither is `cannot verify`, exit 2, naming the directory. So a damaged or copied checkout is never taken for an installation, and the publisher's tests are never silently skipped. Anything that runs Hosting's `npm test` in its directory, such as KAAL's own lanes and coverage, runs it all.
- **hosting/F21** [hosting/I6]: **One result.** A run ends in exactly one of three results, named in a final summary line and carried as JSON on a line starting `kaal-hosting-verification `:
  - `failed`, exit 1: a delivered case failed, or the consumer changed during the run.
  - `cannot verify`, exit 2: nothing failed, but the run cannot claim verification, because a prerequisite is missing, no case ran, a loop ran no case, a case was skipped or marked todo outside its declared applicability, a declared case did not run, the installed files do not match the shipped manifest, or the verification itself could not complete.
  - `verified`, exit 0: every declared case ran and passed, apart from those declared not applicable on this platform, which are named.

  Every `failed` and `cannot verify` names its cause and a next step. The JSON carries `result`, `cause` (absent when verified), `package` (`name`, `version`, `location`), `platform`, `node`, `digest`, `cases` (each with `name`, `loop` and `outcome`: `pass`, `fail`, `skipped`, `todo`, `not applicable` or `not run`) `traces` (each identifier a case cites, with the cases that cite it) and `coverage` (each identifier defined in `docs/`, mapped to `covered`, `not applicable`, `allocated` or `unverified`).
- **hosting/F22** [hosting/I6]: **Evidence.** The output names the package, its version and install location (its real path), the platform and Node version it ran on, the digest of the installed files, and every case with its outcome. The digest is the SHA-256 of one line `<path>\0<sha256>\n` per installed file other than the manifest and the copy's own `node_modules`, in path order, so anyone can recompute it from the installed copy. The shipped manifest, `test/verify.json`, gives the SHA-256 of every other shipped file (`hashes`) and the inventory of delivered cases by name (`cases`). A mismatch, or a file the manifest does not ship, is `cannot verify`, naming the files. The manifest is consistency evidence, not provenance.
- **hosting/F23** [hosting/I6, hosting/I7]: **Declared coverage.** The manifest's `coverage` declares every identifier defined in `docs/`, each either covered by delivered cases in a named loop, allocated to the publisher's Engineering Test Plan with what the publisher runs, or named as verified by no Test Case with the reason. The manifest and the cases' titles only declare: a title's citations are traces from a case to what it tests, and neither certifies coverage. A run reports an identifier as `covered` only when a case that cites it passed in that run, and as `not applicable`, not verified by that run, when every case that cites it is declared not applicable on that platform (hosting/F25). Otherwise an identifier declared covered that no passing case cites is `cannot verify`. A run prints the allocated and unverified ones as not verified by it, apart from what it covered. An identifier that is none of these is `cannot verify`.
- **hosting/F24** [hosting/I6]: **Intact consumer.** The run compares the consumer's content, the installed copy included and other `node_modules` excluded, before and after. A difference is `failed`, naming the paths.
- **hosting/F25** [hosting/I6]: **Declared applicability.** A case may declare the platforms where it does not apply, such as an executable-mark case on Windows, with the reason in `docs/testing.md`. The manifest's `applicability` maps each such case to those platforms. There it is not run, its outcome is `not applicable`, and it does not keep the run from `verified`. A skip or todo that is not declared this way is `cannot verify`.
- **hosting/F35** [hosting/I9]: **The declared interface.** hosting/A15 declares every entry of Hosting's package interface: each `exports` subpath and its target, each `bin` command and its target, and each `files` entry. Each entry's status is exactly `delivered` or `planned`, followed by the change that delivers it. The declaration is read strictly: a row with an unknown kind, an empty entry, a duplicate, or any other status (missing, misspelled, or malformed) fails the Test Case, and is never read as planned. The candidate conforms when, judged against that declaration alone:
  - every `exports` subpath, `bin` command and `files` entry it has is declared;
  - every `delivered` entry is present;
  - a `planned` entry may be present, and once present it is held to the same rules as a delivered one;
  - each present export and command points at its declared target;
  - every target it names (each condition of an export, and each command) is in the packed tarball;
  - the tarball holds only `package.json`, `README.md`, `LICENSE` and what its `files` entries ship;
  - installed alone in a fresh consumer, each export loads by the package's name and subpath, and each command is linked.
- **hosting/N4** [hosting/I6]: The verification entry uses only Node's built-ins and imports nothing from `dist/`, so a broken runtime cannot mask itself. It realizes the same three-result consumer-verification semantics as Guard in Hosting's own code. Hosting depends on no Testing or Guard package, and the verification adds no runtime dependency.

## Platform coupling conformance

- **hosting/F27** [hosting/I8]: **What is read.** `couplings(files, options)` reads every JavaScript and TypeScript source among `files` (`.js`, `.mjs`, `.cjs`, `.ts`, `.mts`, `.cts`; not `.d.ts`), taking `files` as `read` returns them. Comments do not count. Each file is in scope `production` or `test`. A file is `test` when its path has a `test`, `tests`, `__tests__`, `fixtures` or `scripts` segment, or its name has `.test.` or `.spec.`; everything else is `production`. `options.test(path)` replaces that rule. The report lists, in `sources`, every source it read with its scope, in path order, so the production and test code covered is stated. Files that are not sources are listed as skipped, with the reason. The same input always gives the same report.
- **hosting/F28** [hosting/I8]: **What is found.** An identifier bound in the same file to a platform query or a platform literal, such as `const WINDOWS = process.platform === "win32"`, is found where it is bound and wherever it is used. Each finding names its `rule`:
  - `platform-query`: the host is asked which platform it is: `process.platform`, `process.arch`, `os.platform()`, `os.type()`, `os.arch()`, `os.release()`, `os.version()`, `os.EOL`, `path.sep` and `path.delimiter`, `path.win32` and `path.posix`, through any import or destructuring of `node:os`, `os`, `node:path`, `path` or `process`.
  - `platform-literal`: a string literal naming a platform or OS family (`win32`, `darwin`, `linux`, `freebsd`, `openbsd`, `sunos`, `aix`, `android`, `cygwin`, `netbsd`, `windows`, `macos`).
  - `host-api`: a host-specific mechanism that Hosting mediates or that only some hosts have. These are `shell: true` and a literal `cmd`, `cmd.exe`, `.cmd`, `.bat`, `powershell`, `sh`, `/bin/sh` or `mkfifo` command given to `spawn`, `spawnSync`, `exec`, `execSync`, `execFile`, `execFileSync`, `fork` or Hosting's `execute`; `net` listening on anything but a numeric port; a literal mode (`0o…`) passed to `chmod`, `chmodSync`, `mkdir` or `writeFile`; `symlink` with `"junction"`, `"dir"` or `"file"`; `process.getuid`, `process.getgid`, `process.geteuid`; `os.homedir`, `os.userInfo`; and environment variables that are host-specific (`PATHEXT`, `ComSpec`, `SystemRoot`, `USERPROFILE`, `APPDATA`, `HOME`).
- **hosting/F29** [hosting/I8]: **How a finding is classified.** Each finding has one `kind`:
  - `coupling`: any finding in production scope.
  - `registration`: in test scope, a platform finding decides whether a test is registered or run. That covers a `skip`, `todo` or `only` option or call (`it.skip`, `t.skip()`, `{ skip: … }`), a test or suite registered inside a branch, and an early `return` from a test.
  - `dilution`: in test scope, a platform finding decides what is asserted. That covers an assertion inside a platform branch, and a platform-dependent expected value or argument to an assertion (`assert.*`, `t.assert.*`, `expect(…)`).
  - `setup`: in test scope, any other platform finding, such as a fixture built differently per host with the same assertions afterwards.

  A finding that is both `registration` and `dilution` is reported as `registration`. Each finding carries its file, 1-based line and column, scope, rule, kind, and the construct as written.
- **hosting/F30** [hosting/I8]: **Review, not verdict.** A finding is evidence for review. `couplings` never turns one into a pass or a fail, and it never drops one. A capability may acknowledge a finding with a comment, `// kaal-hosting: platform <reason>`, at the end of the finding's line or on the line just above it. The finding then carries `acknowledged` with that reason. It is still reported, at the same place, with the same `kind`, and still counted. An acknowledgement is evidence offered to a reviewer, never an approval: it neither passes a Test Case (hosting/F33) nor withdraws a review request. An acknowledgement with no reason does not count. Whether a judged finding is settled, and with what evidence, is Review's to say.
- **hosting/F31** [hosting/I8]: **The shipped suite.** Hosting ships the suite to anyone who inspects a capability: Engineering, a consumer repository, an agent workflow or release acceptance. The inspected capability never imports or depends on Hosting; only the runner does.
  - `boundary({ name, root, builtins, test })`, from `@kaihacksai/kaal-hosting/boundary`, inspects the sources under `root`, read through Hosting's `read`, with `couplings` and with the existing `inspect` against `builtins` (the host modules the capability declares it may import, default none). `test` is passed to `couplings`. It returns the result of hosting/F33.
  - `boundarySuite(options)`, from the same entry, registers one `node:test` suite named for the capability. It has one Test Case for each deterministic case of hosting/F33, and one case, `judgment requested`, that is reported as `todo` while any review is requested, never as a pass. It writes the result as one line, `kaal-hosting-boundary {…}`, and emits each review request as a diagnostic.
  - The command `kaal-hosting-boundary --name <name> --root <dir> [--builtin <module>]…` prints the same line. It exits 0 when the result is `verified` and no review is requested, 1 when `failed`, 2 when `unknown`, and 3 when `verified` with a review requested.
  - The production entry and `@kaihacksai/kaal-hosting/conformance` never load `node:test`; only `@kaihacksai/kaal-hosting/boundary` does.

  In Testing's Plan → Suite → Case model, this is a Suite, and each capability inspected is a target of its Cases. KAAL's Engineering runs it across KAAL; any other runner may run it too.
- **hosting/F32** [hosting/I8]: **Stated coverage.** The report carries `coverage` and `exclusions`, as `inspect` does, and `sources` states which production and test files were read. A report with no finding means none was found within that coverage, never that the capability complies.
- **hosting/F33** [hosting/I8]: **Deterministic where possible, review where not.** The result carries `name`, `result`, `review`, `cases`, `failures`, `findings`, `reviews`, `summary`, `violations`, `validation`, `outside`, `sources`, `skipped`, `coverage` and `exclusions`.
  - `cases` are the deterministic Test Cases, each with an `outcome` (`pass`, `fail` or `not run`): `inspection completes`; `host modules are declared` (no `inspect` violation); and `production code leaves the host to Hosting` (no `platform-query` or `host-api` finding in production scope, acknowledged or not).
  - `result`, in Testing's vocabulary, is `unknown` when the inspection could not complete, with each reason in `failures`; otherwise `failed` when a case fails; otherwise `verified`. `result` speaks only for the deterministic cases.
  - `reviews` holds one request for every other finding: each test-scope finding and each production `platform-literal`, acknowledged or not. Each request carries an `id`, `kaal-hosting/<rule>@<file>:<line>:<column>`, which is the same on every run over the same sources, so a judgment can cite it. It also carries `rule`, as `kaal-hosting/<rule>`; its `owner`, `Hosting`; the finding; and the question a reviewer must answer for its `kind`. It carries no outcome: an `acknowledged` reason inside the finding is evidence only, and an open request stays open in the result. `review` is `requested` while any request is open, else `none`. A review request is never a passed case.
  - `summary` counts the findings of each `kind`, acknowledged ones included, and how many are acknowledged.

  Engineering and Review own how results and judgments are recorded.
- **hosting/F34** [hosting/I8]: **Review instructions.** Hosting ships `skills/kaal-hosting-boundary/SKILL.md`. It starts with a Bare section, which reads a `kaal-hosting-boundary` line with no Skill. It then gives, for each `kind`, what a reviewer looks for and what evidence settles it: `coupling`, `registration`, `dilution` and `setup`. It explains that an `acknowledged` reason is evidence to weigh, not an approval, and that an agent escalates to a human through PREACH when its authority is not enough. The rules and questions are Hosting's; the judgment and its record are Review's.
- **hosting/N5** [hosting/I8]: The suite is tested with positive and negative fixtures. Each rule and each kind has at least one fixture that must be found and one similar one that must not. A T114-like OS-specific skip is among them. At the suite's contract level, a negative capability fixture with production coupling and T114-style skipped tests and assertions, a fixture that needs only judgment, and a positive one that leaves the host to Hosting fix every finding's place, the outcomes, the review requests, the counts, the sources read and the exit codes. These publisher tests of the suite stay publisher-only.

## Portability across capabilities

- **hosting/F36** [hosting/I10]: **The operating-system boundary is declared by Hosting.** `@kaihacksai/kaal-hosting/conformance` exports `OS_BOUNDARY`, a frozen list of the package names that are the operating-system boundary, exactly `["@kaihacksai/kaal-hosting"]`. `osBoundary(name)` is `true` for a listed name and `false` for every other string, and throws a `TypeError` for anything that is not a string. A package's own field, such as `osBoundary: true` in its manifest, never makes it the boundary. Engineering establishes Testing's `osBoundary` (testing/F67) from this declaration.
- **hosting/F37** [hosting/I10]: **Host facts.** A host fact is a named capability of a host that a case may need, named without any platform: `kaal-hosting/special-entries`, a FIFO and a Unix-domain socket can be placed in a directory tree. `facts()`, from `@kaihacksai/kaal-hosting/fixtures`, establishes each fact on the running host by trying it in a fresh temporary directory, never by reading the platform's name, and returns `{ [fact]: { holds, reason, evidence } }`: `holds` a boolean, a nonempty `reason`, and an `https` link to the evidence. Hosting adds a fact only in a new version of Hosting.
- **hosting/F38** [hosting/I10]: **The special-entry fixture.** `specialEntries(dir)`, from `@kaihacksai/kaal-hosting/fixtures`, where `kaal-hosting/special-entries` holds, makes a FIFO at `dir/fifo` and a listening Unix-domain socket at `dir/socket`, and returns `{ holds: true, fifo, socket, close }`. `close()` stops the listener and leaves the entries for the case to inspect. Where the fact does not hold, it makes nothing and returns `{ holds: false, fact, reason, evidence }`, the same reason and evidence as `facts()`. It never throws because a host lacks the fact. Where the fact holds but the fixture cannot be made in `dir` (for example, `dir` is missing or is a file), that is a setup failure: it throws a `SetupFailure` with `outcome: "unknown"`, the fact, the directory and the reason, and makes nothing. It never returns `holds: false` for it, so a setup failure can never stand for a host that lacks the fact or justify a case being not applicable; a case using it fails, never skips or passes. It is the only place a KAAL test makes a FIFO or a socket.
- **hosting/F39** [hosting/I10]: **Applicability rules.** For every package but the boundary:
  - A case may be not applicable by host fact: `{ host: [fact…], reason, evidence }`, where each fact is one of hosting/F37's, the reason is nonempty and the evidence is an `https` link. It is not applicable on a run only where `facts()` established one of its facts not holding there. The case stays registered on every host, with the same title and body, and is never reported as passed.
  - A case is never scoped by `platforms`, and a manifest never limits the package by `os` or `cpu`. Either is an architectural violation (testing/F67), never an exemption.
  - Applicability by optional complement (`requires`, `absent`) is Testing's and the composition rule's, not Hosting's. The audit leaves it alone.
- **hosting/F40** [hosting/I10]: **The portability audit.** `portability({ name, root, builtins, test, applicability })`, from `@kaihacksai/kaal-hosting/boundary`, runs `boundary` (hosting/F33) on the same options and extends its result. `applicability` is the capability's declarations, keyed by case name, as the runner read them from the capability's manifest or Test Plan.
  - `osBoundary` is `osBoundary(name)` of the `name` in `root`'s `package.json`, `false` where there is none.
  - `applicability` lists one finding per problem, each with the `case` (or `package.json`), its `rule` and the problem stated: `platform-applicability`, a declaration with nonempty `platforms`, or a manifest `os` or `cpu`, outside the boundary; and, for a declaration with `host`, `unknown-host-fact` (a fact that is not hosting/F37's), `unreasoned` (no reason), `unevidenced` (no `https` evidence), and `stale` (no test source registers a case of that title, or every fact it names holds on every host in hosting/F41's guide).
  - Two deterministic cases follow hosting/F33's three: `applicability is not scoped by platform`, which fails on any `platform-applicability` and is `not applicable` where `osBoundary` is true; and `host exceptions are well-formed`, which fails on any other applicability finding. Both are `not run` when the inspection could not complete. `result` follows hosting/F33 over all five cases.
  - `reviews` adds one request per host declaration, well-formed or not: `id` `kaal-hosting/host-applicability@<case>`, `rule` `kaal-hosting/host-applicability`, `owner` `Hosting`, the `case`, the `declaration`, and the question whether the case is genuinely inapplicable where the fact does not hold, with its assertions intact where it does. A `review` link inside the declaration is evidence only, and the request stays open in the result: the judgment and its record are Review's (hosting/A14).
  - `challenged` lists, sorted and once each, the case names Testing must not count as evidence (testing/F58, `challenged`): each declared case with an applicability finding, and the title of each test that a `registration` or `dilution` finding decides or sits in, where that title is a string literal. A `setup` finding challenges nothing.
  - hosting/F33's other members, `summary` included, are unchanged.
  - A conditional expression that picks between a test registration function and anything else, such as `(WINDOWS ? () => {} : it)(…)`, is "a test registered inside a branch" of hosting/F29, so `registration`.

  `portabilitySuite(options)` registers the five cases and `judgment requested` as `boundarySuite` does (hosting/F31). The command takes `--applicability <file>`, a JSON file of the declarations; with it, it runs `portability` and prints the result on the same `kaal-hosting-boundary` line with the same exit codes, and without it, it is hosting/F31's command unchanged.
- **hosting/F41** [hosting/I10]: **The per-host review guide.** Hosting ships `skills/kaal-hosting-boundary/HOSTS.md`, pointed to from the Skill. A table between `<!-- kaal-hosting:hosts -->` markers gives, for each fact and each of `linux`, `darwin` and `win32`, whether it holds (`yes` or `no`) and an `https` link to the evidence. On each host, `facts()` agrees with that host's row, so every Hosting lane checks the guide. The guide then states the rules of hosting/F39, explains each applicability finding and the host-applicability request, says what a reviewer checks for each fact on each host, and escalates through PREACH when an agent's authority is not enough.
- **hosting/N6** [hosting/I10]: The audit is tested with positive and negative fixtures. Guard's negative sources are among them: a registration off one platform, a skip and a todo inside a case, an undeclared skip option and an unlisted platform reference. Each is found, and each case it decides is challenged by name. A portable guard/T114 is not. Each applicability rule has a declaration that must be found and a similar one that must not.
