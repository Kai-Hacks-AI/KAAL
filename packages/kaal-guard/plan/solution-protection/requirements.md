# Solution protection: Requirements

Each obligation names, in brackets, the Intent outcomes it serves. Numbers continue Guard's own (F up to 40, N up to 13).

## Functional

- **guard/F41 Registration beside the guarded thing.** [guard/I10] A folder registers its checks in `guard.json` beside it: `{ "checks": [ { "name": "test", "command": "npm test", "aggregates": ["solution"] } ] }`. `name` has no space or colon; the check's id is `<folder>/<name>` (`packages/kaal-controls/test`). `command` follows guard/F9 and runs in the folder that holds the file. `aggregates` lists the aggregates the check belongs to; a check may belong to several. Anything else in the file is refused as cannot judge, naming the file and the member.
- **guard/F42 Add-only from the base.** [guard/I11] The registrations the base holds are the baseline. The candidate's registrations are the baseline plus any it adds, and a pull request's own additions run in it. A candidate that removes a baseline registration, or changes its `command`, `aggregates` or folder, is cannot judge, naming the file and the check. There are exactly two exceptions, and nothing else lifts it. (a) The candidate's diff holds only registration files (`guard.json` and the aggregates file), so that it lands alone and reviewed, as guard/F7 already asks of a trusted declaration. (b) The suite no longer exists: the same diff deletes the `package.json` of that registration's folder. Deleting `guard.json` while the `package.json` stays, or removing its `test` script while it stays, is a removal of protection and stays cannot judge.
- **guard/F43 The aggregates file and the always list.** [guard/I10, guard/I11] `aggregates.json` in Guard's configuration directory (default `.kaal/config/guard`, the consumer's choice by `--config`) states, per aggregate, `always`, the check ids that must run in every run, and `exempt`, a map from a path to the reason it needs no registration. It is read from the base. A missing or unparseable file on the base is cannot judge, never empty. `aggregates` is valid only for the name `solution`; `change` and `delivery` are refused as not built yet.
- **guard/F44 Completeness: the package's own suite runs.** [guard/I10] Every `package.json` in the repository (outside `node_modules`) with a `test` script must be covered, and covered means that the package's actual suite is what runs. The folder holds a `guard.json` check that belongs to `solution` and whose `command` is `npm test` (or `npm run test`), so the command is the package's own `test` script and cannot be swapped for another command (`node -e 0`, `true`). Or the path is in `exempt` with a reason. Otherwise `plan` fails naming the folder, the check that does not run the suite, or the exact line to add. `plan` records the `test` script text it judged for each check, and `run` records the script it executed (guard/F46, guard/F48).
- **guard/F45 Plan.** [guard/I10] `kaal-guard plan --aggregate solution --run <id> --head <sha>` writes the expected set (always, plus every registration that belongs to the aggregate, from guard/F42), the CI matrix over it, the run id, the judged revision (`head`) and each check's `test` script text, as JSON. An empty expected set is cannot judge.
- **guard/F46 Fold.** [guard/I10, guard/I12] `kaal-guard fold --aggregate solution --plan <file> --reports <dir>` passes only when the set of checks that reported equals the expected set exactly and each one's report records success (guard/F2: pass, or not applicable shown as such, or held shown as held). Each report is bound to the current run and the judged revision: it carries the plan's run id, the judged `head` and the `test` script it executed, and a report whose run id, `head` or script differs from the plan's is stale or mismatched and fails, naming the check and the differing member. An absent report, an empty set, a report of anything else, and a report of a check nobody expected each fail, naming the check. It reads the per-check reports, not a count and not a job result. The pass rule is the same as release/C170's and is kept in one function so the two stay equal.
- **guard/F47 One name in both places.** [guard/I10] The workflow template runs `plan`, one job per check (named by its id) and `fold`, on `pull_request` and `merge_group`. The fold job's name is the only name a ruleset requires (`Solution protection`, provisional, to be confirmed with Release). A per-check job's name never equals a fold name, so it cannot be required by accident.
- **guard/F48 Report.** [guard/I12] `run --check <id> --run <id> --head <sha> --report <path>` writes the check's result, and `fold` writes the aggregate's, as `guard-report.json`: check id, aggregates, run id, judged `head`, the script executed, result, finding, fix hint, the registration file it came from, and for a fold the checks that decided it. A crash, a missing registration, an unparseable file and an unreadable list are written there too, never only to a log. The output and the CI step summary name the file.

## Nonfunctional

- **guard/N15 Honest exits.** [guard/I10] A check that did not run is never a pass: a command that cannot start, a crash of `plan`, `run` or `fold`, and a missing report each exit non-zero and are recorded.
- **guard/N16 Dumb and independent.** [guard/I10] `plan`, `run` and `fold` read exit statuses and reports only. They import nothing of Controls, Testing or Core, and take no mode.
- **guard/N17 Legacy stays out.** [guard/I11] A `.kaal/config/guard/<name>.md` declaration is never a member of an aggregate, and `aggregates` in one is refused.
