# controls/I12 cases test the criterion

A control states what it is for, and its Test Cases point back at it. The package can count that the Cases ran GREEN often enough and that a provoked failure was caught, but a Case can pass reliably on something nearby and a provoked failure can be a fixture, so a control could show Tested while its stated criterion is unproven. Every control can be verified and validated, whatever its type, and the two stay apart. A Test Case verifies it: a script's result, does the control do what it says. A review validates it: is what it says the right thing for its Intent, and do the Cases cover it. kaal-testing verifies any element and kaal-review validates any element, so the package keeps neither record: it checks what a script can check about the provoked run, says what a good review of a control must cover for each type, and reads the reviews that point at the control. A control report uses both edges.
