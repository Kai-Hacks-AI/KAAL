# controls/A17 judgement-beside-results

`scripts/evidence.mjs` keeps `judgeEvidence` and adds the `without` and `shows` rules to it, reporting `unnamed`, `unshown` and `boundaryUnnamed` in its verdict. It also exports `readSubjects(path)`, which reads the `subject.json` of every kaal-review application folder under a directory, and `reviewsOf(control, subjects)`, which returns the reviews whose `focus` is `control` and whose `subject` is the control id, each with `read` (`complete`, or `partial` with the Intents and Cases it did not name). It stores no validation and defines no review shape: the record is kaal-review's and the package only looks it up. A new reference `references/judging-criterion.md` says what a review of a control must cover, per type, for the criterion against the Cases and against the Intent; `SKILL.md` gains one pointer line within its 600 words. The control carries neither edge: a Case verifies it by pointing at it and a review validates it by pointing at it, and `judgeEvidence` and `reviewsOf` are the two lookups by control id that a report joins. The Skill's own files say a review record and name no other package, because the Skill stays standalone (controls/T777); this document and the Change name kaal-review. The scripts stay in the Skill's `scripts/` folder, know no repository path and need nothing beyond the foundation and the hosting. Where KAAL keeps its reviews of controls is for Engineering, and the `subject` field is for kaal-review to accept.
