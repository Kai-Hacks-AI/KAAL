# controls/F216 flag-in-the-run

1. `boundary` may carry `flag: {name, value}`: the name of the flag the adopter read and its value, `null` when the adopter read it and it is not set. The library reads no environment, repository variable or file; it is told. The flag state is `on` when `value` is exactly `'on'`, `off` for any other value including `null` and the empty string, and `UNKNOWN` when `flag` is missing or malformed (a `name` that is not a non-empty string, or a `value` that is neither a string nor `null`).
2. When the state is `off` the control still runs: the check is called once, and the verdict is the check's findings judged as a detective would, never blocked. The answer says `mode: 'off'` and `applied: false`, and the mode the caller asked for is kept beside it as `requested`. A check that throws still gives `UNKNOWN`, not blocked. The control is never skipped, so a switched-off control is a recorded run and silence is never a status.
3. When the state is `on` the control runs in the mode asked, as before, and `applied` is `true`. When the state is `UNKNOWN` the control runs in the mode asked, as before (the library does not guess a switch), and `applied` is `null`: the answer is never reported as applied or as off.
4. `log` gains `flag: {name, value, state}` with `state` of `on`, `off` or `UNKNOWN` (`name` and `value` are `null` when it is `UNKNOWN`), and its `mode` is the mode that ran. `record` gains `mode`, `applied` and the same `flag`. A record is still `null` when the boundary lacks `x`, `run` or `sha`. The other fields and their meaning do not change (controls/F203 items 4 and 5 are amended by adding these fields).
5. A flag never changes a verdict that was not asked for: the state `on` and a missing flag give the verdict of controls/F203, and nothing here lets a flag turn a FAIL into a PASS. The name `KAAL_<CAP>_<CONTROL>` and the rule that only `on` is live are the adopter's convention, not the library's.
