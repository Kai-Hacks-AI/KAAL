# controls/N8 skill-is-setup-agnostic

The Skill and its scripts know nothing of the KAAL repository. They name no KAAL path, scope, capability, id or folder layout, and work in any setup. Anything specific to a setup, such as the directory to check, comes in as input. The check is copied alone out of the repository and still runs on controls in any folder layout. The Skill also names no hosting term and no repository id form: it says "change under review" where it means the change a check judges (the term "pull request" belongs to a hosting adapter) and it shows no Change id such as `<capability>/C8`. The Skill may name the declaration it defines (`<capability>/CTL<n>` and the four DIRT values) and nothing of where a repository keeps them.

The Skill is also a package that works on its own. It depends on no other Skill or package, and in particular it does not point at the `kaal-testing` Skill. The only dependencies it may have are the foundation, for shared semantics, and the hosting, for OS-specific execution. Its own text says what it needs of verification, validation and a finding.

The scripts do no platform work of their own: no file system, process, operating system or line-ending code. What they judge comes in as text with `/`-separated, repository-relative paths, read by hosting. This holds for what the package publishes. A deprecated shim, a script that still reads files for a caller that has not moved yet, is named in `files` with a `!` entry, is not published, says `DEPRECATED shim` in its first lines, and is deleted when its callers are on hosting.

Engineering carries what is specific to KAAL: which folder it checks and where its migration note lives (controls/A11).
