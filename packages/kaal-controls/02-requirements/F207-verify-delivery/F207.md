# controls/F207 verify-delivery

1. `scripts/verify-delivery.mjs` exports `findUnrecorded({declarations, delivered, revision, scope})`, pure.
2. `declarations` and `delivered` are two inventories, each `{revision, scope, complete, entries}`, established independently of each other and of any declaration of what is delivered. `entries` of `declarations` are `{id, path}` of the controls declared; `entries` of `delivered` are the ids or paths found in the actual delivery. Discovery is the adopter's; the evidence contract, the shape above, is Controls'.
3. An inventory is usable only when `complete` is `true`, its `revision` is the applicable `revision` and its `scope` is the applicable `scope`. A failed, partial (`complete` not `true`), stale (another revision or scope), missing or malformed inventory makes the check throw, so that the adapter fails closed with `UNKNOWN`. `UNKNOWN` never passes and is never filtered by a ratchet allowance.
4. An empty inventory is clean only when completeness is established: an empty `delivered` with `complete: true` gives an empty answer, and an empty `delivered` with anything else throws. An empty `declarations` with a non-empty `delivered` names every delivered entry.
5. For every delivered entry that is neither the id nor the path of a declared control the finding is `unrecorded:<entry>`: confirmed nonconformance, the only finding, and the only name that can be baselined.
6. The answer is a sorted list of unique names. It reads no file and writes nothing, and knows no repository, path, flag or service. It stays detective and non-blocking; whether a finding blocks is GitHub configuration, and activation is a separate Owner decision.
