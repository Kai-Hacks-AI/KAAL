# controls/F214 wired-status

1. `scripts/judge-wired.mjs` exports `judgeWired({declared, installed, running, revision, scope})`, pure: it reads no file, runs no command and knows no repository, path, flag or service. `declared` and `installed` are two inventories `{revision, scope, complete, entries}` as in controls/F207: `declared.entries` are `{id, path?}` of the controls to report on, and `installed.entries` are the ids or paths the adopter observed installed in the delivery. `running` is a list of the ids whose running is proven for `revision`. `revision` and `scope` are non-empty strings.
2. For each declared control it gives one status: `code-only` when no installed entry is its id or its path, `wired` when one is and the control is in `running`, and `wired-unproven` when one is and the control is not in `running`. The answer is a list `{control, status}`, one entry for each declared control, sorted by control. An empty `declared` with a complete inventory gives an empty list. An installed entry that no control declares is ignored here.
3. An inventory is usable only when `complete` is `true`, its `revision` and `scope` are the applicable ones and `entries` is a list. A missing, malformed, partial, stale or other-scope inventory, a declaration without a text id or with a repeated id, an installed entry that is not text, a `running` that is not a list of text, a running id that no control declares, and a running id that is not observed installed make the judge throw, so that the adapter answers UNKNOWN for the whole report. No control is given a status from evidence that cannot be trusted.
4. It is a report, never a finding. `code-only` is not a nonconformance, nothing here is ratchet-eligible, and nothing blocks. It does not change its inputs.
5. The facts it reads stay independent: it takes installed and running as given and infers neither from the other. Whether a control is declared, implemented or tested is not decided here.
