# controls/F239 the first flags file is inert and advisory

Enduring requirement (Cases T1742 and T1743):

1. `engineering/14-operations/controls/flags.json` is a flag file of the library (`kaal-controls/flags@1`) that its own `parseFlags` accepts.
2. Every entry names a control whose record carries that exact id (capability and control: `release/CTL40` is not `core/CTL40`), and each control has one flag name in the convention `KAAL_<CAPABILITY>_<CONTROL>`, with the capability of the control.
3. Every value is one the library recognizes (`flagState`: `preventing` or `on`, `advisory` or `off`, `stopped`), so a later flip to `on` or `preventing` is accepted and a made-up value is refused. The value and the effective state are two facts: `on` and `preventing` are one effective state (PREVENTING), `off` and `advisory` another (ADVISORY).
4. `validateFlags` over the controls the file names, at the places it names, is ok.

Acceptance of C181 (evidence of that Change, not a permanent rule, so later entries, flips and WIREs do not break the suite):

5. The first file holds exactly eight entries: `release/CTL40` and `release/CTL41`, each at `Promoting`, `Collecting`, `Hotfixing` and `Wiring`, named `KAAL_RELEASE_VERIFY_PROMOTION_ORIGIN` and `KAAL_RELEASE_VERIFY_PROMOTION_HEAD_EVIDENCE`, all `advisory`, for controls declared preventive.
6. It is inert: at its DO no workflow or hook names it or supplies `KAAL_FLAGS`.

Another control, place, value or flip is a later Change, each on the Owner's decision.
