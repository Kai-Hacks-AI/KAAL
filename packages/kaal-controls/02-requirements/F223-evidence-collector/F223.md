# controls/F223 evidence-collector

Every control prints the same `kaal-control {json}` line through the controls library (the run record: `control`, `x`, `run`, `sha`, `verdict`, `by`). This requirement is the reader of those lines and the format of the ledger, so every control and every ratchet gets its evidence the same way. Release keeps only its counts.

1. `scripts/lib/collect-evidence.mjs` exports `parseControlLines(text)`, `collectEvidence({ control, situations, runs })` and `renderLedger({ title, situations, rows })`. Pure: it reads no file, runs no command, calls no service, does not wait and does not poll. It imports only `./contract.mjs`.
2. `parseControlLines` returns the records of the `kaal-control {json}` lines of a log, in order, and ignores every other line and a line whose JSON is not an object.
3. `situations` is a list of `{ name, kind, required }`: `kind` is `A` (agreement), `P` (provoked demonstration) or `N` (not applicable), `required` is a whole number, or `null` for `N`. Release declares them; the library fixes no count.
4. `runs` is a list of `{ run, situation, examined, lines, old, provoked, expect }`. The caller states `examined`, the identity of the content the check examined, from Hosting; what triggered the run is not a concept of the library; `lines` is the log text; `old` is `{ conclusion, identity }` of the old check or null, where `conclusion` is `success` or `failure`, what a job gives. The library maps it: `success` is `PASS`, `failure` is `REPORT` or `FAIL`, whichever the control's mode emits. `collectEvidence` gives one row per run, in order: `{ run, situation, identity, kind, verdict, reason }`, with `kind` `V`, `A`, `P` or `null`. V is a valid verdict record of the examined content that is not an agreement; A and P are the counted kinds. A row counts only when its kind is `A` or `P`. The verdict of a row is the verdict on the record's line, never the conclusion of the job that printed it (a job that reports still ends green).
5. The rule of a row, applied in this order:
   - `situation` is not declared: no kind, reason `unknown-situation`. Its kind is `N`: reason `not-required`.
   - `examined` is not an identity (controls/F218): reason `examined-identity-missing`.
   - No record of the control in the log: `no-record`. Records of the control that give different verdicts: `contradictory-records`.
   - The record's `sha` is not an identity: `recorded-identity-missing`. It is another identity than `examined` (for instance the merge commit of a pull request run, release/D20, when the head was examined): `recorded-not-examined`. This is the identity check of testing/C84, applied through the contract.
   - The record's verdict is `UNKNOWN` or not one of the verdicts of controls/F218: reason `unknown-verdict`, not counted, and the row is in `defects`. UNKNOWN is never an A and never a P, also when the old check failed and also when both sides are unknown.
   - A provoked run whose verdict is the `expect`ed one (`FAIL` by default) is a `P`, reason `provoked-as-expected`, and the run id goes to `defects` otherwise (`provoked-not-expected`, not counted).
   - Any other run is an `A` only when `old` is on the same identity and its conclusion maps to the record's verdict (reason `agrees`). `old` on the same identity with the other conclusion is not counted, reason `disagrees`, and the run id goes to `disagreements`. `old` null or on another identity is not an A and not a disagreement: the row is a `V`, reason `old-not-run-on-identity`.
   - One identity counts once per control and situation: a second counting row of the same situation and identity is not counted, reason `duplicate`.
6. The answer is `{ rows, counts, met, disagreements, defects }`: `counts` the counting rows per situation, `met` whether the count reaches `required` (an `N` situation is always met), and the lists of run ids. A disagreement blocks enforcement until the Owner decides it; the library only lists it (release/C153).
7. `renderLedger` returns Markdown in the format of release's evidence files: a "Count" table (`Situation`, `Kind`, `Required`, `Counting`), a "Counted" table of counting rows and an "Inspected and disqualified" table of the others with their reason. The text is built from the rows only.
8. What is not here: reading the runs (their logs and the old check's result) is Hosting's; running the collector on each completed check run as an event is a WIRE of Release's, on the Owner's go; the swap criteria, meaning how many A, P and N each check needs, stay Release's. Testing owns the meaning of evidence integrity; the check in item 5 applies it and does not redefine it.
9. The call is per control: one run holds several jobs and controls, so the caller calls `collectEvidence` once per control and run. How the counts of several controls make the count of a check (the least of them, not the sum) is Release's. A check whose evidence writes no `kaal-control` record (admission, merge group) is not read by this function: Release keeps those counts apart, and the function does not take a run without a record as evidence.
