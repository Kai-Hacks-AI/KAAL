# controls/F209 demand-record

1. `scripts/demand-record.mjs` exports `findRecordDue({discrepancies, unknown, owners, pr, timing, observed, revision})`, pure. It judges **timing only**: when a correction is due. It makes no status comparison and no judgement of correctness; `discrepancies` and `unknown` are the answer of `assessRecord` (C144), the names `<fact>:lags:<id>` and `<fact>:overclaims:<id>`, and the unknown list `<fact>:<id>`.
2. `owners` maps a control id to the owning capability. `pr` is `{capability}`: the capability whose pull request is judged. `timing` is the list of `{control, fact, revision, followsEvidence}`: for each control and each fact, whether the judged pull request follows the installation and the applicable evidence of that fact at that revision (`true` or `false`, established independently by the adopter from the history and correlated to the judged pull request and revision; the mechanism is the CTO's). Controls and facts acquire their evidence at different times, so applicability is per control and per fact, never one value for the whole pull request. The **owning capability's next applicable pull request** is one with `pr.capability` equal to the owner: an unrelated capability's pull request is never applicable and nothing is due on it.
3. `observed` is the list of `{control, revision, installed, operationalEvidence, testing}` for the applicable `revision`: whether the control is observed installed in the actual delivery, whether operational evidence exists, and whether the `tested` fact rests on `pre` (before a WIRE) or `operational` testing. Pre-WIRE facts are `defined`, `implemented` and pre-installation `tested`. Post-WIRE facts are `running` and operational `tested`.
4. On an applicable pull request every discrepancy is due, `record-due:<fact>:<direction>:<id>`, except one: a `lags` of a post-WIRE fact is not yet due unless the control is observed installed, its operational evidence exists and the `timing` entry of that control and fact has `followsEvidence` `true`. Timing is relative to installation and to the evidence, not installation alone, and an early pull request, before them, is not due. An `overclaims` is a false claim and is never deferred because the control is not installed.
5. Unknown evidence is never turned into clean. A non-empty `unknown` for a control owned by `pr.capability`, an applicable pull request with no `timing` entry for a discrepancy's control, fact and revision, or one whose `followsEvidence` is not a boolean, a control with no owner or no observation for the revision (or one of another revision), a malformed discrepancy name, or any malformed input makes the check throw, so the adapter fails closed with `UNKNOWN`, never passing and never filtered by an allowance. Only a confirmed `record-due` can be baselined.
6. The answer is a sorted list of unique names, empty only when nothing is due and nothing is unknown. It reads no file and writes nothing, and knows no repository, path, flag or service. It stays detective and non-blocking; activation is a separate Owner decision, and the mechanism that finds the pull request is the CTO's.
