# controls/C24 one ratchet library and a mandatory baseline file

Two ratchets exist (release CTL20 and CTL36). Each derives its baseline its own way: CTL36 reads `baseline.json`, CTL20 computes it in code and has no file. A third ratchet would invent a third way. This Change makes the shape of a ratchet the same everywhere and puts the shared part in one library that every ratchet, in KAAL Engineering, Embed and External alike, uses.

1. **One library.** `skills/kaal-controls/scripts/ratchet.mjs`: pure, no file, Git or network access. `judgeRun({findings, baseline, previous})` is the comparison of C21 and C22 (what `judge-mode --mode ratchet` does today); `judge-mode.mjs` calls it, so its behaviour and its Cases do not change. The caller reads the files and the Git data and passes values in. The library sits in the Skill, so it works in a consumer that knows nothing about KAAL.
2. **The baseline is a file, and it is mandatory.** A control with `strategy: ratchet` names in `baseline-source` the path of a JSON file that lists finding names (a list of strings, each once). The finder lists the control with a problem when the value is not such a path, the file is not among the files it reads, or it is not a list of unique strings. The accepted baseline is read as Git data of the base, never from the pull request (the C22 rule); this stays the caller's, and the Skill says so.
3. **Out of scope:** the history of a baseline (C25), the adoption in CTL20 and CTL36 (release), any deadline.

## Answers for release (its question of 24 November)

- Entry point: `judgeRun` takes arrays of names (`findings`, `baseline`, `previous`) and returns the verdict of C21. It takes no path and no ref: the judge reads the base's `baseline.json` as Git data and passes the list.
- CTL20 gets a `baseline.json` listing its five workflows; its judge reads the base's file instead of deriving the baseline in code (release's PLAN).
