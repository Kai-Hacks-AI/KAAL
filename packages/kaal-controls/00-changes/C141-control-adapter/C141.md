# controls/C141 every control runs through one thin adapter that leaves the evidence from which its record is derived, and a check finds a control that is not registered correctly

Asked for by Kai after release found that five Act controls still record `status: designed` although they are installed and have run. The record lags reality, and nothing says so. This Change states the concept and its limits. It builds on the ratchet library (C24, C25) and the evidence of a `tested` claim (the existing `evidence.mjs`).

## The concept

A control is a pure check plus a declaration. The **adapter** is the one thin function between the two and the world. A control does not apply a mode, read a baseline, decide what to do when it could not judge, log or write evidence by itself. The adapter does, for every control, and only these five things:

1. **Mode.** It applies the mode the caller resolved (detective, preventive or ratchet) to the findings, through the existing `judgeMode`. Which flag or ruleset chose the mode is the adopter's.
2. **The ratchet filter.** In ratchet mode it applies the allowance (C24) and takes the base's baseline as given, never from the change under review.
3. **Fail closed.** A check that throws, or returns something that is not a list of names, is `UNKNOWN`, and `UNKNOWN` never passes.
4. **The log.** One structured line per run: control, mode, verdict, number of findings, run, revision.
5. **The record.** One record of the run: `{control, x, run, sha, verdict, by}`, `by` being `adapter`. It is the line that shows the control ran, on which kind of X (a fixture, a real pull request, a provoked failure), and with what result. A run that cannot say its `run` and `sha` produces no record.

The checks stay pure. The adapter reads no file and calls no service: the caller passes values in and gets the verdict, the log line and the record out. The adapter stays thin by a rule: it carries a concern only when every control needs it and it can be stated in one sentence. A concern that one control needs stays in that control.

## Where the evidence lives and how the record is derived

Judges read files only, and CI must not push. So the adapter writes nothing into Git. A run prints its record, and the record is committed as a line in `records.jsonl` beside the control, by the Change that claims the status the evidence supports, as the history of a ratchet is written by the pull request that shrinks it (C25). Records only grow. A pull request that raises a status cites the record lines that show it, and a judge reads them with the control. The record file is the evidence; the `status` in the declaration is the claim; the status **derived** from the evidence is a third thing and is only computed, never written by a script.

- `designed`: the declaration is valid (as today).
- `implemented`: not derived. Only an observation shows it, as `judging-status.md` says.
- `running`: at least one record of an adapter run on a boundary of the real kind, with a verdict other than `UNKNOWN`. A result the mechanism produced on its boundary is what the Skill already says shows running.
- `tested`: the existing `evidence.mjs` verdict on the Cases of the control, unchanged.

A record lags when the derived status is higher than the claim. A record overclaims when the claim is `running` or `tested` and the evidence shows less. A script never edits a claim: the finding names the status the evidence supports and the Change that owns the control writes it.

An honest limit: a record is a recorded claim that a run happened. Whether the run really exists (its id in the CI service, its revision in Git) is checked by whoever holds that service, not by this judge, which sees the lines. That is one open point below.

## What CI finds

A pure judge, `judgeRegistration`, reads the controls found in a place, what the adopter says is delivered, which controls run through the adapter, and the records, and lists findings by name:

- `unadapted:<control>`: a control that is declared with a station, or delivered, and does not run through the adapter.
- `unrecorded:<path>`: something is delivered and no control declares it.
- `record-lags:<control>` and `overclaims:<control>`.

It is a check like any other, so it follows the protocol and the existing library, with no new mechanism:

1. **Detective.** It reports. It blocks nothing.
2. **Ratchet.** The controls that exist today are not adapted. Their names form the baseline of a ratchet (C24), with a history (C25): the check blocks a new control that is not registered correctly and lets the old ones through until release migrates them one at a time. The ratchet ends at zero.
3. **Preventive.** Only after Kai's go, and only with the provoked-fail evidence the existing protocol asks for: a control the check let through, then the check turning RED on it.

## Where a stale record blocks

Kai agreed the place: a record that lags is stopped on a pull request that is relevant to it, and forces the update there. Records are written only by a normal Change of the capability that owns the control, never by a WIRE and never by CI. A WIRE may not write package files, and CI must not push. There are three places, each a pure judgment over the same findings (`judgeDue`), each wired by release as a station and each following the protocol: detective first, preventive only on Kai's go with provoked-fail evidence.

1. **Installed.** A control becomes installed by a WIRE, and the WIRE cannot update the record. So the record is due on the owning capability's next pull request. The check on a pull request into that capability's collector finds `record-due:<control>` for a control the adopter says is installed and whose claim is still `designed`, and blocks it until the Change updates the record.
2. **Running and tested.** A pull request that raises a control's mode (the flag is turned on, or the control becomes preventive) must carry the evidence in the same Change: to switch a control on, an adapter record that shows it ran, with a verdict other than `UNKNOWN`; to make it preventive, the evidence a `tested` claim needs. Otherwise it finds `evidence-due:<control>` and blocks. This is the place where the protocol's step from detective to preventive is checked.
3. **Backstop.** A promotion into main finds `record-lags:<control>` and `overclaims:<control>` over every control, and blocks if there is any, so a record that slipped past the first two places is stopped before it reaches main.

The adopter says which controls are installed and which mode each has (the flag and the ruleset are its own), and passes them in. The judge reads values.

## Not here

Migrating the Act controls onto the adapter and wiring the check as a required check are release's, after this Change. Where delivery is declared, how a run is known to exist, how the flag for the advisory step is named, and the ruleset belong to release, hosting and the Owner. Nothing is implemented before the Owner's go on this PLAN.
