# controls/C145 demand Record finds that the record of an installed control is due on the next pull request of the capability that owns it

One small control with one property, built on the library of controls/C141 (the adapter and `deriveStatus`). Asked for by Kai: small, meaningful controls, each following the change protocol until it blocks.

**The control.** `controls/CTL4`, `demand Record`, type detective, status designed. For every control whose id is in `installed` and whose claim is `designed`, the finding is `record-due:<id>`. A claim of `implemented` or higher is not due. `installed` is what the adopter says is installed, because installing is a WIRE, which cannot write package files; the record is therefore due on the owning capability's next pull request into its collector.

**The check.** `scripts/demand-record.mjs` exports `findRecordDue({controls, installed})`, pure. It returns a sorted list of unique names, empty when nothing is found, and throws on an input that is not a list, so the adapter fails closed with `UNKNOWN`. It reads no file and knows no repository.

**The rollout, by the change protocol.**
1. **Detective.** The check reports through the adapter and blocks nothing.
2. **Advisory.** The adopter runs it as an advisory check behind its own flag, and evidence is collected: Cases on fixtures, real runs on pull requests, and a provoked failure.
3. **Preventive.** Only on the Owner's explicit go, and only with the provoked-fail evidence the protocol asks for.

## Not here

Wiring the control as a station or a required check, the flag, the ruleset, and migrating the controls it finds are release's. Nothing is implemented before the Owner's go on this PLAN.
