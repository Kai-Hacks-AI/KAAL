# controls/C29 an accepted failure stays FAIL, flagged ACCEPTED, and permits delivery only for itself

Follow-up to C27 (CARE), asked for by the CPO: C27 stops at a complete decision record. C29 states what a decision does to a control's report and to delivery, without hiding a failure.

**The relation.** A finding is a transient observation, not an artefact. When Review finds it valid, it becomes a **Test Case** (the property that fails) and a **Defect** (the gap). Those two are the persistent things. A control's report cites the failing Test Cases. Nothing else about a finding is stored.

**Reporting.** An accepted failing control stays **FAIL** in the control report. It is flagged **ACCEPTED** only when every Test Case it fails is covered by an acceptance. It is never reported as PASS, and the acceptance does not change the control's result.

**Acceptance.** An acceptance is one entry in an acceptance list, naming the control, the failing Test Case it covers, the Defect, an owner and a reason. It covers exactly that control and that Test Case.

**Delivery.** A separate verdict, `judgeAcceptance`, reads the control results and the acceptance list and answers `PERMIT` only when every non-passing control is a FAIL whose failing Test Cases are all covered. A failure no acceptance names, a different Test Case, an UNKNOWN result and a control without a cited Test Case all make it `BLOCK`. A new or different failure never inherits an acceptance. An acceptance that matches no failure is listed as unused and does not block.

**The Skill.** `references/acceptance.md` teaches this in setup-agnostic words, and `SKILL.md` gains one pointer line within its 600 words.

## Not here

Where the acceptance list is stored, who may add to it, how CI calls the verdict, the ruleset or required check that enforces it, and any change to the report format of a particular station belong to release and the Owner. The check is pure and activates nothing. See `change.md`.
