# controls/C25 a ratchet keeps its history in git

Ratchet progress is a fact over time. Today a baseline only shows its size now; nothing records when it shrank or which Change delivered the reduction. This Change makes the history part of the ratchet, written in git by the pull request that shrinks the scope, and judged by the same library as the comparison (C24).

1. **A history file beside the baseline.** `history.jsonl` in the folder of the baseline file, append only, one JSON object per line. A ratchet has one (it starts with the line of adoption).
2. **The line.** `{"at":"2026-11-24T09:00Z","change":"release/C131","from":5,"to":4,"removed":["ci.yml:generic-name"]}`. `at` is UTC to the minute, `change` the id of the Change that delivers the reduction, `from` and `to` the sizes of the baseline, `removed` the names that left it, sorted. The adoption line is `{"at":...,"change":...,"from":null,"to":5,"removed":[]}`.
3. **The pull request writes it, the library judges it.** The pull request that lowers the baseline appends exactly one line in the same change. `judgeProgress({base:{baseline,history}, head:{baseline,history}, change:{id, exists}, window:{from,to}})` in `ratchet.mjs` says PASS, FAIL with a reason, or UNKNOWN when an input is missing. It takes values only: the caller reads `base` as Git data of the base and `head` from the merge result.
4. **What it checks.** A baseline of the same content adds no line. A baseline that shrank adds exactly one line whose `from`, `to` and `removed` match the two baselines. The earlier lines are unchanged (the base's history is a prefix of the head's). `change` is the Change the pull request carries (the caller passes its id and whether its folder exists in the head tree). `at` is not before the last earlier line and lies inside the window the caller passes: from the time of the base commit to the time of the head commit. A baseline that grew fails as in C22.
5. **The report reads the file.** Count now, the series over time and the exit (`to` is 0) come from `history.jsonl` on main. The report is a later Change.

## How a pull request records its time and its Change reliably

- **Change pointer.** The pull request names its Change in the line; the judge checks it is the Change the pull request carries (isolated by Change Isolation) and that its folder exists in the head tree. The merge commit's PR number is not known to the pull request and is not asked for: the merge commit is found from the Change id and the file's `git log`.
- **Timestamp.** A pull request cannot know its merge time, so `at` is the author's declaration, held inside the window `[base commit time, head commit time]` and never before the last line. It is a claim bounded by two Git facts, not a measurement; the report may show the committer date of the line's commit beside it (Git data, read-only). A line that fails the window is rejected, so a wrong time cannot be earlier than the base or later than the head.

## Left open (for the CPO, with a recommendation)

- Adoption line `from: null` (recommended) or `from: 0`.
- A `step` field (`DO`) and a `note`: recommended not now, the Change id already says it.
- Window from the commit times of the base and the head (recommended), or from the two commits' author dates. The caller supplies it; the library compares text.
- Whether the PR number also goes in the line (needs a second push after opening; recommended not).
- Ids G102, F39, T1120 are taken by hand; on a clash the newer pull request renumbers.
- Depends on C24 (`ratchet.mjs`, the baseline file). The DO waits for C24's DO; release adopts it in CTL20 and CTL36 (its own PLAN).
