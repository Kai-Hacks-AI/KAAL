# Pull Promotion: host-neutral gathering of stock items and consumption of their OUT verdict (target)

Scoped `pull/` (ids are global). Nothing of pull/F25 to F49 is relaxed. Everything is advisory and read-only. The package implements neither stock readiness nor destination admission, and knows no installation convention. The transaction is stock item, OUT ready, destination pull, destination IN, merge. OUT precedes the pull; IN follows it.

- **pull/F50. The package turns normalized stock items into the deliveries `laneStep` takes.** `resolveDeliveries(facts)` in `scripts/deliveries.mjs` takes `facts.classes` (declared delivery classes), `facts.candidates` (stock items `{id, class, name, revision, stock}`), `facts.authorities`, `facts.verdicts` and `facts.registrations`. An item whose class is not declared is ignored and reported as a finding. Each delivery is `{class, source, name, revision, out, in, ready, pull}` with `source` the item id, opaque to the package. No `value`, `size` or `unit` is produced. Facts that are missing or not lists give no deliveries and a finding, never a guess, and the input is not changed. The package never creates a stock inventory: it lists only the items it is given.
- **pull/F51. OUT is a consumed verdict, never a computed one, and it alone makes an item ready.** `out` is decided only from `facts.verdicts` (`{candidate, side, verdict, revision, authority}`): `PASS` when a verdict for side `out` is `PASS` with `revision` equal to the item's `revision` and `authority` equal to the one `facts.authorities[class].out` registers; `FAIL` for a `FAIL` with that revision and authority; `UNKNOWN` for everything else (no verdict, another revision, another or unregistered authority, `held`, any unrecognised value). `ready` is true exactly when `out` is `PASS`. The package reads nothing behind a verdict, so verdicts for different classes with differently shaped evidence give the same result, and an item is `ready` with no IN verdict at all.
- **pull/F52. IN belongs to the destination and follows the pull; it never gates selection.** `in` is the verdict of side `in` at the item's exact revision from `facts.authorities[class].in`, as `PASS`, `FAIL` or `UNKNOWN` under the same rules as F51, and `null` when no such verdict exists (the delivery PR has not been created or evaluated). `in` never changes `ready`, never removes an item from `deliveries` and never makes one `ready`: a `FAIL` is reported on a still-listed item and blocks completion, not discovery. The host adapter derives an IN verdict only once a pull request into `main` exists at that exact revision, from the checks `main` actually requires (`PASS` when every required context completed `success` at that revision, `FAIL` when one failed, otherwise `UNKNOWN`, and `UNKNOWN` when the required checks cannot be read). It holds no list of IN checks.
- **pull/F53. The adapter discovers stock items from registered stock, and reads by GET calls only.** The adapter (`engineering/release-management/05-src/pull-promotion/gather.mjs`) lists the uniquely named branches of the registered stocks and maps them to the declared classes using the class routes of `kaal-pull.json` read from `main` (never a literal prefix). A head outside a registered stock is not an item, and an issue or a PR is never one. Its reader uses only read requests to list heads, pull requests into `main`, check runs and the checks `main` requires; it sends nothing that creates, updates, merges, approves, comments or dispatches. A request that fails or is paged out leaves what it could not read UNKNOWN, never PASS.
- **pull/F54. The package is host-neutral.** The same unmodified `scripts/deliveries.mjs` gives correct results for a different host, naming and source representation (items that are not Git branches, other class names, other revision forms), and its source contains none of `kaal/`, `hotfix/`, `wire/`, `github`, `branch`, `.kaal` or a file or network access.
- **pull/F55. Auto-pull is opt-in at stock level, judge-pull is surfaced.** A delivery is `pull: 'auto'` only when its item's `stock` is in `facts.registrations` (accepted registrations); every other item is `pull: 'judge'` and is still returned, never dropped and never silently auto-eligible. Registration decides only the mode; it never turns an `out` or `in` into `PASS`, and nothing in the result approves or merges.
