# Pull Promotion: host-neutral gathering and consumption of the delivery verdicts (target)

Scoped `pull/` (ids are global). Nothing of pull/F25 to F49 is relaxed. Everything is advisory and read-only. The package implements neither stock readiness nor destination admission, and knows no installation convention.

- **pull/F50. The package turns normalized candidates into the deliveries `laneStep` takes.** `resolveDeliveries(facts)` in `scripts/deliveries.mjs` takes `facts.classes` (declared delivery classes), `facts.candidates` (`{id, class, name, revision, owner}`), `facts.authorities`, `facts.verdicts` and `facts.registrations`. A candidate whose class is not declared is ignored and reported as a finding. Each delivery is `{class, source, name, revision, out, in, pull}` with `source` the candidate id, opaque to the package. No `value`, `size` or `unit` is produced. Facts that are missing or not lists give no deliveries and a finding, never a guess, and the input is not changed.
- **pull/F51. OUT and IN are consumed verdicts, never computed ones.** For each side, the verdict is decided only from `facts.verdicts`, a list of `{candidate, side, verdict, revision, authority}`: `PASS` when the verdict is `PASS` with `revision` equal to the candidate's `revision` and `authority` equal to the one `facts.authorities[class][side]` registers; `FAIL` for a `FAIL` with that revision and authority; `UNKNOWN` for everything else (no verdict, another revision, another or unregistered authority, `held`, any unrecognised value). The package reads nothing behind a verdict, so verdicts for different classes with differently shaped evidence give the same result.
- **pull/F52. The host adapter normalizes GitHub into those facts, and IN is the destination's own result.** The adapter (`engineering/release-management/05-src/pull-promotion/gather.mjs`) maps this installation's branch naming to the declared classes, builds the candidates, and derives the IN verdict from the pull request into `main` whose head is the candidate's revision and from the checks `main` actually requires: `PASS` when every required context completed `success` at that revision, `FAIL` when one failed, otherwise `UNKNOWN`; no PR at that revision, or required checks that cannot be read, is `UNKNOWN`. No list of IN checks is held by the adapter or the declaration. A head outside the installation's naming is not a candidate.
- **pull/F53. Facts are read by GET calls only.** The adapter's reader uses only read requests to list heads, pull requests into `main`, check runs and the checks `main` requires. It sends nothing that creates, updates, merges, approves, comments or dispatches. A request that fails or is paged out leaves what it could not read UNKNOWN, never PASS.
- **pull/F54. The package is host-neutral.** The same unmodified `scripts/deliveries.mjs` gives correct results for a different host, candidate naming and source representation (candidates that are not Git branches, other class names, other revision forms), and its source contains none of `kaal/`, `hotfix/`, `wire/`, `github`, `branch`, `.kaal` or a file or network access.
- **pull/F55. Auto-pull is opt-in, judge-pull is surfaced.** A delivery is `pull: 'auto'` only when its candidate's `owner` is in `facts.registrations` (accepted registrations); every other candidate is `pull: 'judge'` and is still returned, never dropped and never silently auto-eligible. Registration decides only the mode; it never turns an `out` or `in` into `PASS`, and nothing in the result approves or merges.
