# Pull Promotion host integration: Requirements (target)

Scoped `pull/` (ids are global). It integrates `pull/C1` with the host (it does not wire it to a trigger: that is a separate, future Change); the Script's own requirements are `pull/F1` to `pull/F13` and `pull/N1` to `pull/N3`. It is a separate Change on its own collector and depends on `pull/C1`: it borrows neither its ACT nor its completion evidence.

Three things are kept apart (CPO, 12 Nov 2026): the **execution environment** (where the command runs), the **authentication** (what it may read with) and the **decision authority** (who authorizes promotion). The Owner authorizes promotion; the Owner is not the test runner.

- **pull/F14. The connected path.** In the consumer's Delivery (for KAAL, `engineering/release-management/05-src/pull-promotion/`), `run.mjs <repo> <declaration file> <collector> [--audit <file>]` obtains the observations from the shared GitHub observer (the reader and normalizer of the host-observation contract, [decomposition.md](decomposition.md) E1 and E2), passes them with the declaration to `pull-promotion.mjs` and prints the verdict. It imports nothing of Analyze Flow, neither its Script nor its supplier, and holds no host mapping of its own. The KAAL declaration (`declaration.json`: owners, lifecycle, explicit dependencies, legacy records, check owners, holds) is reviewed like any other PR.
- **pull/F15. Portable execution and explicit authentication.** The command runs unchanged on any appropriately provisioned runner: a person's machine, a CI job or an agent session. It needs Node and exactly one supported credential, named explicitly: (a) a token in `GH_TOKEN` or `GITHUB_TOKEN` carrying only read permissions (contents, pull requests, checks, actions), or (b) an already signed-in `gh`. It reads no other environment and fails naming the missing or insufficient credential. Provisioning a read-only credential is the preventive control of the read-only claim; the evidence of F16 is detective.
- **pull/F16. Read-only, with a stated observation boundary.** All host access goes through one reader. With `--audit <file>` the command writes one JSON line per host request (method, endpoint, and for a query the operation kind) and closes the file with one `context` line (collector, collector head as read, credential kind, runner kind, time). The claim and what proves it:
  - *Proved by the audit:* every request the command issued through the reader is a read (HTTP GET, or a GraphQL query with no mutation); no request goes to any other host.
  - *Proved by the state comparison:* the audits and the snapshots cover every invocation of the command in the acceptance run, not a selection of them. A defined snapshot of host state (all open pull requests with their state, draft, auto-merge, head, base, labels, assignees, reviewers and merge state; every branch and its head; the repository's merge and auto-merge settings; its rulesets where readable) is identical before the first invocation and after the last, taken from the same credential, on a host that was otherwise quiet. A difference fails the Case and is investigated; a run on a busy host is rerun, not excused.
  - *Not proved:* mutations outside that snapshot (issues, comments, releases, secrets and anything else), a command that bypasses the reader (T1 forbids network and process APIs in the Script; the adapter is checked the same way for everything but the reader), or an adversarial adapter. The threat is an accidental mutation by the adapter, not a malicious one.
- **pull/F17. Acceptance evidence is collected first and certified after, tied to an exact head and host state.** Two separate steps, never one. *Collection:* every invocation of the command in the acceptance run writes its own closed audit, and the final snapshot of F16 is taken after the last invocation. *Certification:* only then `certify.mjs --head <sha> --snapshot <file> --baseline <file> --audit <file>...` runs over that completed evidence. It reads files only, issues no host request and is not an invocation of the adapter, so it cannot be part of the evidence it certifies. It refuses (non-zero, naming why) when an audit is unreadable or empty of requests, any audit holds a request that is not a read, or the final snapshot differs from the baseline. It emits the record: the implementation head given (the commit of the checkout that ran), the collector and its head, credential kind (never its value) and runner kind as closed in the audits, the digest of the final snapshot, the digest of the audits read, the count of audits (invocations), and the time. The record is attached to the DO, against the head it was produced for; a later head needs a new record.
- **pull/F18. Read-only contract holds for both runners.** The Case is the same on a person's machine, in CI and in an agent session; there is no step that requires the Owner's device.
- **pull/F20. Not a trigger.** The command is invoked by a person or an agent and by nothing else. No Git hook, CI workflow, scheduled job, required check, ruleset or Guard references `pull-promotion` or its `run.mjs`, and none is added; connecting the command to such a trigger is a separate wiring Change with its own PLAN. The command takes its observations from the shared observer by importing it, imports nothing of Analyze Flow, and holds no copy of any host mapping.
