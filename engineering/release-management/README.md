# Release management (Engineering)

The root holds the full loop for how a package moves from a working branch out to the world. The stations below it repeat the same loop, one station at a time. Each station has **in** (the receiver's check), **stock** (what holds while work sits at the station) and **out** (the sender's check), so what is out of one station and what is in to the next may be different controls.

| Folder | What it is |
| --- | --- |
| `01-intent/` to `04-test/` | the overarching view of the root: Intent, Requirements, Architecture (the flow drawing), Cases. They describe the target only (B). |
| `05-src/` | components (architecture elements), all peers, named by what the code is (`lineage/`, `release-engine/`, `lanes/`, ...); no station folders |
| `00-changes/` | the Change (A to B): the present state, the gaps, the route from the present controls to these, the temporary mechanisms with their ends, and the evidence that the target is reached. It references the target by id and never restates it. |

Layout (Owner, 9 Nov): the folder is only the root loop, `00-changes` to `06-defects`, and it is traced as an element of the Delivery architecture (Delivery vs Solution placement). `05-src/` holds components, all peers, each an element of the architecture with no loose files. Controls are matters of concern, traced through the root documents (Intent entry, requirement, allocation, Cases, Defects where any); a component carries its own Intent, Requirements and Cases only when it moves. The station is the control target, a separate attribute recorded as a traced edge in `03-architecture` and not a folder; its workflow is named by the process step, `KAAL / release / <step>` (`integrate`, `promote`, `publish`) (the target `collectors` is named so it is not confused with KAAL as a whole). A control may be realized by a native setting or a tool and have no component; a component may realize several controls. A component uses another only through a declared `uses` edge. The name follows Domain-Driven Design, with release-management as the bounded context. Source-code tests always sit next to the code in its component; the root only traces them. Station `13-change-branch` is not part of this architecture (Owner, 9 Nov).

The names are the Owner's (agreed 9 Nov 2026). Solution and Delivery describe the target (B); Change describes the transformation from the present to it (A to B) and owns the present state, the gaps, the sequence, the temporary mechanisms and the evidence that B is reached. Both kinds of documentation are needed to succeed, and keeping each clean helps agents to deliver (Owner, 9 Nov).
