# C129 change

## PLAN

Two controls, two judges, one shared pure layer and one reader. Nothing here installs a workflow, sets a flag or changes a ruleset. The workflow is engineering's (`engineering/C32`); this Change is the two commands its jobs call. Release owns the control judgments, engineering owns the workflow source.

### Decisions (the approval of this pull request is the go for the DO)

1. **Two controls, not one.** `release/CTL34 verify CodeQL analysis` (Intent release/I68) answers whether every expected configuration has an analysis of the merge-result sha without an error. `release/CTL35 verify CodeQL findings` (Intent release/I69) answers whether an open alert on the merge ref is at or above the threshold. Each has its own command, findings file, verdict, evidence and record, so each can be assessed, registered, improved and enforced alone. The workflow may run them as two jobs (recommended, so a ruleset can name them one by one) or as two steps; that is engineering's decision.
2. **The commands.** `node 05-src/codeql-gate/judge-codeql-analysis.mjs --out <findings.json>` and `node 05-src/codeql-gate/judge-codeql-findings.mjs --out <findings.json>`. Both take everything else from the environment of the job, so no argument can name another sha: `GITHUB_REPOSITORY`, `GITHUB_SHA`, `GITHUB_REF`, `GITHUB_TOKEN` (`security-events: read`), `CODEQL_EXPECTED` (one quoted, space-separated string of `/language:<name>`, as engineering's F93 pins), `CODEQL_ANALYZE_RESULT` (`needs.analyze.result`). The findings judge also takes `CODEQL_SECURITY_ALERTS_THRESHOLD` and `CODEQL_ALERTS_THRESHOLD`. Optional `CODEQL_WAIT_SECONDS` (600) and `CODEQL_POLL_SECONDS` (30). The sha and ref are never read from the head of the pull request or the event payload.
3. **What each writes.** A sorted JSON list of finding names in `--out`, and no verdict: the verdict is kaal-controls' `judge-mode.mjs --mode preventive --findings <file>` (exit 0 PASS, 1 FAIL, 2 UNKNOWN; a missing, unreadable or malformed findings file is UNKNOWN; read from `kaal/controls/control-modes`, controls C22). The analysis judge names `missing:<category>` and `errored:<category>`. The findings judge names `alert:<number>`. Neither names the other's findings.
4. **UNKNOWN is the absence of the file.** An API error, an unreadable response, an unset input, an unknown threshold value, or an analysis still absent when the wait ends exits 2, writes no file and removes a stale one. The reason goes to stderr. No code of ours decides the verdict.
5. **The wait depends on what is known.** If `CODEQL_ANALYZE_RESULT` is not `success`, an analysis did not complete and none will arrive: the analysis judge reads once and names what is missing, with no wait. If it is `success`, each expected analysis should arrive: both judges poll every 30 seconds up to 10 minutes (engineering C32, question 3), and the end of the budget is UNKNOWN, not `missing`, because a late upload is the failure of #2313 and a script cannot tell lateness from absence. The findings judge needs the analyses of the sha to trust the alert set: when an expected analysis is absent it is UNKNOWN (it cannot tell), not a finding and not clean. Time and sleep are injected, so no Case waits.
6. **Two threshold dimensions, the confirmed legacy values.** `security_alerts_threshold` takes `critical`, `high_or_higher`, `medium_or_higher`, `all`, `off`; an alert counts when its security severity reaches it. `alerts_threshold` takes `errors`, `errors_and_warnings`, `all`, `off`; an alert counts when its rule severity reaches it. An alert at or above either is a finding. Any other value is UNKNOWN. The values stay as the CPO confirmed, `high_or_higher` and `errors`, in the workflow source, unless a separate policy decision changes them.
7. **The alert set is the open alerts of the merge ref, deliberately stricter than the legacy rule.** The CPO's direction: this migration is not constrained to like-for-like behavior, and an alert already open on the base may block an unrelated change if the consequence is explicit and demonstrated before activation. The DO therefore **provokes an inherited finding** on a disposable pull request into a disposable base that holds an open alert, runs the findings judge, and records whether an unrelated change is blocked. That observed result goes back to the CPO and the Owner for the enforcement decision. Nothing is activated by it.
8. **Layers.** `lib/analysis.mjs` (the analysis findings and the wait) and `lib/alerts.mjs` (the alert findings and the thresholds) are pure over facts and import nothing; time, sleep and the read are arguments. `lib/read.mjs` is the only reader: it pages `GET /repos/{r}/code-scanning/analyses?sha=&ref=` and `GET /repos/{r}/code-scanning/alerts?ref=&state=open`, with `fetch` as an argument. Each command wires them and does the only file write of its process. A Case pins that the pure layers import nothing, as T1314 does for `lib`.
9. **The controls.** `04-controls/CTL34-verify-codeql-analysis/CTL34.md` and `04-controls/CTL35-verify-codeql-findings/CTL35.md`, each `type: preventive`, `status: designed`, `has` its Intent, evidence from fixture, one real run and one provoked FAIL. Neither declares a ratchet strategy: there is no baseline, the check is in or out from the first run. Neither gets a release flag: engineering's C32 stages the gate as jobs that are seen to run (detective in effect: a red job blocks nothing while no ruleset names it), and the Owner's go makes each required.
10. **Staging stays the Owner's.** This Change gives two commands and two records. The workflow DO is engineering's once the commands are on main; the release WIRE that installs the source, the ruleset swap and any preventive activation each need Kai's own go.

### Cases (plain `.test.mjs`; they land with the DO, ids taken then after the highest on main, as in C125)

- the analysis findings: a complete set is `[]`; a missing configuration is `missing:/language:actions`; an analysis with an error is `errored:`; an analysis of another sha is ignored; an extra configuration is not a finding; and it names no `alert:`.
- the alert findings: `high_or_higher` counts `high` and `critical` and not `medium`; `errors` counts rule severity `error` and not `warning`; both dimensions together; an alert that is not open does not count; an unknown threshold value throws; and it names no `missing:` or `errored:`.
- the wait: returns at once when all expected are present; polls at 30 seconds and returns when the last arrives; at 600 seconds still missing is not ok and names them; an API error is not ok; with `analyzeResult` not `success` it reads once.
- each command: an injected environment and fetch; findings written to `--out`, exit 0 even when the list is not empty; exit 2 and no file for each UNKNOWN of decision 4 (and, for the findings judge, for an absent analysis), a stale file removed; sha and ref come from the environment only.
- layers and verdict: the pure layers import nothing; neither command prints `PASS` or `FAIL`; the only write is `--out`.
- the control records: CTL34 and CTL35 exist, preventive, each `has` its own Intent, no `strategy`, no `:ratchet`; and the two do not name each other's findings.
- the provoked inherited finding (decision 7) is a recorded observation in `do.md`, not a Case.

No workflow job, no WIRE, no `.github` change, no ruleset change, no removal of the legacy rule, no activation. Dependency Review has the same gap and is its own Change.
