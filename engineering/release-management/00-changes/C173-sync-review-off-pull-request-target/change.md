# release/C173: sync review leaves pull_request_target and keeps its automated approval and review through the Approver App

## Reason
From 2 December 2026 GitHub blocks `pull_request_target` by default in public repositories (read from search results; the changelog itself is for the Owner to confirm). `sync-review.yml` (verify Sync, approve Sync, review Sync, release/C58 and C65) is the fifth workflow of the repository that still triggers on it, next to the four replaced checks of release/C153. The Owner's ruling (28 Nov): the workflow moves off `pull_request_target` and keeps its automated approval and review, through the KAAL Approver App, as one of the three Apps that aid Controls (Approver, Inspector, Dispatcher). The release/C152 on main only changed how a SYNC is recognised (from git, not the title); it did not move the trigger.

## The contract
1. **verify Sync runs on plain `pull_request`.** A workflow of its own, with no token (`permissions: {}`), no secret, the default branch checked out as the trusted judge, and the candidate fetched as Git data from `refs/pull/<n>/head` and never checked out, built, installed or run (the mechanism of release/C90). The judgment is the existing `sync-review/cli.mjs verify`; the head read is the revision of the event, a mismatch or an unreadable ref is refused. It uploads its verdict as data: the verdict, the pull request number, the head sha and the base ref.
2. **approve Sync and review Sync run on `workflow_run`.** A second workflow, run from the default branch when the verify workflow completes. It downloads the verdict as data, never runs anything of the candidate, and asks GitHub for the pull request **as it is now**. It acts only when the pull request is open, its head repository is this repository (a verdict from a fork is never acted on), its base is a `kaal/`, `hotfix/` or `wire/` branch, and the **revision pair** matches: the head sha, the base ref **and the base sha** of the pull request as GitHub says now equal those the verdict carries. A head alone is not enough: if the base moved or the pull request was retargeted, the verdict is stale and nothing is approved. 
   **Provenance.** The verdict is trusted only if it comes from the verify workflow's own completed run: the `workflow_run` event names that run (its id, its workflow, its head sha, its conclusion `success`), the artifact is downloaded from that run and no other, and the verdict inside names the same run, head sha, base ref and base sha. **The run must also be of the trusted file.** A pull request runs the workflow files of its own head and `workflow_run` matches a workflow by name, so a candidate could define a workflow called `sync verify` that uploads a forged verdict. The acting jobs therefore require that the run's workflow path is `.github/workflows/sync-verify-plain.yml` and that this file at the run's head sha has the same blob as on the default branch (read through the API, no checkout); otherwise the verdict is refused. T1686 carries a negative run for each. A missing artifact, a run of another workflow, a run that did not conclude `success`, an artifact from another run, or a verdict that does not match the pull request now is refused: the job says what was missing and does nothing. The verify job writes the base sha it judged (the tip it fetched) into the verdict.
3. **The Inspector signs `verify Sync`** (CPO choice, 28 Nov: one approval mechanism with Review C8, which accepts only a `verify Sync` check signed by the Inspector). A job `sign Sync` of the `workflow_run` workflow posts the check run `verify Sync` through Hosting's `postCheckRun` (hosting/C117) under a grant of the KAAL Inspector App (`KAAL_APP_INSPECTOR_KEY`, `KAAL_APP_INSPECTOR_ID`, the ability `post-checks`), at the head sha of the bound run and nowhere else. It posts only after the provenance of point 2 holds, and the conclusion comes from the bound verdict: PASS is `success`, FAIL is `failure`; an UNKNOWN verdict or a refused one posts nothing, so Review abstains. One POST, no retry (Hosting's rule); a refusal or failure of the post is a red `sign Sync` and approves nothing. Nothing else posts a check of that name: the plain job of the verify workflow is therefore named `judge Sync` (not `verify Sync`), so that exactly one run of the name `verify Sync` exists at a head, and it is the Inspector's (`signer: kaal-inspector`). `approve Sync` needs `sign Sync` and acts only when it succeeded with `success`; `review Sync` needs both and still runs when they did not (the routing to a person never depends on the signature). How the job obtains the built Hosting function (a build of the package from the default branch checkout, or the Controls signing script) is chosen in the DO; the call is `postCheckRun`, never a hand-built POST.
4. **The Approver App holds the write.** approve Sync and review Sync take their token from the KAAL Approver App (secret `KAAL_APP_APPROVER_KEY`, variable `KAAL_APP_APPROVER_ID`, release naming of the Apps), not from `GITHUB_TOKEN`. The verify job holds none. Until the credential exists, approve Sync stays a dry run (`KAAL_SYNC_APPROVE` not `on`) and review Sync keeps its label and comment through the App's token or says that it cannot.
5. **The rules do not change.** `approve Sync` approves only a SYNC that verify passed at the current head, never into the default branch, and only when `KAAL_SYNC_APPROVE` is exactly `on`; `review Sync` puts every other outcome in front of a person. No control is weakened: the same two Cases of release/C58 and C65 (T754 to T759, T791 to T793, T851 to T855, T936, with T757 amended by C152) hold as they are.
6. **No `pull_request_target` remains** in the sync workflows, and the old `sync-review.yml` is retired in the same WIRE that installs the new two.

## Carried Cases whose expectation changes (amendment, before the DO)
Four carried Cases read `wiring/workflows/sync-review.yml` itself and assert its `pull_request_target` trigger or its one-file, three-job shape. They cannot hold unchanged once the source is gone, so the PLAN names them and the DO changes only what is listed (the same rule as release/C168):
- T757 (C58): asserts the trigger is exactly `pull_request_target` and that the three jobs share one file with `needs: verify`. New expectation: the three jobs exist under the same names across the two new sources; the trigger of verify is `pull_request` alone and that of approve and review is `workflow_run` alone; each job still runs only for a SYNC into a `kaal/`, `hotfix/` or `wire/` base, judges from the default branch, and approves only when switched on; no `: write` outside `pull-requests: write` of the two acting jobs; no merge, edit, push, force, swallowed failure or `--auto`.
- T793 (C60): asserts `needs: [verify, approve]` and `needs.approve.outputs.approval` inside one file. New expectation: review waits for approve in the `workflow_run` source and reads its outcome from it; approve does not read its own outcome; permissions are unchanged.
- T851 (C65): asserts verify has no token and no API, takes head and body from the event, and fetches once; the acting jobs never fetch or name the candidate and are handed the verdict. New expectation: the same, with the verdict handed from the downloaded artifact of the verify run and not from `needs.verify.outputs`.
- T855 (C65): asserts three jobs in one file, and that no job able to write fetches the candidate. New expectation: three jobs across the two sources, same shape rule.
The path they read changes to the two new sources; every other assertion stays. Nothing else carried changes: the entry Cases, T936, T1556 and T1559, the controls' drafts and `delivery-map.json` stay as they are, because the installed `.github/workflows/sync-review.yml`, `delivery-map.json` and the trigger baseline of CTL20 change only in the WIRE (Owner go).
