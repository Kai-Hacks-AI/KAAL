# release/C65 the SYNC review reads the candidate only where no token can write

Follows release/C58 and release/C60. The workflow of `verify Sync`, `approve Sync` and `review Sync` runs on `pull_request_target`, and each of its three jobs fetches the candidate's commits as Git data. Today the safety of that rests on one promise: the scripts never check out or run anything of the candidate. A promise like that is a directive control. It holds while nobody changes the code, and CodeQL (`actions/untrusted-checkout`) reads the workflow as exactly what it fears: a job with a token that can write fetches the candidate and later runs code (code-scanning alerts 56 and 57 on the WIRE #1885).

This Change makes the boundary preventive. Only `verify Sync` reads the candidate, in a job with `permissions: {}` that calls no API. `approve Sync` and `review Sync` never fetch it: they take the verdict as data and check it against the pull request and the base as GitHub says they are now, and the approval stays pinned to the head the verdict judged. A candidate that could change what a script does could still not reach a token, and CodeQL then enforces the same boundary on every later edit.

It is a source in Engineering. Nothing here changes `.github`, a ruleset or a setting. A new WIRE installs the result and replaces the one in flight.
