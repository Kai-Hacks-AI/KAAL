# Development hooks: one thin entry per Git hook, no new judgments (PLAN)

PLAN, nothing is built. The Owner likes all the common client-side Git hooks (10 November). This PLAN argues each one from Intent, says which Guard checks it would call and what it needs, and says plainly where there is no argument. It builds on the Development stage and the feedback, evidence and authorization distinction of the lifecycle assessment, and uses the `development/` domain the Owner decided on (feedback-only: no control, judgment, ruleset, gate or environment; see #1354).

## What every hook shares

- **Feedback only.** Every client-side hook can be skipped (`git commit --no-verify`, `git push --no-verify`; the `post-*` hooks and `pre-rebase` are not skipped by `--no-verify` but are advisory too), and a hook result is never evidence for a CI gate. A hook says "not verified locally" where a fact is missing, never a pass.
- **Thin.** A hook file in `.githooks/` holds no judgment. It names its hook point and calls Guard for the checks registered for that point. All judgment stays in the controls (lineage, change isolation, and so on), which CI also runs. A Case fails a hook file that contains a judgment.
- **USE versus BUILD.** Guard's `runs: [hook]` today means the one `pre-push` hook: the declaration has no hook point, and Guard supplies `head`, `base`, `base-ref` and `changed` only at push time. Guard's declaration format is a strict subset: an unknown member is refused. So the point of a check cannot be added to a declaration without a change to the package. Birth in KAAL: a KAAL-side table maps each hook point to the Guard checks it calls, held in `development/`, the feedback-only domain the Owner decided on (the hook entries themselves stay in `.githooks/`, where Git reads them), and a Case checks that every check it names is declared `runs: [hook]`. Moving the point into Guard's declaration is the later abstraction. Whether `kaal-guard run --hook` accepts `--check <name>` to run a named subset is to be confirmed in the RED; if not, that is a Guard gap to raise, not to work around.
- **Facts.** Only `pre-push` has facts today (head, base, base-ref, changed). Each other hook has different ones (staged paths, the message file, the previous and new head). A check may declare only facts the hook point supplies; a Case reads the declaration and the table and fails a check that needs a fact its hook point cannot give (the same registry reading as `earliestStage` of #1352).
- **Latency.** The hooks run on every commit or checkout, so each has a time budget set by a Case at RED and approved by the Owner. No number is chosen here.

## Each hook, argued from Intent

Intent I1 is that only an approved, correctly shaped change reaches `main`, by the lineage. A local hook has an argument when it finds, earlier, something CI would also find, or when it keeps the local feedback honest.

## The commit message form (Owner direction, 10 November; a proposal for the Owner to confirm)

The Owner's direction: a commit message carries **the concern the commit drives**, from the improvement cycle (plan; do and check; act), and **a reason**, the piece that drove it (a Change, an Intent, a Requirement and so on) with its reference, depending on which piece drove the commit. The history already half-says this: titles such as `Engineering: PLAN for version Package`, `guard/C134 PLAN: ...`, `Testing DO: ...`, `Engineering: RED for ...` carry a phase word, and the pull request template's Intent section is the reason. The proposal makes it one form and one check.

**Subject:** `<Area> <PHASE>: <concern>`, for example `Engineering DO: recovery text names a route out of a stuck pull request`.
- `<Area>`: as today (`Engineering`, `Hosting`, `Guard`, or a capability/change id such as `guard/C134`).
- `<PHASE>`: one of `PLAN`, `DO`, `ACT` (Owner, 10 November: **RED is not a phase word**). RED and GREEN are the state the automatic check produces, never authored. `PLAN`, then the check, makes it RED; `DO`, then the check, keeps it RED, makes it GREEN, or keeps it GREEN for a refactor; `ACT` is the learning step afterwards. There is no `CHECK` word either: checking is automatic, and it is where the hooks, CI and the other controls protect the red-to-green game. Writing the failing Cases belongs to `PLAN`.
- `<concern>`: what this commit drives, in a few words; not what the diff contains.

**Reason trailer (required, exactly one):** `Driven-by: <scope>/<ID>`, the driving piece's qualified id in the repository (`release-management/F10`, `guard/C134`, `hosting/D11`, `release-management/T25`); its kind is the id's letter (qualified references, below). **A commit has exactly one driver** (Owner, 10 November): zero `Driven-by:` lines fails, and so does more than one. This is the reason in a form a parser can read, so the check is a parser, not a pattern over free text.

```
Engineering DO: recovery text names a route out of a stuck pull request

Driven-by: release-management/F10
```

**`Driven-by:` is required on every commit (Owner, 10 November), as a semi hard stop.** The rationale is the Owner's: if you cannot name why, why are you doing it? A commit that cannot cite the piece that drives it (an Intent, a Requirement, an Architecture, a Defect, a Case or a Change) is a commit nobody has argued for, which is the "never do things because it was done" rule applied at the smallest unit. "Semi" because the hook is feedback and can be skipped, while the same `message` check in CI judges the commits of the pull request, so a commit with no reason does not reach `main` unremarked; and because a reason is a real piece of the documentation (looked up), not a formality. It is not a way to block a person who has a reason but has not yet recorded it: the recovery in the verdict is to write the piece first (a PLAN adds the Requirement or the Case it will cite) and then cite it.

**Exactly one driver per commit (Owner, 10 November: "like in a car").** Each commit is driven by one piece. It may be a top-level one, such as an Intent, which then pulls the rest behind it (the Requirements, Architecture and Cases that follow from it), but there is still one driver, not a list. The `message` check fails a commit with no `Driven-by:` and a commit with more than one, each with its recovery: for none, name the piece or write it first; for several, name the one that drives, usually the highest that truly moves this commit, and split the commit if two pieces each drive part of it. The check cannot know which of several is the true driver, so it judges the count, not the choice, and the person or reviewer judges the choice (a validation, Review's, not a verification).

**Qualified references (Owner, 10 November: ids need their context; `Driven-by: <capability>/<ID>`).** `T30` or `F10` alone is ambiguous, because the numbers repeat across capabilities. The repository already writes ids as `<scope>/<ID>` where it matters (`hosting/F15`, `hosting/D11`, `change/I7`, `guard/C134`, `release-management/T25`), and the Owner's form is exactly that:

`Driven-by: <scope>/<ID>`, for example `Driven-by: release-management/F10`, `Driven-by: hosting/D11`, `Driven-by: change/I7`, `Driven-by: guard/C134`. Exactly one line.

- **The kind is the id's letter, not a second word:** `I` Intent, `F` Requirement, `A` Architecture, `D` Defect, `T` Case, `C` Change. The earlier `Driven-by: Requirement ...` form is dropped; nothing is left to disagree.
- **Is `<capability>/<ID>` enough for Engineering? Yes, with the scope being the numbering namespace as written (checked in the repository).** Engineering has two coexisting namespaces: `engineering/<ID>` (for example `engineering/F3` and `engineering/F20` in `lanes/README.md`, `engineering/T4` in `github/branching.md`, `engineering/C6`, `engineering/C7`), one sequence shared by its areas (`lanes`, `github`, `verification`, and so on), and `release-management/<ID>` (this bounded context's own F, A, T and I numbers, which collide numerically with `engineering/F1`, `F3`, `F20`, so the scope is what makes them unique). `engineering/<area>/<ID>` is therefore **not** needed. What would make it needed is a duplicate: if two areas define the same `engineering/F3`. The `message` check's id parser fails on an id defined twice within one scope, so a collision is found and reported, and the fix is then a rename or a sub-scope, not a longer form for everyone. I did not exhaustively verify that no such duplicate exists today; the check does, and its RED Case runs it over the repository.
- **A Change can also be named by its record**, the path id under `.kaal/changes/` (for example `Driven-by: engineering/26/11/10/04`, read as the record at that path), since a Change Record is a document with a stable place.
- **Resolution, by parsing, never by matching words:** one table (born in KAAL, in the Development domain) maps each `<scope>` to the documents that define its ids (for example `release-management` to `engineering/release-management/0[1-4]*` and the Case tables of `00-changes`; `engineering` to the Engineering area documents; `hosting` to the package's source documents, not its `dist/` copy). The check reads the ids those documents define with the same id parser `00-changes/documentation.test.mjs` already uses (one place), and fails when the reference is not defined, the scope is unknown, or the id is defined twice in its scope. Its message names the nearest defined ids, the recovery.
- **Tree used:** the commit's own tree (staged, in the hook; the head, in CI), so a commit that introduces the id it cites (a PLAN that adds `F10`) resolves.
- **A pull request number or a URL is not a reference.** A reason is a piece of the solution, delivery or change documentation, not a place where it was discussed.

**Where the other commits fit under PLAN, DO and ACT (my reading, for the Owner to confirm).**
- **A fix after review** carries the phase of what was reviewed: a revision of a plan or of its failing Cases is `PLAN`; a fix to the build that keeps it GREEN is `DO`.
- **A retirement** (removing an old check once the new one covers it) is a change like any other: planned (`PLAN`), then removed (`DO`) with the check proving the coverage stays GREEN.
- **A termination** (the cleanup Change at the end of a change's life) is `DO`, with its own `PLAN`.
- **A promotion or a synchronization** is not authored work. It is a merge of what is already checked, in the form the lineage controls judge, and carries no phase word; the `message` check leaves it to them.
- **`ACT`** is only the learning step after the check: a Defect found and its Case, a check moved earlier because of its `Earliest:` line, a rule or Requirement corrected because of what the run taught. It is not the place for review fixes, retirements or promotions.

**Owner direction (10 November): RED is no distinct pull request.** The failing Cases ship inside the `PLAN` pull request, and its check is red by design; the sequence reads PLAN, DO, ACT. Practically, a failing Case is carried unwired (no lane or suite names it yet, as `recovery.red.mjs` is today), so the pull request's own CI stays green while the Case reports red when run; the DO wires it and it goes GREEN. Pull requests already in flight keep their titles (#1352 stays as it is), and this PLAN's own sequence below follows the new reading: the "RED" step is the Cases written within `PLAN`.

**One `message` check, three places.** The shared Guard check judges this form: subject shape, the phase word from the closed list, exactly one `Driven-by: <scope>/<ID>` whose scope is known, whose id letter is one of the six kinds, and whose reference **exists** and is defined once in its scope (looked up, not guessed). `commit-msg` runs it on the commit message; CI runs the same check on the pull request title and body, because of how this repository squashes (read from the repository settings on 10 November: squash title `COMMIT_OR_PR_TITLE`, squash message `COMMIT_MESSAGES`): the squash subject is the commit's title when the pull request has one commit and the pull request title when it has several, and the squash message is the concatenation of the commits' messages, so every `Driven-by:` trailer of every commit reaches `main`; the pull request template's Intent section is where the reason is written out in full. A merge commit or a synchronization has its own form (the lineage controls already judge it) and is not judged by this check.

**`prepare-commit-msg` pre-fills it, never decides.** In an empty message it writes the area and the `Driven-by: <scope>/<ID>` line of the Change from the branch's Change, using the same convention the pre-push hook already has for the branch's target (`git config branch.<branch>.kaalTarget`): a `branch.<branch>.kaalChange` setting naming the Change, set once per branch. The phase it takes from the previous commit's subject on the branch, else leaves a placeholder the `message` check then refuses. It does nothing when a message exists (`-m`, merge, squash, amend).

**Decided, not open:** `Driven-by:` on every commit and its form `<scope>/<ID>` (Owner, 10 November). The phase list is decided (`PLAN`, `DO`, `ACT`; neither `RED` nor `CHECK`). The squash default is verified, not open: because the squash message is the commits' messages, a check on each commit message is what governs `main`'s history, and the pull request title check covers the multi-commit subject. The check judges only what the Owner confirms.

## Sequence

1. This PLAN, CPO review.
2. The failing Cases (nothing wired), written inside the `PLAN` pull request of each hook step, not in a separate one: every `.githooks/*` file is thin (parsed, no judgment); every hook point names only checks declared `runs: [hook]`; every check's declared facts are supplied at its hook point; the equivalence of hook and CI verdicts where facts exist; "not verified locally" where they do not; a time budget per hook.
3. DO, one hook per step, in this order: make `pre-push` thin, then `commit-msg` and `prepare-commit-msg` over the shared `message` check (area prefix first, the other rules as they are decided), then `pre-commit` after the `changed` fact for staged paths is decided with Guard, then `pre-rebase` (advisory), then `post-checkout` and `post-merge` once the install baseline is proven.
4. Guard abstraction, later: the hook point as part of the declaration, and the product-language vocabulary of `earliestStage`, as the Owner placed it (born in KAAL, abstracted later).
