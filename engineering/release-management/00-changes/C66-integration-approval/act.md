# C66 act

A 4L retrospective of the Change, from the viewpoint of the agent that carried it.

## Liked

The proof that a bot's approval alone can merge a SYNC (#1912) gave the Intent a real observation to be written against, and the `pull_request` rule landed as a copy of the draft in `interface.md`, so the Case could compare the file to its draft. Reusing the format release/C70 defined for declared rules meant no new vocabulary in `stages.json`.

## Learned

The PLAN said a `status` line waits for release/C62; by the DO release/C62 was on `main`, so the control had to carry `status: implemented` and the Case that forbade the line had to require it. Two older Cases (T481, T482) assumed Integrating had one rule and one approval rule counted as a legacy control, so adding the rule meant amending them and saying so. Approval and stale-approval dismissal are described as implemented only: nothing is loaded, so nothing yet refuses an unapproved merge.

## Lacked

A list of the Cases that assume the shape of a stage's rules, so the amendments needed by a new rule are known before the DO, not found by running the runner. An answer from the Owner on the approver login, the unattributed-changes setting on `kaal/**` and hotfix latency, which stay open in `change.md`.

## Longed For

The ruleset loaded beside the old one with a real refusal recorded, so the control can move from Implemented to Running and Tested. A check that a PLAN's statement about the state of `main` (here, the missing `status` finder) is still true when the DO starts.
