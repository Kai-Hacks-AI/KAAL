# release/C133 the remaining pull_request_target gates run on pull_request

Three workflows still use `pull_request_target`: `sync-review` (release/D15), `change-isolation` (release/D16) and `lineage-synchronization`, the Branching gate (release/D17). The Owner chose route A for them (CPO handover, 25 November): content-only checks on a plain `pull_request`, plus a ruleset on the delivery paths. This Change decides how that route is built and what each gate becomes. It is a PLAN: it adds no source, no workflow, no Case, no ruleset change and no flag.

Two outcomes are evidenced independently: delivery-path isolation and trusted judge execution (see `change.md`); no DO is authorized before the CTO proves the first. The idea of route A: a pull request on `kaal/**` cannot touch a delivery root (`.github`, `.githooks`, `.kaal`, `.agents`, `.claude`, declared in `delivery-locations.json`), because the ruleset allows those paths only on `wire/*`. Then the workflow file a plain `pull_request` runs is the default branch's content, unchanged by that pull request, and the reason for `pull_request_target` is gone. The trust no longer comes from the trigger; it comes from the ruleset.
