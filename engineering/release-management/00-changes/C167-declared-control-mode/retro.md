## What was delivered
The shared helper `05-src/lib/entry-flag.mjs` reads a control's declared mode (the `stations` field of its record) and its flag (the controls instance's `flags.json`), validates with the controls library, hands the adapter `toBoundary` of the flag and returns the library's exit. The three command lines call it and the seven entries name no mode literal. Cases T1630 to T1634 are green.

## What we learned
- **Ownership took three rounds.** The intended mode is Release's (in the control's own record), the flag is the controls instance's, the meaning of the combination is the library's. First drafts had Release deriving a mode from a flag, then a missing flag "never blocking". Both were wrong, and the CPO's holds were right.
- **An unknown flag is a configuration error, not a state.** The controls contract moved twice before it settled: an unknown flag ran detective, then fail-safe, then (CPO and Owner, 27 Nov) an unknown decision blocks CI for every control type, while an unknown result (Torn or Mute) is judged by the known decision. Release consumes it and interprets nothing; T1631 asserts it row by row and T1634 ratchets that.
- **Adoption is not free.** Because every unknown decision is red, a job that adopts `validateFlags` before the flag file and its entries exist turns red, detective jobs included. So the adoption of an entry is a WIRE on the Owner's separate go, landed together with the check's entries in `flags.json` (`advisory` first). The engagement is by the job supplying `KAAL_FLAGS`, `KAAL_STATION` and `KAAL_CONTROL_RECORD`; a job that supplies none behaves as before.
- **A gap kept visible.** A pull request for which a control does not apply returns 0 before the flag is read, so a configuration failure of a control that does not apply is not surfaced on that pull request. T1633 pins this on purpose ("not applicable answers zero and writes no record"). It is for controls to say whether the library should surface the configuration even then.
- **The merge queue.** Reading the live rulesets for the swap showed that the `old promotion` ruleset also governs the merge queue and that the queue's reporters are other workflows. Requiring the plain jobs' own names would have hung every merge into main. This is why the swap is by name transfer (release/C168), not by a ruleset edit, for all four checks.
- **A defect of ours in a ledger.** The trusted-execution proof file had its T2 section three times, from a replace that ran thrice in the script that wrote it. It was found at the recount, fixed in #2941, and the T2 audit now covers all 174 admitted runs.
