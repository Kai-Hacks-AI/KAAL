## Liked

  keeps: it said open findings on the merge ref may be evaluated only if explicit and demonstrated, and that the DO provokes an inherited finding and reports what happens. That request is what found the defect below, and it settled a question the PLAN could only argue.
- subject: two distinct controls for analysis completeness and findings
  keeps: when the analysis was absent the findings judge said UNKNOWN instead of reading an alert set it could not trust, and the observed runs showed each control answering for its own cause.

## Learned
- subject: a fixture built on my guess of an API's shape hid a field name
  source: the real answer names the commit of an analysis `commit_sha`; my reader and my seven Cases used `sha`, so on a real pull request the analysis judge never found its analysis and answered UNKNOWN after ten minutes. Green Cases did not show it; the experiment on a disposable pull request did (fixed in the DO before the CPO approval).
- subject: a pull request ref shows only the alerts the change introduces
  source: with alert #65 open on the disposable base, the merge ref of an unrelated pull request listed no alert in any state, and a pull request that adds its own vulnerable file listed that one alert and the findings command wrote it. Alerts that exist only on a base branch are not visible to a pull request check.
- subject: a PLAN that carries RED Cases fails Engineering and Workspaces
  source: the first PLAN pull request failed both checks until I moved the Cases to the DO; those checks run every Case in the folder.
