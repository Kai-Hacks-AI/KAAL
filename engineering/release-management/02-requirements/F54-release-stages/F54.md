# release/F54 release-stages

Release management is a pipeline of **Stages**, taught by the Skill, declared and configured by the consumer, and realized by a binding.

- **Concept.** A Stage has a **Subject** (what moves through it), **gates** (logical check identities), **evidence** judged PASS, FAIL or UNKNOWN (UNKNOWN never passes), an **authority** (who may pass it), a **transition** (how the Subject leaves) and a **destination** (a logical name for where the Subject stands when it leaves). Stages are ordered; a Subject leaves Stage n by its transition and enters Stage n+1. A Stage may have **parts**: named alternate incoming paths into that Stage, each of which passes the Stage's gates. A part is not a Stage and not a predecessor. The concept names no platform.
- **Vocabulary.** The activity names are those of release/C35: Developing; Integrating, with its parts Collecting, Hotfixing and Wiring; Promoting; Publishing. This requirement adds no competing stage model; it states the same activities without a platform.
- **Declaration and configuration.** A consumer declares its Stages as plain configuration files in `.kaal/config/release/`, one per Stage, following the way Guard is configured. A Stage file states its order, name, Subject, gates, authority, transition, destination and parts. Destinations and gates are **logical identities** the consumer names. A Stage file holds no branch, pattern, tag, check name, tool, registry or platform. Declaring Stages does not require a new Core Node.
- **Binding.** How a platform realizes the declaration is a separate binding. It maps each logical destination and each logical gate to the platform's own data (for GitHub: branches, patterns, rulesets and required check names; for githooks: hook points; for manual: an Owner checklist). Platform data such as `main` or a check name lives only in a binding and never in a Stage file. A binding adds no Stage and changes no gate. Bindings are later Changes.
- **Structure is not authorization.** The judge of a declaration answers only whether its structure is sound. A sound structure never authorizes a release, never shows that a Stage or the pipeline is operationally ready, and never passes a gate. Authorization and readiness are reported UNKNOWN, and so is binding coverage.
- **Separation.** Scope completeness, product verification and publication readiness remain separate gates (release/F53).
