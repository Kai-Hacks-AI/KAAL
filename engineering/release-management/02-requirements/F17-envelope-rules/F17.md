# release/F17 envelope-rules

The envelope of a pull request is its title and its body, read together with the route it takes and its commits. It is judged by these rules, and each breach is one finding. The rules come in three layers, so that a new PR type adds a template and changes no shared rule.

## 1. Shared rules, for every TYPE

- Title: `<TYPE>: <description>`, with TYPE an upper-case word and a description that is not empty; no Change id, link, emoji or attribution wording in the title.
- Body: level-2 chapters only; the first is `Change` and it is not empty; nothing stands before the first chapter or after the last chapter's content; no chapter holds a link, emoji or attribution wording; no HTML comment stands before the first chapter or carries attribution or metadata; and the body holds no template declaration (`KAAL-PR-template`), which is template metadata and never part of an authored body. This is the contamination of release/F13, stated for all types. The shared rules do not name any TYPE or chapter.

## 2. Structure, derived from the declared template

A template declares itself with an HTML comment, `<!-- KAAL-PR-template: <TYPE> -->`. The chapter names and their order for a TYPE are the level-2 headings of the template that declares it. The templates are read from the base of the pull request, never from its head, so that a PR cannot change the template it is judged by. The registry of types is the set of declared templates; nothing in the judge lists the types.

The reader sorts every template it finds in the places GitHub reads templates from (`pull_request_template` in the root, `docs/` or `.github/`, and a `PULL_REQUEST_TEMPLATE/` directory in any of them) into three classes: declared KAAL templates (DEFAULT among them), and the others, and reports each class explicitly:

- **Declared KAAL templates.** They form the registry. A declaration that is malformed (no TYPE, not upper-case, several in one template), a template that does not start with a `Change` chapter, or a TYPE that two templates declare, is a finding on the template set. A TYPE with a malformed or duplicate declaration is ambiguous and is not in the registry.
- **DEFAULT, the TYPE of the fallback (release/F19).** The single default file GitHub names (`pull_request_template` with any extension and any letter case, in the root, `docs/` or `.github/`, and not inside a `PULL_REQUEST_TEMPLATE/` directory) that declares `<!-- KAAL-PR-template: DEFAULT -->` on its first line and starts with a `Change` chapter. DEFAULT is a TYPE: it is in the registry beside the specialized TYPEs, and a pull request titled `DEFAULT: <description>` is judged by its chapters like any registered TYPE. By policy DEFAULT applies only when no specialized TYPE fits: a matching specialized template always takes precedence, so a PR whose title names a specialized TYPE is judged by that template and never by the DEFAULT chapters. DEFAULT has no row for the route or the Change identity in layer 3, so both are reported as not judged. A DEFAULT declaration anywhere else (including a file inside `PULL_REQUEST_TEMPLATE/`), not on the first line, a second DEFAULT, several default files even when only one declares DEFAULT, a default template whose first chapter is not `Change`, or a typed template declaring DEFAULT is a finding on the template set, and DEFAULT is then not in the registry. What the DEFAULT template contains is decided by release/F18, not here.
- **Other templates, not declared as KAAL templates**, which includes a default file that carries no declaration. Each is neither ignored nor called invalid. The result carries a decision point: "I found templates that are not KAAL templates; what should we do with them?", with each path and the facts the reader saw (its level-2 headings and whether it holds a declaration-like comment). The checker proceeds without them: the typed judgments are unaffected, and these templates are never used to judge a PR. Only the Owner decides what becomes of them (declare one as a KAAL type, leave it as a third-party template, or remove it); the checker takes no authority over a template that is not a KAAL template.

A TYPE in the title that is not in the registry is unsupported. The shared rules still apply, its chapters are not judged, and the result says so explicitly. It is never treated as a known type and never reported as fully judged. The hint comments of a template are not chapters and are allowed inside a chapter.

GitHub, not the checker, chooses what a person sees: it fills a new pull request from the default file, or from a `PULL_REQUEST_TEMPLATE/` file that the person picks with the `template` query parameter, and it reads templates from the default branch. The checker judges what was written, and it does not select or change a template.

Deriving the headings is not verifying what a chapter must say. What a chapter must contain, such as the driver of a SYNC or the priority judgment of a PROMOTION, stays with the requirements and Cases of that type.

## 3. Rules keyed by TYPE, where a type has them

Some rules cannot be derived from headings, and each is one row for one TYPE. A TYPE without a row for a rule is reported as not judged for that rule.

- Shape of the `Change` chapter: PLAN, DO and ACT name the id, the name and a description or scope; SYNC and HOTFIX name the id and the name only; PROMOTION gives one line per delivered Change with its id, name and the phases carried. Only PLAN's shape is on `main` (release/F3: `<id> <name>: <short description>`, and each chapter one short paragraph); the others are added with their templates.
- Route: PLAN, DO, ACT and SYNC take a base under `kaal/`, never `main`. PROMOTION takes `main` as base and a head under `kaal/`. HOTFIX takes a head under `hotfix/` (the CPO decision recorded with the Hotfix interface of release/C11). The base of a HOTFIX is not judged and every HOTFIX result says so under not judged: its branch lifecycle, its base or bases and its admission path belong to the Hotfix delivery-path Change, a separate Change, and are not inferred from the HOTFIX template.
- HOTFIX body and head: a pull request from a `hotfix/` head must be a HOTFIX, and any other TYPE from such a head is a finding. The Defect, Urgency and Approach chapters of a HOTFIX each need content, and the Change chapter of a HOTFIX is one line, `<id> <name>` (release/F16): the id, one space and a name of words joined by single spaces, where a word holds letters, digits and `_ . ' ( ) / & + -`. A colon, a description, markup, a control or an invisible character, and a second space in a row are findings. Everything else about a HOTFIX needs a reviewer and is listed under not judged on every HOTFIX result: whether the change corrects only its defect, and whether the Defect and the Urgency are true, beside the base and the Change identity. A HOTFIX never reaches PASS from the envelope alone.
- Change identity, for PLAN, DO and ACT: the id that begins the `Change` chapter equals the `Driven-by:` trailer of every commit, and each commit has exactly one. SYNC, PROMOTION and HOTFIX are deliberately not judged: their commits carry the trailers of the commits they bring, and which commits count, and which id a SYNC body names, is not yet defined by their templates and delivery paths.

## 4. The verdict

A result has two parts that must not be confused. `ok` is local validation only: it says that no rule found a fault, and `ok` alone never authorizes success, merge, admission or promotion. The verdict is the only result a consumer may rely on: FAIL when a rule found a fault, UNKNOWN when none did but something was not judged, and PASS only when nothing was left unjudged. UNKNOWN never passes. A valid HOTFIX is `ok` with the verdict UNKNOWN, since its base is not judged. Every result lists everything it did not judge.
