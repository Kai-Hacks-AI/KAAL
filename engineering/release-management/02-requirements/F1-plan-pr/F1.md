# release/F1 plan-pr

verify Plan returns PASS, FAIL or UNKNOWN for a PLAN. A PLAN passes only when it satisfies all of these rules.

1. Every Change has at least one driver: it implements an Intent, resolves a Defect, or both. Every Change closes at least one Gap and may close several, and every Gap, a parent Gap included, has exactly one closing Change. A Gap that needs several Changes is decomposed through `parent` into child Gaps. A parent is done only when its children are done: a parent Gap with a passing Case needs a passing Case on every child Gap, which may happen in the same Change. A parent Gap that passes while a child Gap does not fails with a Recovery that names the open child Gaps. (release/T2, release/T42)
2. Every functional and nonfunctional Requirement serves an Intent. (release/T3)
3. Every Architecture element addresses at least one functional Requirement, nonfunctional Requirement or Defect. `parent` is separate same-kind decomposition from child to parent: it exists, has the correct kind and forms no cycle, and it confers no coverage. (release/T4)
4. Every Case tests one or more targets, every link resolves with the correct type, and ids are unique. Every node id, Case ids included, has the form `<capability>/<kind><n>`, and no id encodes where a node sits. Each Intent, Requirement, Architecture element, Defect and identified Gap has at least one outer-loop Case, and a Case may cover several targets. (release/T5, release/T14)
5. Every Case sits at the place derived from its `tests` list: beside the nearest shared ancestor of its targets, then the common Intent, then the capability itself. A Case declares no place: it points only at what it tests and sits where its targets sit. The reader observes the folder it was found in, and placement is validated against that, separately from identity. A Case in the wrong place fails with a Recovery, and a Case whose folder cannot be read yields UNKNOWN. A Gap sits in the folder of its closing Change. (release/T6)
6. A PLAN contains at least one meaningful observed RED condition: an executed Case that fails because an Intent, Requirement, Architecture element, Defect resolution or expected behaviour is unfulfilled. Passing Cases are allowed. An unconditional failure alone is not that condition. (release/T7)
7. Change-oriented Cases that prove identified gaps closed are kept apart from target-oriented Cases that prove the target, and a Case may cover several gaps. (release/T8)
8. Every failure carries findings and a Recovery. Unreadable or unresolvable input, and missing evidence, yield UNKNOWN, and UNKNOWN never passes. Every template heading is parsed. (release/T9)
