# release/F16 hotfix-interface

The body of a Hotfix pull request is a short interface of exactly four level-2 chapters in this order, Change, Defect, Urgency and Approach, and nothing else: no other headings, commentary, test results, CI status, execution logs or attribution. It repeats nothing that the Change, its Cases, the diff, the branch and pull request metadata or the delivery controls already hold, and so has no chapter for the correction itself, the route to `main` or production, or recovery.

- Change: one line, `<id> <name>`, the stable identity of the Change. The pull request title carries a type and a human-readable purpose and no identifier, so the body is the one place of the pull request that names the Change. The line is an identity, not a description: the Defect says what is broken.
- Defect: the KAAL Defect, referenced by its KAAL identity `<capability>/D<n>`, such as `hosting/D10`; a GitHub issue or URL is not that identity. It then says what is broken, and which state is defective. Production, `main` and the unpromoted work of a collector are three states, not one. A Hotfix may correct a defect in any of them. The chapter names which, by package and published version for production, and never claims a production impact that does not exist. The defect must justify the Hotfix.
- Urgency: why this cannot follow the ordinary Change path, and the consequence of waiting. A ticket number or a priority label alone is not an answer.
- Approach: why the chosen path is the fastest safe one from the RED Case to GREEN, rather than a broader improvement or a refactoring. It states the choice and what it trades off, not the implementation: the correction is whatever turns the Case of the defect GREEN. Where production is affected, it also says what else from `main` a new published version would carry.

The shared formatting contract of all PR interfaces applies to it and is not defined here: exactly the prescribed level-2 chapters in order, concise intention-focused content, no extra headings or commentary, no generated attribution, session link or tool footer, and no duplicated implementation details, test results, CI status or execution logs. This requirement states only what is particular to a Hotfix, and implements no formatting logic of its own. Each chapter is short and carries concise author guidance. The body states no verification: what shows the defect and its correction is a Case that reproduces the defect, RED before the correction and GREEN after it, together with the checks and the review. The interface guides the author and replaces no control. It does not define the branch or the controls through which a Hotfix is delivered: that is the Hotfix delivery path, a separate Change.
