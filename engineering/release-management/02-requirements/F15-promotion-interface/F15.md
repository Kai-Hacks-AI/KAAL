# release/F15 promotion-interface

The body of a promotion pull request is a short interface of exactly two level-2 chapters in this order, Change and Why now, and nothing else. They answer two distinct questions: what is delivered, and why it should be delivered now rather than later. The formatting follows the contract shared by all PR interfaces: exactly the prescribed chapters in the prescribed order, concise content, no extra headings or commentary, no generated attribution, session link or tool footer, and no duplicated implementation detail, test result, CI status or log. This requirement states only what is particular to a promotion. It reuses no other heading of the PLAN, DO or ACT interfaces.

- Change: one line per Change the promotion delivers, `<id> <name>: <phases carried>`, with the stable id of the Change, not of a pull request, and the phases it carries (PLAN, DO, ACT). It describes none of the Changes.
- Why now: why delivering to `main` now rather than later is worth it, forward-looking: what it unblocks or enables. It keeps the comparative judgment of priority: it names only the other Changes that bear on this decision, never a backlog and never earlier promotions told as history. Every Change it names carries an explicit reason for its relevance, such as a dependency, what this delivery unblocks or enables, or why it takes precedence, so that no reference stands unexplained and no unrelated Change is listed. It does not restate the PLAN, the diff, the Cases or the verification.

The body holds no source or destination (the pull request shows them), no description of new behavior (a promotion delivers Changes that already landed in a collector), no test or check results, no approvals, no retrospective, no merge method and no attribution. Those live in the files, the checks, the review history and Branching, and a statement of them in a body cannot be tied to the head it was written for.

The title of a promotion pull request is `PROMOTION: <meaningful description>`, type first and purpose second, in words a reader of a pull request list understands. It holds no Change id, no collector name and no pull request number. The stable id stays in the Change chapter of the body.

Prior review is history: the approvals of the Changes were given to those Changes. The authorization of a promotion is the Owner's go on that promotion, recorded in its own review history, and the body neither carries nor implies it.

Each chapter is short and carries concise author guidance. The interface guides the author and replaces no control.
