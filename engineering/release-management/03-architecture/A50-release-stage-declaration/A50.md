# release/A50 release-stage-declaration

A Stage file has YAML-style frontmatter between `---` lines and a prose body: `type: Release/Stage`, `order` (a positive integer), `name`, `subject`, `gates` (a non-empty list of logical gate identities), `authority` (`owner-approval`, `two-person` or `automatic`), `transition` (`integrate`, `mark`, `publish` or `install`) and `destination` (a logical name), and optionally `parts` (a list of names of the alternate incoming paths of this Stage). The shape is in `interface.md`.

`parts` semantics, all checkable by a pure judge: each part name is non-empty and unique within its Stage and across the declaration, and no part carries the name of a Stage. A part is not a predecessor: predecessors follow from `order` alone.

The judge is `05-src/stage-declaration/declaration-judge.mjs`, a pure function of the parsed files. It checks that Stage names and orders are unique, every required key is present, `authority` and `transition` are from their lists, every gate and destination is a plain logical name, parts are as above, and no Stage file holds platform data: a platform, tool or registry word (GitHub, githooks, git, npm, ruleset, workflow, branch, tag), a path or a glob pattern, or a name that is only meaningful to a platform. It returns `{ structure: 'SOUND' | 'UNSOUND', findings, stages, authorization: 'UNKNOWN', readiness: 'UNKNOWN', bindingCoverage: 'UNKNOWN' }`. It has no boolean that a caller could read as ready or allowed, and a sound structure leaves the other three UNKNOWN. It is not a workflow or a required check.

The Skill vocabulary reference is `05-src/stage-declaration/reference.md`, the concept in prose without a platform term. KAAL's own activities, in release/C35's names, are expressed as an example set in `05-src/stage-declaration/instance/` that the judge finds sound. The example holds no `main`, no branch pattern and no check name: those are the GitHub binding's data, which release/C35 holds in `05-src/stages/stages.json` and the ruleset sources, outside the abstraction. Reconciling the two is a later Change. Installing the example into `.kaal/config/release/`, any binding, and delivering the reference and judge into `packages/kaal-release` are later Changes. Plain configuration files follow the Guard pattern; whether Stages should instead become a Node type is left open.
