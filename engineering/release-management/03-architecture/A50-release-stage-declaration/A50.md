# release/A50 release-stage-declaration

A Stage file has YAML-style frontmatter between `---` lines and a prose body: `type: Release/Stage`, `order` (a positive integer), `name`, `subject`, `gates` (a list of check names), `authority` (`owner-approval`, `two-person` or `automatic`), `transition` (`merge`, `tag`, `publish` or `install`), `target`, and optionally `routes` (a list of Stage names that name the routes allowed to enter this Stage). The shape is in `interface.md`.

The judge is `05-src/stages/stage-judge.mjs`, a pure function of the parsed files. It checks that Stage names and orders are unique, every required key is present, `authority` and `transition` are from their lists, every gate is a non-empty name, every route names an existing Stage, and no Stage file names a platform, tool or registry (GitHub, githooks, git, npm, ruleset, branch, tag name, workflow). It returns `{ valid, findings, stages, bindingCoverage: 'UNKNOWN' }` and never judges a binding. It is not a workflow or a required check.

The Skill vocabulary reference is `05-src/stages/stages-reference.md`, the layer-one concept in prose without a platform term. KAAL's own Stages (Development, Integration, Promotion, Publishing, as release/C35 defines them) are expressed as an example set in `05-src/stages/instance/` that the judge accepts. That set is KAAL's data and is not part of the package. Installing it into `.kaal/config/release/`, a binding to GitHub or githooks, and delivering the reference and judge into `packages/kaal-release` are later Changes. Plain configuration files follow the Guard pattern; whether Stages should instead become a Node type is left open.
