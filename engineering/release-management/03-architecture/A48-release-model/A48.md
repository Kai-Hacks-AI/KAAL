# release/A48 release-model

A planned version has one manifest, `engineering/release-management/05-src/scope/<package>-<version>.json`, with two parts that mirror the two meanings of Release: `contract.intents` (the static Release: Intent ids, each `new` or `retained`) and `delivery.changes` (the delivery: the committed Change ids with their capability, no roles). Nothing else is listed; candidate Changes under consideration are not part of the manifest.

The judge is `05-src/scope/scope-judge.mjs`, a pure function of the manifest, the set of Change ids delivered on `main`, and optionally a function `serves(changeId)` that returns the Intent ids of a Change from the existing traceability. It reads and changes nothing. It returns three separate answers:

- `deliveryScope`: `complete` (every declared Change delivered), `delivered` and `missing`.
- `contract`: `unserved`, the `new` Intents that no Change of the delivery scope serves; UNKNOWN when `serves` is not given. A `retained` Intent is never counted unserved, because an earlier version delivered it.
- `productVerification` and `publicationReadiness`: always UNKNOWN, each with what is not judged.

The result has no single `ready` field, and the judge rejects a Change entry that carries a role, because every declared Change is committed. The judge is not a workflow or a required check. It is tested in the collector on known good and bad manifests (T330); completeness of a real delivery scope is a separate readiness Case that stays RED until delivered (T331). The first real manifest for kaal-release 0.0.1, including which Intents are in its contract and which Changes are committed, is a later DO that needs the owners' agreement.
