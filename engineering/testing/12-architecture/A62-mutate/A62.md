# testing/A62 mutate

`lib/mutate.mjs` composes what Testing already has and decides nothing: Hosting reads the tree and writes each scratch copy (`read`, `initialize`, `scratch`), `runCases` (`testing/C63`, with `testing/C81`) runs the Cases and reports GREEN, RED (assertion) or UNKNOWN per test, and the classification of a mutant is a pure function of that run report and the application of the change (`classify`, pure). So the meaning of killed is the runner's meaning of RED: an assertion, never an unrelated error. The record keeps the shape of the other Testing records (a schema, counts, a `complete` that is true only when nothing is unresolved) and can be an input to a later observation, but it is its own form and does not extend `kaal-testing/observation@1`. Mutants are given, not generated: choosing a violation of a claim is Testing's Skill (Targeted Mutation Verification) and the caller's work, and generating mutants from operators brings equivalent mutants and needs its own Change. A caller that wants a gate over survivors (no new survivors against a baseline, a ratchet) reads `survivors` and owns the decision, as hold Act owns its verdict, or runs `--strict` and takes its exit code as a plain answer to whether every mutant was killed, which is not a verdict on the Change; wiring a job is the caller's, here engineering's. Candidate code runs in the scratch copies, as Cases do, so the same residual risks apply: a Case can lie about its result, and the record is evidence for a reader, not enforcement. Rejected: a mutation library as a dependency (a runtime dependency and an engine that does not know Testing's meaning of killed), and applying patches with an external `patch` program (a host command; an exact `find` and `replace` is checkable and portable).
