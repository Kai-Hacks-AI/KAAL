# Research: representation follows audience and ownership

> Research, not a PLAN. It reports evidence and proposes owner-scoped Changes. It changes no artifact, and each proposal is its owner's to plan, after the Owner decides.

**The rule (the Owner, #607 and #609, 2026-10-29).** The test is whether an artifact is meant for human–agent collaboration.

- Collaborative documents, human–agent or human–agent–script, are Markdown with validated YAML frontmatter. The frontmatter holds the structured members that scripts read, Skills' scripts included, for deterministic execution. The body carries semantics, rationale and guidance.
- A script consuming the frontmatter does not make the document machine-only.
- JSON and other native machine formats are for contracts, exchanges and state that are purely code- or machine-oriented, where no human–agent collaboration is needed.
- Neither classification is inferred from the presence or absence of prose. What decides it is the artifact's actual authoring, review and negotiation role.

Core's Deterministic Frontmatter states the mechanics: `N1`, `N2`, `N3`, and `F8`, under which each Capability owns its Types and their validation, never looser than `F1`–`F6`. This research keeps that contract as it is.

**What was read.** Every tracked `.json` file on `main` and on every `kaal/*` branch at 2026-10-29 11:40Z, except `package.json`, `package-lock.json` and `tsconfig*.json`, which are their tools' formats. For each: who writes it, who reads it, and whether it carries prose. Every Markdown file on `main` with frontmatter, for a `type` and for the prose keys `F3` forbids. And the two frontmatter validators on `main`, Core's (`packages/kaal-core/src/frontmatter.ts`) and Guard's (`packages/kaal-guard/lib/config.mjs`).

## 4. Requirements against the validators

- **Guard's `Guard/Check` Type cannot be stated in `F1`'s value kinds.** `F1` lists `id`, `name`, `enum`, `ref`, `path`, `boolean`, `number` and `parameter`, says there is no free-text kind, and allows a mapping only as a `ref`. Guard's validator accepts `command` as any string with a program in it, and `outcomes` as a map from exit status to `held` (`config.mjs`, lines 191–217). `F8` says a Capability's own validator is never looser than `F1`–`F6`. So Guard is conformant in spirit (no prose key, `type: Guard/Check`, unknown keys refused), but its Type has no `F1` schema, and Core's validator could not check it.
- **Nothing checks this today.** The Engineering step that applies Core's frontmatter conformance cases to Capability-owned artifacts, Guard's declarations among them, is planned in `engineering/guard/change.md` and was never created.
- **The genesis `Node.md` has no `type`.** It is the one intended exception (the Owner's Typed Form ruling). No other Markdown file with frontmatter on `main` lacks a `type`, and none carries an `F3` prose key outside `SKILL.md`, which `F7` exempts.

## 6. Ownership claims, classified by role

The question is the claims' actual authoring, review and negotiation role. Their lack of prose is not the test. Read on 2026-10-29 across `main` and every `kaal/*` collector:

- **Authoring.** 15 distinct claims exist. Each was written once, in the Change that established its Capability, and each claims exactly its own package directory (`packages/<…>/`). Testing's reader enforces that: a claim may only cover the tree that holds it.
- **What changed afterwards.** Across all 66 commits that touch a claim:
  - no claim's `paths` ever changed;
  - every later edit was mechanical. Either the `owner.id` was refreshed after the Capability Node's bytes changed (Graph, #173), or Testing reshaped the claim format (`capability` became `owner`, then `kind` was added).
- **Review and negotiation.** No claim was the subject of a review discussion. Ownership was negotiated elsewhere: in Capability Nodes' text, in the Owner's rulings on pull requests (for example #599 and #585), and in project decisions. The claim file then recorded the outcome mechanically.
- **Consumers.** Only scripts read the claims: `kaal-testing/attribution` and `engineering/contracts/measure.mjs`. No person or Agent reads one to decide anything.

**Classification: machine-oriented.** A claim is a derived, mechanically maintained record of an ownership decided elsewhere, so JSON is appropriate.

**What would change that.** A claim would become a collaborative governance artifact, and Markdown with validated frontmatter would then be appropriate, if claims started to carry ownership that is decided in the file itself. Examples: a claim beyond the claimer's own package directory, such as a repository-native tree, or two Capabilities negotiating one path. Then the claim's owner (Testing, for the format) proposes the migration as its own Change, with this evidence redone.

## Decided by the Owner (#609, 2026-10-29)

1. **P4: no migration authorized.** Section 6 classifies ownership claims with evidence, under the rule above. They are machine-oriented today, so JSON is appropriate. Any migration would be a separately scoped Change led by the owner, and nothing here implies one.

This stays research. Each implementation belongs to its owner's separately authorized Change, and nothing here authorizes a DO, a synchronization, a promotion or a publication.
