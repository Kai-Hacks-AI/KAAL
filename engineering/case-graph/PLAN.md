# Engineering: the Case graph computer, a requirements traceability computer (PLAN)

Status: PLAN (engineering, collector `kaal/engineering-boundary-engine`). Ids provisional until the collector integrates them. It authorizes no DO beyond this plan's own, and no promotion, version bump, SYNC, ledger entry, release dispatch or npm publication.

## Intent

A capability's Cases sit beside the Node that motivated them (an Intent, a Requirement, an Architecture element, a Defect, or the source). Whether a Case ships, and which suite it belongs to, must not be a folder or a hand-kept list. It is computed from the Case's `tests` edge and the capability's Architecture. Engineering owns the computer, because Engineering owns the one YAML parser; a capability stays dependency-free and its shipped verification reads only JSON that Engineering wrote (Owner rulings of 2026-11-09: computed, not folder-based; the parser is an acceptable Engineering dependency).

## Requirements (provisional ids)

- **R1. The computer.** `engineering/case-graph/compute.mjs --package <dir> [--write|--check]` reads a capability package and prints, or writes to `<dir>/04-test/engineering-check/cases.json`, or checks, the computed Case graph. It only reads the package (no import of a Case, no run, no network).
- **R2. The inputs.** (a) The Architecture Node `03-architecture/architecture.md`: the sections `## Solution`, `## Delivery` and `## Cross-cutting`, each element line `- **<cap>/A<n>** [<ids>]: ...` (the bracket lists the Requirements and Intents the element answers). (b) Every Case file: a file named `*.test.mjs` or `*.test.ts` outside `00-changes/`, `node_modules/`, `dist/` and `.git/`. Each starts with a YAML front matter block in a leading block comment, `/*---` ... `---*/`, with `tests` (the list of Node ids it verifies: Intents, Requirements, Defects or Architecture elements) and, optionally, `runs: external` (another runner owns its execution), parsed with `yaml`. Architecture never points at a Case; the graph is read from the Case side only. (c) Each Case title, `<cap>/T<n> [<targets>]: ...` or a fictitious `<cap>/TX-<name>`.
- **R3. The computed graph.** One record per Case: `id`, `file`, `targets`, `branch` and `ships`. The branch derivation is authoritative and in this order: (1) when a Case names an Architecture element (`A<n>` in its title), that element's branch is the Case's, and every target must still be valid for it (a target the element does not answer, or that is answered only by an element of the other branch, is refused, so the element chooses the branch without hiding an invalid target); a Case that names a cross-cutting Requirement and one explicit element takes the element's branch; (2) when it names none, it is the single branch that answers its targets (`solution` or `delivery`). `ships` is true exactly when the branch is `solution`; `ships` exists only as computed output in `cases.json`: it is never Case front matter and never a hand-kept source, and the computer refuses a Case file whose front matter carries a `ships` key (R4). One record per file: `ships`, `runs` (`shipped`, `collector` or `external`) and its Case ids. Order and format are deterministic.
- **R4. Fail closed.** The computer refuses (exit 2, nothing written) on: a Case file with no front matter or invalid front matter; a `tests` edge that is not exactly the union of its Cases' targets; an edge to an id no Node defines; a target answered by no element; a duplicate Case id; a Case whose title has no id and targets; a Case in both branches (a Case that names elements of both, or whose targets are cross-cutting and which names no element); a file whose Cases are not all of one branch (the file ships or does not); a front matter carrying `ships`; a Case that names an element for a target that element does not answer; and a Case file that cannot be read.
- **R5. Outer checks are Delivery, said in Architecture.** Whether a Case can run in an installed copy is decided by where Architecture places what it verifies, not by a flag. A check of a shipped part from outside the installed package (it imports the repository or packs it) names a Delivery element that places outer checks, so its branch is Delivery and it does not ship. The capability states that element in its own Architecture.
- **R6. Capability side stays parser-free.** The capability's own tooling (build, collector, shipped verification) reads only `cases.json`. It copies a Case file into `dist/` only when `cases.json` marks it as shipping (its Cases are Solution), runs the other Case files itself unless they are `runs: external`, and fails closed when a Case file in the tree is not in `cases.json`, when `cases.json` lists a file that is missing, or when a Case would run twice or not at all.
- **R7. Currency, a mandatory gate.** `--check` recomputes the whole graph from the actual Architecture and the Case front matter and titles, and fails when the file on disk differs in any content (a Case's `branch`, `ships`, `targets`, a file's `tests` edge, `runs`, or the Case set), not merely in file names. Engineering runs it for each capability it builds, and it is a required step before any release-candidate proof; the capability cannot run it (it has no parser).
- **R8. One dependency.** The computer imports `yaml` and Node's built-ins only. No package imports it.
- **R9. Traceability coverage gaps.** Engineering owns this report for now (Kai, 9 Nov); where it finally lives is open. The graph is a requirements traceability matrix, and the report lists its coverage gaps. KAAL's edge words map to the industry terms: *answered by* is *traced to* (Intent answered by Requirements, Requirements by Architecture, Architecture also answers Defects, and all of them by Cases, which is forward and backward traceability from Intent down to Case). An item nothing answers is **untraced**: an Intent no Requirement answers, a Requirement no Architecture element answers, a Defect no Architecture element answers, and an Intent, Requirement, Defect or Architecture element no Case answers. A Case that points at nothing resolvable is **orphaned** (R4 refuses it). The report is an observation and never an implicit pass or fail (it does not change the exit code and gates nothing). A Case answers a Node when it points at it (`tests`) or at something that answers it further in (a Case on an Architecture element answers the Requirements and Intents above it, and the Defects it answers). A disposition for an untraced item is recorded in the repository, as for boundary findings; the computer decides none.

## Architecture

`engineering/case-graph/compute.mjs` (CLI) over `graph.mjs` (the library: `readArchitecture`, `readCases`, `compute`). The computer shares no code with the boundary engine except the `yaml` dependency. Suites (BEST) are a later, separate extension of the same graph: one suite per Case, computed from the edge, never a hand-kept list.

## Testing (RED until the DO)

Engineering Cases on fixtures (no live capability is read): R2 inputs found, R3 each branch computed, R4 each refusal, R5 an outer check that names the Delivery element is Delivery and does not ship, R7 `--check` fails on drift, including a wrong-branch graph and a `cases.json` that keeps the same file names but a changed `tests` edge, and passes on a fresh one, R8 imports; R4 also covers a Case that names a cross-cutting Requirement and one explicit element (the element chooses the branch, an invalid target is still refused) and a `ships` key in front matter. A conformance Case runs the computer on a fixture shaped like Foundation 0.0.2 (the Cases that ship today are exactly the computed Solution Cases), and a fixture with untraced items and an orphaned Case proves R9 (reported, exit code unchanged).
