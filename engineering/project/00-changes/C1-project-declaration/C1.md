# project/C1 project declaration

First, smallest slice of the Project capability: a Project is one Markdown file that declares the Changes it delivers, in order. One package function reads and checks it. No state, no tooling around it, no gate, no WIRE.

## Baseline

`main` holds no Project concept and no `kaal-project` package. Changes already carry plain Dependency rows where a real merge dependency exists (a live PR link). Those stay on the Change and are not repeated in the Project.

## Gaps

| Gap | Target | Gap |
| --- | --- | --- |
| project/G92 | project/I34 | a Project cannot be declared or checked |

## The declaration

```
---
id: project/P1
title: bring control status to main
delivers: [release/C62, controls/C12]
---
```

`delivers` lists Change ids (`<capability>/C<n>`); its order is the delivery order. One-way: the Project names Changes; no Change names the Project. The check receives the Project text and the texts of the delivered Changes from the caller, so it works outside KAAL. It reports findings; it decides nothing and gates nothing.

## Three places (engineering vs package vs .kaal)

| File | Place | Role |
| --- | --- | --- |
| `engineering/project/**` (this Change, I34, Cases T820 to T823, `examples/P1-control-status.md`) | engineering (lab) | the PLAN and KAAL's first worked Project |
| `packages/kaal-project/**` (`lib/project.mjs`, the Skill, `scripts/check-project.mjs`) | package (product) | generic, KAAL-agnostic; written in DO, absent in PLAN, which is why the Cases are RED |
| `.kaal/project/**` | instance | not used until `kaal-project` is on npmjs and embedded; until then the example above is KAAL's Project |

## Exclusions

- No edit of any other collector, Change or package. No dependency except Foundation and Hosting (none needed yet).
- No state, status, schedule or progress tracking of a Project; no back-pointer from Change to Project.
- No CI control, hook, workflow, ruleset, WIRE, npm publication or embedding.
