# C144 requirements added (ids provisional until the collision check at the exact head)

- **guard/F49 Every Solution and Change file is owned, or Guard fails.** [guard/I1, guard/I2] *Owned* means the file's nearest `kaal-guard.json` (the deepest folder that holds it, F43) declares at least one check that applies to it: a check with no `when`, or a `when` that matches the file's path relative to that `kaal-guard.json`. This applies once the repository has any `kaal-guard.json`; a repository with none behaves as before.
  - **Unowned is a fail.** For each changed Solution or Change file that is not owned, Guard prints a `fail` for `ownership`, naming every such path, what is missing (no `kaal-guard.json` above it, or the nearest one names no check for it) and where to register: add a `kaal-guard.json` at the package root or in the open Change folder, or widen the `when` of the nearest one. Guard does not run everything for it and does not hide it: the checks that were selected still run, and the run's status is the fail's.
  - **Delivery is not judged.** [Owner, 2026-11-18: Delivery Architecture, Solution Architecture and Change are three layers. Guard protects Solution and Change, the easy path; the engine is protected by WIRE, the hard path.] A changed path in Delivery is neither owned nor unowned, and no `kaal-guard.json` owns it (the C143 boundary, kept). Delivery is `.github/`, `.githooks/` and `.kaal/`, and the files at the repository root, which F45 already gives to Engineering. Guard treats these as Delivery without being told, and they stay protected by the WIRE and the hard wiring outside Guard; this Change adds nothing to either.
  - **Engineering areas are Solution.** `engineering/<name>` registers through its own `kaal-guard.json` like a product, and a file in it that no `kaal-guard.json` covers is unowned like any other. A piece of an area becomes engine only when a WIRE copies it into `.github` or `.githooks`; the copy is Delivery and the WIRE is its protection. There is no Delivery list and no per-area exemption. This is the coordinator's reading of the Owner's correction at 14:17, not yet confirmed by the Owner.
  - **Guard is wired; what it guards is declared.** [Owner, 14:18] The judgement is part of Guard's `run`, so it applies on every surface where Guard is wired, the hook and CI alike, with nothing surface-specific. A local hook can be skipped, so protection has two layers: the wiring (hook and CI, which is the WIRE's and the wiring owner's) and the declaration (`kaal-guard.json`, which F49 makes complete for Solution and Change). The CI surface is the one that cannot be skipped. This Change wires nothing and adds no required context; making ownership a required check is a separate wiring decision.
  - **Where something is guarded is a decision, not a declaration.** [Owner, 14:19] A `kaal-guard.json` says what is checked (`id`, `run`, `when`). It does not say which hook, CI surface or stage runs it, and it has no member to say so: F43's file refuses any other member. Registering a check, or owning a file under F49, never chooses a surface; the Owner or the wiring owner decides where it runs, as WIRE's scope is an Owner decision. F49 therefore judges ownership the same on every surface and asks for no surface from the registrant.
  - **No root-file fallback.** An earlier draft had a root `kaal-guard.json` own repo-level files and delivery tooling. Delivery is exempt by the rule above, so the root file is not needed for it. A root `kaal-guard.json` stays allowed and works as F43 says for any file it covers.
  - **Removed paths are not judged.** A changed path that no longer exists in the working tree (a deleted file, a closed Change's folder) has no owner to ask for, so closing a Change is never refused for removing it.
  - **An unknown selection judges nothing and says so.** When the changed files are not supplied, or `--full` is given, Guard runs every `kaal-guard.json` as F45 says and prints one note that ownership was not judged, with the reason.
  - **Amends guard/F43** (its sentence that a file with no nearest `kaal-guard.json` selects no check and is not unknown) **and guard/F45** (its statement that unclaimed means Engineering, now replaced by the Delivery rule above); both stand for selection, and F49 adds the judgement on top. The `kaal-guard.json` at the `.kaal/` root still runs on every run. Guard T209's fourth step (a file with no `kaal-guard.json` selects nothing) is amended in the DO: its `.github` example becomes a Delivery path that is not judged. C143's statement that an engineering area root carries no `kaal-guard.json` no longer holds: an area that wants its files owned registers one.

No DO, publication, wiring or version bump is authorized by this PLAN.
