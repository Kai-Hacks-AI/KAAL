# C144 requirements added (ids provisional until the collision check at the exact head)

- **guard/F49 Every Solution and Change file is owned, or Guard fails.** [guard/I1, guard/I2] *Owned* means the file's nearest `kaal-guard.json` (the deepest folder that holds it, F43) declares at least one check that applies to it: a check with no `when`, or a `when` that matches the file's path relative to that `kaal-guard.json`. This applies once the repository has any `kaal-guard.json`; a repository with none behaves as before.
  - **Unowned is a fail.** For each changed Solution or Change file that is not owned, Guard prints a `fail` for `ownership`, naming every such path, what is missing (no `kaal-guard.json` above it, or the nearest one names no check for it) and where to register: add a `kaal-guard.json` at the package root or in the open Change folder, or widen the `when` of the nearest one. Guard does not run everything for it and does not hide it: the checks that were selected still run, and the run's status is the fail's.
  - **Delivery is not judged.** [Owner, 2026-11-18: Delivery Architecture, Solution Architecture and Change are three layers; Guard protects Solution and Change; the engine is harder to change and travels independently.] A changed path in Delivery is neither owned nor unowned, and no `kaal-guard.json` owns it (the C143 boundary, kept). Delivery is: (a) `.github/`, `.githooks/` and `.kaal/`, and the files at the repository root, which Guard treats as Delivery without being told; and (b) the engineering areas named in the **Delivery list**, `{ "areas": ["engineering/<name>", ...] }` at `.kaal/delivery.json` (provisional name). Delivery stays protected by hard wiring outside Guard (F45's rule, C143's wiring split); this Change adds nothing to that wiring.
  - **The Delivery list is read from the base**, like a trusted declaration (guard/F7), never from the candidate. A change that adds an area to the list and changes a file in it in the same push does not exempt that file; the listing takes effect once the base has it. The list itself is under `.kaal/`, so it is Delivery and changes only through the engine's own path. This is the Owner's "products and Changes register as they go, the engine is harder to change", read as a declared list of Delivery areas in place of a `kaal-guard.json` per area. **That reading is mine, not yet confirmed by the Owner**; the other reading is a `kaal-guard.json` in each engineering area.
  - **No root-file fallback.** An earlier draft had a root `kaal-guard.json` own repo-level files and delivery tooling. Delivery is now exempt by the rule above, so the root file is not needed for it. A root `kaal-guard.json` stays allowed and works as F43 says for any file it covers.
  - **Removed paths are not judged.** A changed path that no longer exists in the working tree (a deleted file, a closed Change's folder) has no owner to ask for, so closing a Change is never refused for removing it.
  - **An unknown selection judges nothing and says so.** When the changed files are not supplied, or `--full` is given, Guard runs every `kaal-guard.json` as F45 says and prints one note that ownership was not judged, with the reason.
  - **Amends guard/F43** (its sentence that a file with no nearest `kaal-guard.json` selects no check and is not unknown) **and guard/F45** (its statement that unclaimed means Engineering, now replaced by the Delivery rule above); both stand for selection, and F49 adds the judgement on top. The `kaal-guard.json` at the `.kaal/` root still runs on every run. Guard T209's fourth step (a file with no `kaal-guard.json` selects nothing) is amended in the DO: its `.github` example becomes a Delivery path that is not judged.

No DO, publication, wiring or version bump is authorized by this PLAN.
