# C143 requirements added (reworked to the Owner's `kaal-guard.json` design of 14 Nov, 21:24 to 21:43; ids provisional until the collision check at the exact head)

**Boundary and asymmetry.** Solution and Change checks stay flexible; Engineering's delivery engine is protected outside Guard. Guard's job is stable invocation and reliable execution of the checks that apply.

**Where Guard is told what to run.** Not by a registry and not by an installed copy. One file, `kaal-guard.json`, sits in exactly three kinds of place: a **package root** (Solution), an **open Change folder** (wherever the Change puts it, including under `engineering/`; it is removed when the Change closes) and the **`.kaal/` root** (deployed capabilities, always guarded). **Engineering does not use Guard; its Changes do.** An engineering area root, `.github`, `.githooks` and the root files carry none. Engineering's standing checks have an explicit wiring step outside Guard (`discovery-proposal.md`, last section).

- **guard/F43 Nearest `kaal-guard.json`.** The file is `{ "checks": [ { "id", "run", "when"? } ] }`: `run` is a command (the words Guard runs today, no shell features), `when` an optional glob list relative to the file. Owner and origin follow from the file's place; there are no `origin` or `owner` members and no installed copy. For the changed files between the base and the candidate, Guard takes for each file the **nearest** `kaal-guard.json` up the tree and runs that file's checks, each narrowed by its `when`. A file with no nearest `kaal-guard.json` selects no check and is not "unknown". The `kaal-guard.json` at the `.kaal/` root runs on every run, whatever the diff selects. A Change's checks stop running when its file is removed. Today's `.kaal/config/guard/*.md` declarations keep working unchanged. (T209)
- **guard/F44 A package changes its own contract; Guard checks execution integrity.** A package may change its `kaal-guard.json`, removing checks included: that is the package changing its contract, and there is no "add only" rule. Guard runs the file as the candidate has it and does not judge whether an edit to it is legitimate; whether it may land is the delivery system's, enforced outside Guard. Guard is cannot judge, naming the file and check, only for: a malformed file, a check with no command, or a command that cannot start. (T210)
- **guard/F45 An unknown selection runs everything.** If the changed files cannot be computed, `--full` is given, or the Engine's plan is `{ "unknown": true }`, Guard runs every `kaal-guard.json` and says so. `run` takes an optional `--plan <file>`: `{ "in-flight": [folders] }` adds those folders' files to the selection (a capability whose own resolved dependency tree changed is in flight; Engineering computes it, never Guard). A plan that is unreadable, malformed or empty is cannot judge. No outcome is ever a silent success. Guard computes no ownership and no dependency graph. **Owner decision (20:19):** the full run happens on the merge queue, which is where it fits; the separate wiring owner implements that later. This Change itself wires no gate, event or schedule. **The rule behind them (Owner, 21:19):** every file is either Solution, owned by its capability, or Delivery tooling, owned by Engineering. There is no "shared" category. Anything shared is Delivery, and its coupling is Engineering's to solve, never a capability's in-flight cost. The decisions below are that rule applied. **Owner decisions (20:21 to 20:25):** shared files are owned by Engineering, and unclaimed means Engineering; the single lockfile is an Engineering-tooling constraint (npm workspaces), not a product one, so a lockfile change does not put a capability in flight by default. A capability is in flight through its lockfile only if its own resolved dependency tree changed, which Engineering computes per package or solves by changing tooling. **Root `package.json` (Owner, 20:26):** it is Engineering's. For `workspaces` and `overrides`, a capability is in flight only if an override changes its own resolved tree. Root scripts are convenience, since capabilities own their scripts, so a root script change puts no capability in flight. For root `devDependencies`, a capability is in flight only if a tool it actually uses changed version. **`.github` (Owner, 21:18):** it is 100% Engineering. GitHub is delivery tooling with zero Solution content, so a `.github` change never puts a capability in flight; it is judged by its own Cases plus the full run on the merge queue. No capability check lives in `.github`: capability checks are Guard registrations. This is the Engine's input to the plan, never Guard's. (T211)
- **guard/F46, F47, F48 withdrawn.** F46 and F47: delivery controls and policing of registrations are outside Guard. F48: there is no installed copy, hence no `guard/registered` namespace and no change to guard/F1 or the boundary Case guard/T30. The ids are not reused.
- **guard/A21 Discovery.** Finding the nearest `kaal-guard.json`, the selection (F43), the integrity checks (F44) and the plan (F45) sit in the runner's declaration reading (guard/A1, guard/A3); the adapters are unchanged. The shape of the capability (ownership, definition, installation contract) follows Core's (T213).

**Not in this Change, recorded so it is not lost.** Guard runs from its deployed copy in `.kaal/`, not from the package source, so a change to the Guard package cannot alter the Guard that checks it (package versus deployment, the same rule across the board); graduation is package, embed into `.kaal/`, main, with no separate Change type; in ACT a finished Change's cases are unwired from Guard because target testing guards them from then on. These belong to the next Changes (`change.md`). **Open, Owner has not decided:** a changed file with no owner at all; the suggestion is that Guard reports an ownership defect rather than running everything.
