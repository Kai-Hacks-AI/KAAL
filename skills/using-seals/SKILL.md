# Using Seals

A seal closes a unit: a directory whose files must not change once sealed. Sealing writes `seal.json` into the unit, recording the hash of every other file in it.

Units form a named chain. The using system names each chain (lowercase kebab-case) and decides which units belong to it and in which order; this skill never knows what a unit means. A unit is given as a relative path beneath the root of portable segments separated by `/`: letters, digits, `_`, `-`, and dots only between them, never a Windows reserved name such as `con` or `nul`, and never starting at the root with `seals.json`, which names the chain heads and the lock kept there. That rules out every spelling Windows or macOS would resolve to another directory. A chain refuses units that are listed twice (also when they differ only in case), contain one another, or pass through a symlink or a file, before anything is read or written. Each seal also records the previous seal of its chain, so changing any sealed unit breaks its own seal and every seal after it. Each chain's head, kept in `seals.json` at the root, records every sealed unit of the chain in order and the newest seal, so removing trailing seals is noticed too, and no chain can seal over a unit another chain has sealed, even one whose seal file was removed.

Seal with `scripts/seal.ts <root> <chain> <unit>...`: every open unit of the chain is sealed, oldest first, and the chain's head moves to the newest seal. Sealing refuses a chain whose seals are already broken, an empty unit, a unit holding anything but regular files and directories (symlinks, FIFOs, sockets, devices), and a unit inside or containing a unit already sealed by any chain or recorded in another chain's head, and writes nothing when it refuses. Every chain's head shares `seals.json`, so sealing holds `seals.json.lock` at the root while it runs and refuses to start while another sealing holds it; a lock left behind by a sealing that crashed is removed by hand; if a write fails halfway, it removes the seals it wrote, leaving the chain as it was. A fully sealed chain is left as it is. A using system that seals several chains under one root at once calls `sealChains` from `scripts/seals.ts`: it holds the lock across all of them and seals all or nothing, so if any chain refuses or fails, the seals written for the chains before it are removed and the heads restored.

Check with `scripts/check.ts <root> <chain> <unit>...`. It reports files added, changed or removed after sealing, a seal that no longer matches its own content or belongs to another unit, a seal file or `seals.json` holding anything but exactly the bytes sealing writes, a seal that does not chain to the one before it, a sealed unit after an open one, symlinks or special files in a sealed unit, a seal that is unreadable or not structurally a seal, a unit or unit contents that cannot be read, a seal removed from a unit up to the head, a seal beyond the head, and a head that is missing, records units that do not begin the chain, or does not match the newest unit's seal. A check that overlaps a sealing (the lock is held, or the heads change while it runs) reports that a sealing is in progress instead of a half-sealed chain; check again once it has finished. Checking never takes the lock, so verification stays read-only and independent checks never wait on each other. That is a deliberate consistency boundary: a check that overlaps a sealing may fail transiently (a sealing that fails and rolls back entirely within one check can still show it a seal that is gone again), but it never falsely passes. A caller that needs a definitive result checks when no sealing is running, or checks again after sealing.

Seals and heads are only ever read from regular files, never through a symlink or from a FIFO or device, and heads are replaced by renaming, never written through a link.

File-based seals catch accidental and piecemeal changes, including removed trailing seals. They cannot stop someone who deletes or rewrites a whole chain together with its head: anything stored beside the units can be removed with them. A using system that needs more keeps seals append-only where it controls history, for example by refusing changes that modify or delete existing seal files.

Seals hash exact bytes. The using system must keep sealed files byte-exact wherever they are checked out, for example by disabling line-ending conversion for them. When to seal and what to seal is the using system's decision; this skill only seals and checks.
