# Retro

## Learned

That most of this was already true somewhere. The comparison of closed Changes existed twice, once in admit and once in a shell loop, and the old shell script's cases translated into the new tests almost one for one, which showed me the semantics were never in the shell, only the plumbing. What was genuinely new was the question of where seals live: asking it before building saved me from baking kaal-core's package layout into a KAAL operation.

## Liked

That the decision came before the code. The Owner chose installed KAAL over a faithful port, so the operation is two small functions over two directories, it widens protection without any layout knowledge, and the repository's own KAAL and Changes became real test subjects: each installed seal removed and each closed Change touched is refused.

## Lacked

A way to compare what the shell control protects with what this operation protects, other than reading both. The scope is wider on purpose, but I had to establish by hand that nothing the old control caught is now missed, and nothing records that argument except this Work.

## Longed

For the control to run this operation instead of the shell loop soon, so that the comparison has one home in practice and not only in code, and for the immutability hardening to be decided on its own so that this operation can grow to cover tree and Change seals without a judgment call about repairs.
