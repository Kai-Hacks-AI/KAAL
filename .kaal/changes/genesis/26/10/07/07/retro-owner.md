# Retro

## Learned

The first KAAL-addressed communication capabilities demonstrate that optional Skills can be installed without prescribing a host's own workflow.

The difficult part was not the two carrier forms but protecting the host boundary: path handling, preservation across installation, and honest review provenance.

The initial Worker-created reviews did not meet our independence arrangement. The independently supplied later rounds made the distinction visible and uncovered concrete defects.

KAAL must not mistake technical ability to spawn another context for authority to appoint a Reviewer.

## Liked

The Skills remain separate, optional and small.

Incident asks what happened versus what was expected; Request asks what is wanted versus what is missing.

The carriers remain local, and no transport or automatic backlog behaviour has entered the Change.

The Worker acknowledged the review-process mistake rather than concealing it. The independent Reviewer provided reproducible findings until convergence.

## Lacked

A pre-established and unambiguous Reviewer authority boundary, which is being addressed separately.

Reusable, reviewed path-handling machinery would have reduced duplicated security work.

The installer still needs explicit knowledge of each new instance-owned state directory.

Most importantly, communication has not yet been exercised end-to-end from a real client to KAAL.

## Longed

For Enercon or another willing client to select these Skills and create a real carrier, then for KAAL to collect it through an available adapter without confusing visibility with ownership.

That will test the carrier choices in practice.

I also want the review-authority correction to land without hard-coding subscriptions, vendors or GitHub into KAAL governance.
