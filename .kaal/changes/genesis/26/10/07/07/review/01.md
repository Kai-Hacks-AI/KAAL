## Findings

The meaning is in good shape: the Node keeps known, reachable and all apart, keeps no list, names no host or transport, and the install change is proportionate. The findings below are about the script and the Skill's honesty. I ran the 19 acceptance tests (all pass) and probed collect.mjs in a scratch directory.

1. **A refused or failed write can destroy another record (R8, R9).**
   File: `packages/kaal-collecting/skills/kaal-collecting/scripts/collect.mjs` (`write`, lines 99-111; `clientDir`, lines 84-89).
   `clientDir` checks `existsSync(target)` long before `write` calls `mkdirSync(target)`. If the client record appears in between (a concurrent run, or the long copy walk in `reached`), `mkdirSync` throws EEXIST. The `catch` then runs `rmSync(target, { recursive: true, force: true })`, which deletes the record that the other attempt had just written, and reports "nothing was recorded". That is a silent replacement, and indeed destruction, of a recorded client, which R8 forbids ("a client already recorded is never replaced"), and a refused attempt leaves the world worse, not unchanged. Resolve it so that cleanup only ever removes what this attempt created: for example, an EEXIST from the creating `mkdirSync` is a refusal that removes nothing, and only a later failure removes the directory this call made. The same applies to the `begin` race (line 72), where a collision should be a clean refusal. Add an acceptance test for it. The Evidence claim "a refused attempt writes nothing" does not cover this case.

2. **`begin --date` accepts dates that do not exist and years that do not mean a year (R8, Architecture).**
   File: `collect.mjs`, `begin` (lines 61-73).
   Probed: `begin k --date 2026-02-31` creates `collections/26/02/31/01`, and `--date 1999-01-01` creates `collections/99/01/01/01`. `Date.parse` is not a calendar check, and the two-digit `YY` loses the century. A collection address then claims a day that never happened, or collides with a different century. The flag is also not in the Architecture or the Skill's script list, so it is undocumented surface. Either validate the date properly (round-trip it) and state the flag where the scripts are listed, or remove it. Consider refusing years outside the `YY` the layout can state.

3. **The Skill states the `carriers/` default as if it were settled, not as the assumption it is (Architecture "The one assumption", R11).**
   File: `packages/kaal-collecting/skills/kaal-collecting/SKILL.md`, step 3 ("by default the `carriers/` directory of its KAAL directory").
   The Architecture says this is the single assumed location, to be replaced when the carriers' own location lands. The Skill, the text the collecting agent actually follows, says none of that. Failure scenario: the agent asks a client's adapter for `carriers/`, the client has no such directory (the carriers' real home is elsewhere, or not yet defined), and the agent records `reached` with an empty `<dir>`. The collection then asserts "reached, nothing carried for KAAL", which is false, and it is exactly the collapse of reached with empty that R9 is meant to prevent. State in the Skill that `carriers/` is an assumption pending the carriers' own location, not a defined boundary. State also that a client whose exposure directory is absent is not "reached, empty": it is `unreached` with that reason (or not recorded as an exposure at all). Say what the agent should do when it cannot tell.

4. **Paths git cannot faithfully carry are collected and recorded as if they were (R6, R8; Evidence).**
   File: `collect.mjs`, `reached` walk (lines 122-135); `.gitattributes`.
   Probed: an exposure containing `.git/config` and `.gitignore` is accepted and recorded in `reach.md`. Git refuses to add a path with a `.git` component, so the committed collection would silently lack a carrier that `reach.md` lists. A collected `.gitignore` would hide sibling carriers from `git add`. Either way the record in Git no longer matches the record on disk, and `check` on a checkout fails or passes on a different set. Also, the walk does not refuse other names that are unsafe on common platforms (trailing dot or space, Windows reserved names). The Evidence claims names "unsafe across platforms" are refused, which overstates what is checked (only backslash, control characters, non-NFC and case collisions). Resolve by refusing `.git` components and ignore-control file names, or by saying plainly in the Skill and the Evidence which names are refused and which are not. Add a test for whichever is chosen.

5. **`check` follows symlinks inside a collection and misses stray content (R5, R8, Evidence).**
   File: `collect.mjs`, `check` (lines 150-193).
   Probed: replacing a collected carrier with a symlink to `/etc/hostname` makes `check` read the link's target outside the collection and report only a hash mismatch. A symlinked `carriers/` directory would be listed and read in the same way. `check` also ignores any file beside `reach.md` and `carriers/` in a client directory, so `check` exits 0 on a client directory holding unrecorded extra material, although it is documented as the check that "every collected carrier still matches". Make `check` `lstat` before reading and report a non-plain-file in the collection as a problem, and report anything in a client directory other than `reach.md` and `carriers/`. Add tests. Duplicate path lines in `reach.md` also pass the form check (the render comparison is satisfied); they should be a problem.

6. **Node and Skill differ on what collecting does (minor, consistency).**
   Files: `packages/kaal-collecting/kaal/Collecting-KAAL.md` and `packages/kaal-collecting/skills/kaal-collecting/SKILL.md`.
   The Node says collecting "takes what a client exposes" and is "the KAAL side" of the relationship. The Skill says "It does not reach clients: you do" and that collecting writes only the record. A reader of the Node alone can take collecting to include reaching, which the Architecture and R4 assign to the adapter. Make the Node's sentence say that the collecting agent takes it, by whatever means it has, and that collecting is the record of that, so the two do not contradict.

## Not findings, noted

- `reached` copies whatever directory the agent hands it; it cannot know whether that directory is the client's exposure. That limit is stated in the Architecture ("the adapter produced") and the Skill ("do not stretch an access"), and is honest. A `--from` that is itself a symlink is refused, and symlinks inside are refused. A swap between `lstat` and `readFileSync` is a TOCTOU window that I do not count, because the agent controls `--from`.
- The `engineering/kaal-install` change is proportionate: one constant, matching comments, and a test, and it was needed because a real collection failed `check-kaal-install`. `.gitattributes` is likewise right.
- The collections directory is a record of attempts only, not a registry, given that names are per-collection and nothing aggregates them.
