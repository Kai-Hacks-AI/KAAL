# Retro

## Learned

That moving the compass into Embedding KAAL exposed the right dependency boundary. Changing needs to know the process, but it should not invent identity; Sealing already owns that truth. The resulting sibling dependency is therefore useful information rather than something to hide. I also learned that the process compass can travel independently of the actions it describes: an embedded agent can now know that the Worker must seal Work even though that operation itself has not yet been delivered there.

## Liked

That there remains one process definition rather than an embedded copy and an engineering copy. Engineering now consumes the same compass that Embedding KAAL receives, which makes the repository a proving ground for the delivered capability instead of a privileged implementation of it. I especially liked the isolated embedding test: removing the repository around KAAL is a strong test of whether this Change actually crossed the Engineering-to-Embedding boundary.

## Lacked

A declared way for one Skill to depend on another. "kaal-changing" now genuinely requires "kaal-sealing" for the compass to answer, but that relationship is discovered only when the capability is used rather than understood by installation. I also still lack the corresponding portable acts for sealing Work and closing a Change.

## Longed

For an embedded KAAL to carry enough of Changing KAAL that an agent can not only ask where it is and whose act comes next, but perform every non-human act the process assigns to it, with dependencies made explicit rather than discovered through failure.
