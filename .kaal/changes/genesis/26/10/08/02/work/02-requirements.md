# Requirements

Scope: one capability, a Skill by KAAL's existing meaning (one package, a Node typed by Core's `Skill` Node, an Agent Skill, acceptance in `engineering/`), following the shape of `kaal-review` and `kaal-retro`. Nothing here needs a new Core meaning.

1. **One Skill.** `kaal-intent` (Node `Intent`), one package, independently selectable. Its Node says what the capability means to KAAL and nothing of mechanism: to state what is wanted and why, and to establish that statement as a target. It says it primarily serves the Owner, that outcomes and boundaries are what it states, and that it does not define Requirements, Architecture or implementation.
2. **Optional, never automatic.** Not Core, not needed for a valid embedding, not installed by embedding KAAL; it joins an installed KAAL only by being selected by the exact ID of its Node. It declares no sibling.
3. **No template, no role.** No required headings, parts or names; no schema. No Role Skill, and Intent defines no role: it uses "the Owner" as KAAL's processes already do and assigns nothing.
4. **The smallest mechanical minimum.** An Intent is a text file that begins with the line `# Intent` and says something after it, in bytes that are stable wherever it is kept (valid UTF-8, no NUL, `\n` line ends, final newline). Nothing else is judged mechanically. Whether it says what is wanted and why, has clear boundaries, has drifted into how, or is what the Owner wants, is judgement: the script says so and does not pretend.
5. **A reviewable result.** An Intent has an exact identity: the SHA-256 of its exact bytes, which is the identity a file has anywhere in KAAL (it must agree with Sealing's `artifact-id` for the same file). Because Review names a result and an identity and knows no kind, an Intent can be reviewed with `--of Intent` without any change to Review, and without Intent knowing Review.
6. **Established means fixed.** Establishing an Intent puts forward that identified statement; the Owner's say-so is not an artifact and nothing records it. What changes afterwards is another Intent with another identity. An Intent that cannot be delivered as stated is not edited to fit; what is done with it is the Owner's.
7. **Usable beyond Changing KAAL.** Nothing in the Node, the Agent Skill or the script mentions a Change, Work, ROWING, a Reviewer, sealing, Git or a host. Where Intents are kept, when one is owed, who describes or reviews it, and how an outcome is judged against it are decided by whatever asks for an Intent.
8. **The Agent Skill helps with the thinking, not only the file.** It teaches: start from the Owner's words; give a draft rather than a questionnaire, asking at most the one question that would change it most; say outcomes, reasons and boundaries; notice Requirements, Architecture and implementation and set them aside rather than writing them in (a method the Owner actually wants is a boundary and stays); check; establish by identity; never edit an established Intent.
9. **Changing KAAL consumes it without weakening its fixed target.** By wording only, in its Skill text and ROWING reference (and their installed projection): where an Intent was established with Intent, the Worker keeps it in `work/01-intent.md` byte for byte, its identity is the target the rounds and the Owner's judgment are measured against, a copy in `work/` that no longer has that identity has been changed (which no one inside the change may do), and establishing a different want is another Intent for another change. Changing KAAL still does not need Intent to work. Its sealed Nodes, its evaluator `change-state`, its lifecycle, seats and order are untouched.
10. **Unchanged.** Core, `.github`, every sealed Node other than the new one, the installer, the evaluator, and every closed Change. The installed projection (`skills/kaal-changing/`) follows the package by `npm run install-kaal`.
11. **Proof.** Acceptance on what ships: delivery through Core and a sealed Node, the script through the command an agent runs (what it accepts, what it refuses and says why, that it never writes), identity agreeing with Sealing's, an Intent reviewed through Review's delivered script, Changing KAAL's text and its evaluator's behaviour with and without Intent, and a repository that is not KAAL (not installed unless selected).

## Not decided

- Where Intents are kept, and whether an established Intent should carry a seal. Sealing exists as its own capability; whether and when to seal an Intent is the process's to say.
- Whether Changing KAAL should check the identity of `work/01-intent.md` against an established Intent mechanically (for instance in `change-state`). Today the discipline is stated in words, as it was.
- Whether the Owner's establishing should ever leave an artifact. This Change leaves it as no artifact, like the Owner's judgment in Changing KAAL.
