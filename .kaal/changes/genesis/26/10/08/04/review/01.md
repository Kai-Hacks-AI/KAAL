## Findings

This round reviews the design-only Work at PR head b61e8513378e40b673a07308854317450a59833c, against the fixed Intent, the Requirements and Architecture, existing KAAL semantics, and Kai's recorded directions on PR #70 and the closed design Change genesis/26/10/08/03 (#71). No implementation is requested by these findings.

1. [P2] Keep byte deduplication separate from communication identity (03-requirements.md lines 11 and 20; 04-architecture.md lines 11–12 and 27). R3 makes the same client's same bytes necessarily one Request or Incident sighted again. Kai's first Owner direction explicitly asks for repeated sightings without equating identical bytes with the same client communication. This distinction is observable with existing capabilities: two calls to request.mjs write with the same Wanted/Missing texts created requests/26/10/09/01.md and 02.md, both with SHA-256 806b1629400ba4ee74f4ae5d3352013d791fceb905bb7e2f7eb42b3087db794b. Collection kept both paths and check passed. There is no evidence that these two creation acts are one communication. Preserving both paths avoids byte loss, but does not justify that semantic inference. Resolve R3 and the identity table so a (local client record, hash) key describes the stored byte evidence and does not assert sameness of the originating Request/Incident beyond what is known. State how the existing source-path/collection mappings retain the distinction and unknowns. This does not require opaque IDs, reconciliation or a new capability.

2. [P2] Specify the raw Collection's Record location and reference resolution (03-requirements.md R6, R9, R10; 04-architecture.md lines 7, 17, 22 and 31). R10 places collections, as well as the three new entities, in a caller-supplied Record location distinct from the Engine. The architecture gives the records argument only to reached/unreached, leaves begin and its layout unchanged, and names collections by a relative YY/MM/DD/CC address without saying which directory supplies that address. Existing begin/reached/check all resolve collections beneath their first <kaal-dir> argument. Merely adding an optional persistence directory leaves raw observations under that argument and leaves a reader/checker unable to resolve the mapping from the new Record alone unless that relationship is specified. Two collection stores can each allocate 26/10/09/01, also colliding at the proposed sighting address if combined into one records directory. At design level, say what argument denotes the collection Record, how it relates to the optional persistent records directory, and how a sighting resolves its source collection unambiguously. Show the intended Engine/Record/Subject relationship in an External example and distinguish the compatibility behavior without the optional argument. Reuse the explicit-location direction of #71; no universal root, locator implementation, migration or Changing-contract change is required. Colocation is not itself a finding: #71 permits Engineer's explicit choice to retain Record inside .kaal. The unresolved point is the binding, which must not be inferred from Engine location.

3. [P2] Make the continuity assertion part of the sighting design (03-requirements.md R4; 04-architecture.md lines 17, 39 and 44). R4 and the Owner's latest direction require existing-name reuse to be refused unless the collector explicitly asserts continuity, and require the sighting to record that assertion as an assertion. The only sighting form specified is today's reach.md plus one collection line. Today's form contains client name, outcome, adapter, optional reason and hash/path pairs; none records whether continuity was asserted. The example likewise carries no such evidence. A later reader therefore cannot distinguish explicit reuse from grouping by spelling alone, despite the design's assurance that attribution is never inferred from a name. Specify the minimal assertion representation and its first-sighting versus reuse behavior, including unreached attempts, and state that strict reading/checking requires it for reuse. Keep the local observed-client record distinct from proof of the originating installation's identity. No identity framework or implementation is required.
