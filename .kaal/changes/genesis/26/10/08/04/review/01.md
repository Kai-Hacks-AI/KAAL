## Findings

F1 (P2) — The proposed reuse of Core admission has no supported delivery path.
Against R9, R15, R23 and R25. In 03-architecture.md:103,109,167, check is defined as running Core's admit() over Engine plus BRAIN. But packages/kaal-core/src/index.ts exports only payload, installedSkills, installedExtensions, registerSkill and registerExtension. Its package.json exposes only "."; admit/candidates are internal nodes.ts functions, and the deployed Engine contains artifacts, not that module. The prototype runs a source copy as nodes.mts. That proves the candidate Form, but it does not show how the independent installed Skill can run the same admission machinery without a source checkout, a private API dependency, copied semantics, or a Core API change. Resolve the execution/delivery path explicitly in the Architecture, within the unchanged-Core boundary; name any genuine gap instead of treating it as already supplied. Demonstrate the proposed path outside the engineering source tree. No implementation is requested in this Change.

F2 (P2) — Core admission does not enforce the proposed body-reference contract.
Against R18 and the claim in 03-architecture.md:71,103,109. admit() validates the candidate's own seal and its type chain; it does not read citations in the Markdown body. Using the exact proposed Learning type and candidate bytes with the unchanged nodes.ts, I added a body citation to an absent 64-hex ID and resealed the resulting scratch Node: admit() still admitted it. A citation with the wrong name beside a present Learning's ID was also admitted. The section 7 prototype does not add this validation; its cited-by calculation is a substring count. Therefore checks 1–4 are not all obtained by Core admission, and the relationship integrity claimed by the Architecture has not been shown. Distinguish Core's existing admission from the additional citation validation Learning needs; state the resolvable name/ID citation form and demonstrate refusal of absent, unsealed and wrongly named body targets. Keep evidence identities distinct from Node citations.

F3 (P2) — Establishing a new Learning cannot literally run the established-BRAIN checks first.
Against R18 and the success criterion. 03-architecture.md:115–119 says establish takes a draft anywhere, runs every check, and only then writes its ID-named file and seal. Checks 1–3 require that ID-named file, its seal and Core admission, which requires the seal. An ordinary new draft has none of those; the unchanged admit() refused the proposed candidate when added without its marker. Spell out the pre-write validation of a new draft, distinct from checking an already established BRAIN, including how the prospective candidate is examined without writing or sealing the destination first. Define the failure/write behavior and the already-held case. Demonstrate the first-establishment case from an unsealed draft, not only admission of candidates already sealed in scratch.

F4 (P2) — Establish has no way to require the evidence resolution R18 promises.
Against R12 and R18. 03-architecture.md:105 makes Record optional for check and says absent evidence resolution is reported, not refused. The establish command at :115 has no --record input and nevertheless promises that all checks pass before writing. As specified, a well-formed line naming a nonexistent Change or a missing evidence file can remain unresolved and the draft can be established; the refusal exercised in 04-evidence.md relied on a separately supplied Record. Distinguish permissive reading of a portable BRAIN from establishing a new Learning. Define the evidence-holder input and the refusal policy for establishing when evidence is unavailable, missing, or not a closed matching Change. Reconcile this with the broader evidence kinds and the declared Change-only resolver limit; unsupported kinds must not become silently accepted evidence. Demonstrate that failed evidence resolution leaves the destination untouched.
