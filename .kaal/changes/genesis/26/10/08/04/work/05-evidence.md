Owner's four points:

1. A collection produces persistent, client-attributed sightings: a sighting file per attempt under `clients/<name>/sightings/`, naming its collection and listing `<sha>  <source path>`.
2. Requests and Incidents stay identifiable across repeated collections: the second and third sightings list the same hashes and paths; the stored carriers are found by `(client record, hash)`. The key is storage identity only, as `review/01.md` asked.
3. No unnecessary duplication: the repeat wrote 0 new stored carriers (acceptance: directory listing unchanged); equal bytes at two paths give one stored carrier and two listed paths.
4. Existing behaviour and refusals intact: the 28 existing acceptance tests pass unchanged; a refused exposure with `--keep` writes no sighting and no stored carrier; without `--keep` only `collections/` is written.

## Disclosures

- Round 01 and R8 speak of "the README of the records". I did not write a file into the caller's Record: the limitation is stated in `SKILL.md` and the package `README.md`. If a README must sit in the Record, that is a further small step.
- `check-record` treats `incidents/<name>/` and `requests/<name>/` as stored carriers only for names that have a client record. In a directory that is also a client's own KAAL directory, its own dated carriers (`incidents/26/…`) are therefore not read as stored carriers unless a client happens to be named `26`.
- A refused reuse leaves the begun, empty collection in place, as every refusal of `reached` already does.
- A Record is checked by `check-record`; whether the raw carriers of each collection still match is still `check`, run per collection.
